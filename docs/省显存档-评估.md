翻译成 bash 的等价命令（**已落地成可执行脚本** `C:/Project/local_model/incoming/lowvram/run-18200.sh`）：

```bash
cd C:/Project/local_model/incoming/lowvram/engine
PATH="$PWD:$PATH" ./llama-kvmem-server.exe \
  -m ../model/Ternary-Bonsai-2-27B-PTQ1_0.gguf \
  --host 127.0.0.1 --port 18200 \
  -c 65536 -ngl 99 --kv-dtype q4_0 -ub 64 -b 256 \
  --kvmem-block-tokens 128 --kvmem-sink-tokens 4096 --kvmem-budget 8192 \
  --kvmem-gen-reserve 4096 --kvmem-method recency --kvmem-query-policy user \
  --kvmem-cpu-gb 12 --kvmem-gpu-ratio 0.10 --spec-type none
```

**`-ngl 99` = 全部层上 GPU；权重是否 mmap/流式？** —— 是的，GGUF 走 mmap，但 `-ngl 99` 会把 5.54 GiB 权重**全部搬进显存**（实测坐实，见 §3）。**"压到 6 GB"靠的不是流式权重，而是「KV 分层 + 有界 GPU 工作集」** —— 权重永远要 5.54 GiB，8 GB 卡上只剩 ~0.9 GiB 给 KV，所以 KV 必须下 host。

### 1.3 三条硬约束（违反就 500 / 截断 / 起不来 —— 包方 `判据.txt`【六】+ `03` §三）

1. `--kvmem-sink-tokens` **≥ 4096 且显著小于** `--kvmem-budget`（相等 ⇒ 每个请求 HTTP 500 `incoming block was not placed on GPU`）
2. 单次生成 ≤ `--kvmem-gen-reserve`（默认 4096，**含思考**），超了静默截断
3. `--spec-type none` **不许动** —— 本包**刻意不带 MTP 件**（小显存下投机实测 decode 41.63 → 23.69 t/s，**−43%**）

## 3. 性能实测（按包方 `MUST-DO` C1 口径：长提示 + 长输出 + 贪心 + 丢首发 + 取中位）

### 3.1 decode（显存带宽绑）

| run | 提示 token | 输出 token | decode | prefill |
|---|---|---|---|---|
| 1（首发，丢弃） | 1,275 | 117 | 35.96 t/s | 389.0 t/s |
| 2 | 521（cache 756） | 117 | 36.78 t/s | 384.7 t/s |
| 3 | 521（cache 756） | 117 | 36.89 t/s | 390.4 t/s |
| **中位（丢首发）** | | | **36.84 t/s** | **387.5 t/s** |

> ⚠️ **口径瑕疵（如实记）**：`max_tokens` 给的是 512，但温度 0 下模型自己停在 117 / 176 token，所以输出长度落在 **117–176**，没到包方要求的 ≥400。三次读数极稳（35.96 / 36.78 / 36.89，离散 < 3%），可信；但**严格意义上"长输出"这一条只算部分满足**。

**带宽折算核对**：包方基准 57.75 t/s @ 736 GB/s ⇒ 本机理论 = 57.75 × (288 ÷ 736) = **22.6 t/s**。我们实测 **36.8 t/s，是折算值的 163%**。
⇒ 说明 4060 Ti 上 decode **没被带宽打满**（多半因为 KV 在 host + 工作集只有 8192 token，命中率高）；**这对小卡是好事**，但也意味着这个数不能当作"卡的能力"外推。

### 3.2 prefill（算力绑）

| 口径 | 读数 |
|---|---|
| 20,440-token 提示（单次，`prompt eval time = 49,933 ms`） | **409.35 t/s** |
| 同上过程内衰减：0.08 → 0.96 进度 | 429.1 → 411.6 t/s（**仅降 4%，长提示不掉速**） |
| 1.3–1.5k 提示 | 384–390 t/s |

包方基准 758.45 t/s @ 4080S。折算到本卡（算力比约 0.45）= 341 t/s ⇒ 我们实测 409 t/s ≈ **折算值的 120%**，**落在"达标"档**。

### 3.3 吃满显存余量有用吗？——**没用**（配置 B）

`KVMEM_BUDGET=16384` + `KVMEM_GPU_R=0.25`（把 GPU 工作集翻倍、KV 上卡比例翻 2.5 倍）：

| | 默认（budget 8192 / ratio 0.10） | 配置 B（budget 16384 / ratio 0.25） |
|---|---|---|
| 就绪后显存 | 6,113 MiB | **6,287 MiB** |
| 请求后显存 | 6,147 MiB | **6,371 MiB** |
| decode | 36.89 t/s | **36.58 t/s**（**无增益，反而略低**） |
| prefill | 390.4 t/s | 384.8 t/s |

**⇒ 多花的 174–224 MiB 显存买不到任何速度。** decode 是带宽绑，工作集大小不改变每 token 要读的权重体量。**默认的 8192/0.10 就是本卡的甜点**，那 2 GB 余量留着更安全（余量 2,075 MiB → 桌面/浏览器/别的进程抢显存时不至于爆）。

## 4. ★ 核心问题：8 GB 显存能开多大上下文？

**答案：显存根本不限制上下文，限制它的是 host 内存。** 三组实测：

| 配置 | `n_ctx` | 就绪 | 显存（就绪后 / 请求后） | 功能 |
|---|---|---|---|---|
| 默认 | **65,536** | 6.86 s | 6,113 / 6,147 MiB | ✅ 答 `OK` |
| 对照 A | **262,144（256K）** | **9.95 s** | **6,113 / 6,147 MiB** | ✅ 答 `OK` |
| 对照 B | 65,536 + 大工作集 | 4.64 s | 6,287 / 6,371 MiB | ✅ decode 36.58 |

**`-c 65536` 与 `-c 262144` 的显存读数完全一样（6,113 MiB）。** 这条把"KV 下 host"坐实了：
显存 = 权重 5.54 GiB（固定）+ GPU KV 工作集（由 `--kvmem-budget` 定）+ 计算缓冲，**与 `-c` 无关**。

**上下文真正受什么限制 —— host 侧 KV 池**：

```
KVMEM_TIERS cpu_bytes=12884901888  cpu_slots=5461  slot_bytes=2359296
```

- `slot_bytes=2,359,296` = 2.25 MiB，`--kvmem-block-tokens 128` ⇒ **128 token / 槽**
- `cpu_slots=5461` ⇒ **CPU 侧 KV 容量 ≈ 5461 × 128 = 699,008 token**
- `-c 65536` 只用 512 槽（**9%**）；`-c 262144` 用 2,048 槽（**37%**）

**⇒ 结论分三层：**

1. **本机实测上限**：**262,144（256K）已验证可起、可正确作答、显存不变。**
2. **池容量上限**：**≈ 699K token** —— 也就是说 `-c 524288`（512K）**都不需要额外内存**（池子是 `--kvmem-cpu-gb` 定的，与 `-c` 无关）。包方说的"1M 需 40 GB"是**把 `KVMEM_CPU_GB` 一起调大**的情形。
3. **实践上限**：**host 物理内存**（见 §5 的风险项，这是本报告最需要警惕的地方）。

**推荐配置（推算，待下个窗口实测）**：
```
set KVMEM_CPU_GB=6  &  set KV_CTX=262144  &  其余保默认
→ 池 ≈ 2730 槽 ≈ 349K token 容量，-c 262144 只占 2048 槽（75%），host 侧 6+5.54 ≈ 11.5 GB
```

## 5. ⚠️ 风险 —— 包方文档**站不住**的一条：host 内存

包方 `README`/`判据.txt`/`附录A` 三处都写 **"host ≈ 5.5 GB（`cpu_bytes=12 GiB` 是上限不是预占）"**。

**本机实测对不上：进程工作集 16.6–18.1 GiB。**

| 配置 | 进程 WS（实测 `WorkingSet64`） |
|---|---|
| `-c 65536`（保命档） | 17,861,849,088 B ≈ **16.6 GiB**（就绪后 17.9 GB，请求后 17.7 GB） |
| `-c 262144` | 18,584,690,688 B ≈ **17.3 GiB** |
| 配置 B（budget 16384） | 18,978,598,912 B ≈ **17.7 GiB** |

**归因（实测推断，非包方口径）**：
`17.9 GB ≈ `--kvmem-cpu-gb 12`（12 GiB，**看起来是被真占出来了**）+ 权重 mmap（5.54 GiB）。`
三种配置下 `cpu_bytes=12884901888` **恒定不变**（与 `-c` / `--kvmem-budget` 都无关），进一步支持"这 12 GiB 是按 `--kvmem-cpu-gb` 直接铺出来的池，不是纯上限"。

**后果（本机真实场景）**：
- 跑之前物理可用内存 9.5 GB；跑起来后系统要大量回收页面文件/压缩内存；**停掉之后可用内存回到 19.2 GB**。
- 也就是说：**开着 Chrome + 英雄联盟客户端（实测合计占 ~4.7 GB WS）再跑这个档，31 GB 机器会明显吃紧**，包方 `排错篇` 症状 8「机器变卡」不是理论风险。

**处方（包方 `03` §二 允许，不用改文件）**：

## 6. ★ 和现役 NInfer 方案（8091）的关系：能不能共存 / 要不要替换

**先说一个关键事实：两边跑的是同一个基座模型。**
现役 `models/bonsai2_27b_ternary_ptq1_native_mtp.ninfer` 与本包 `Ternary-Bonsai-2-27B-PTQ1_0.gguf` 都是 **Bonsai-2-27B 三元 PTQ1**（权重 5.52 vs 5.54 GiB，差在容器格式：`.ninfer` vs GGUF）。所以**这不是"换更强模型"，是"换一套引擎+K V 策略"**。

### 6.1 硬碰硬对比（同为 8 GB 卡、同为本机实测/本机文档）

|  | **现役 NInfer（:8091, fast 档）** | **本档 llama+KVMem（:18200）** | 谁赢 |
|---|---|---|---|
| 引擎 | `ninfer-serve-89.exe`（按 cc 重编过） | `llama-kvmem-server.exe`（预编译，不挑卡） | — |
| 权重 | 5.52 GiB（`.ninfer`） | 5.54 GiB（GGUF PTQ1_0） | ≈ |
| **常驻显存** | **7,074 MiB / 8,188**（余量 **507 MiB**） | **6,113 MiB / 8,188**（余量 **2,075 MiB**） | **llama +970 MiB** |
| **decode** | **98 tok/s**（计数型）／ **48.5–50 tok/s**（散文） | **36.8 tok/s**（无投机，任何文本） | **NInfer** |
| **prefill** | **965 tok/s** → 842（长） | **409 tok/s**（20k 提示） | **NInfer 2.4×** |
| **可用上下文** | 池 **32,000**（fast）／ 64,000（long）；`/v1/models` 报 131,072 但**不可信** | **`-c` 65,536 默认 → 262,144 已实测 → 池容量 ≈699K** | **llama 2~8×** |
| 投机解码 | ✅ MTP draft-4，接受率 81–82% | ❌ 刻意不带 | NInfer |
| 就绪 | （文档未记，量级同档） | **6.9 s**（256K 时 10 s） | ≈ |
| 需编译/适配卡 | **是**（按 cc 8.9 重编，换卡要重来） | **否**（内嵌 75/80/86/89/90/120a 六档 cubin + PTX） | **llama** |
| host 内存 | RAM 侧 KV **3.0 GiB** | **实测 WS 16.6–17.9 GB**（含 12 GiB 池） | **NInfer** |
| 视觉 | 已裁掉 | 带 mmproj（8G 别开） | ≈ |
| 长文检索质量 | `NINFER_KV_RETRIEVE=8192` 内容寻址（已验证有效） | `recency`（默认）／`retrieval`（未验） | NInfer（已验证） |

### 6.2 能不能共存

**不能同时驻留。** 6,113 + 7,074 = **13,187 MiB > 8,188 MiB**。三条路：

1. **换着跑（推荐）**：需要长上下文时停 8091、起 18200；完事反向切。两边脚本都已备好（`scripts/serve.sh` ↔ `incoming/lowvram/run-18200.sh`），端口不冲突（8091 / 18200）。
2. **只留 8091 的 long 档**：`PROFILE=long` 已是 pool 64,000 / decode ~31 t/s。**如果需求只到 64K，那这款 llama 档没有存在价值**（它 65,536 上下文下 decode 36.8，只比 long 档 31 快一点，但 prefill 只有 409 vs NInfer 的 842+）。
3. **加卡**（不在本次范围）。

### 6.3 8 GB 上 llama 系 vs NInfer 系的取舍（一句话版）

> **NInfer 系 = "把 8 GB 卡榨到极限换速度"，代价是「按卡重编 + 池容量硬顶 + 余量只剩 507 MiB」。**
> **llama+KVMem 系 = "不折腾就能跑 + 上下文想开多大开多大"，代价是「decode 慢 25%~2.7×、prefill 慢 2.4×、host 内存吃 12 GiB」。**

具体到决策：

| 你的场景 | 用哪个 |
|---|---|
| 日常问答、代码补全、**要快**（98 t/s） | **8091（NInfer）** —— 不换 |
| 长散文生成（44–50 t/s） | **8091（NInfer）** —— 仍更快 |
| **整本书 / 整个代码库 / 200K+ 材料一次读完** | **18200（本档）** —— 这是 8 GB 卡上**唯一**能给你 >64K 有效窗口的方案 |
| 换显卡 / 换机器、不想重编 | **本档** —— 预编译、六档 cubin 通吃 |
| 机器只有 16 GB 内存 | **本档要先把 `KVMEM_CPU_GB` 压到 4**，否则会爆 host |
