# 8 GB 上「200K 上下文」最终结论（RTX 4060 Ti 8G · 2026-10-30 · 全部本机实测）

## 0. 一句话

**8 GB 显存做 200K，不存在「单遍、又快、又准」的选项。** 划算的是两条：
**① 日常 40K 池快问快答（NInfer，107 tok/s）；② 200K 文档走分片（NInfer + `tools/longdoc.py`，316 s/本，可复现 8/8）。**
llama.cpp 的 262K 窗口是真的能开、能答对、能办到「二次读 1.1 s」，但**首读是 O(n²)**：209K 首读 3.2–6.5 小时。

## 1. 三条路实测对照

| | NInfer 40K 池（现役） | NInfer + 分片 | llama.cpp 262K 窗 |
|---|---|---|---|
| 上下文上限 | 40,000（硬） | 无限（按片） | 262,144（硬窗口） |
| 209K 文档首读 | 378.6 s（**只可信一次**） | **316 s** | 3.2–6.5 h（O(n²)） |
| 正确率（8 针） | 首发 8/8；同进程第二次 2/8；150K **0/8（49 个编造暗号）** | **8/8 ×2 次，0 编造** | 30K 冷读 8/8、0 编造；热读 8/8 |
| 重复读同一份 | 30K：45.8 s → 2.0 s（前缀缓存） | 每次都 316 s | **0.9–1.1 s（cached 29,992）** |
| decode | 107 tok/s（计数）/ 41.5（散文） | 同上 | 95–97（热读）/ 65（冷读后） |
| prefill | 8k 1,108 / 37k 1,001 tok/s | 每片 46 s（≤27.3K/片） | **O(n²)**：`t ≈ 4.7e-7·n²` 秒 |
| 峰值显存 | 7,459 / 8,188 MiB | 同左 | 7,872–7,931 / 8,188 MiB |

**为什么单遍 200K 在 8 GB 上不可能**（算术，不是调参）：
权重 6.39 GB（PTQ1_0 1.75 bpw，必须整份驻留）
+ 200K 位置 KV（q3_0，14,336 B/位置）= 2.87 GB
⇒ 9.26 GB > 可用 7.9 GB，**差 1.4 GB**。只能把 KV 尾部放到主机内存（`--kv-vram-cells` / NInfer 的 ring），
而一旦 KV 在主机内存，prefill 就要反复过 PCIe，成本随位置平方增长。

## 2. 三条路各自该怎么用

### 2.1 日常（≤36K 上下文）：NInfer，最快
```bash
bash C:/Project/local_model/scripts/switch.sh ninfer
```
池 40,000 / rk2v4-e8 / MTP draft4 + win8 / `--device-state-slots 0` / CUDA Graph allowance 16。
实测：计数题 107 tok/s、散文 41.5 tok/s、峰值 7,459 MiB（余 729）。

### 2.2 长文档问答（40K → 200K+）：分片，唯一「可重复」的 200K
```bash
bash C:/Project/local_model/scripts/asklong.sh <文件> "问题"     # auto = 超池自动转分片
```
209K → 9 片（每片 ≤27.3K，全部在池内）→ 316 s → 8/8、0 编造，连跑两次结果一致。

### 2.3 真·全窗口单遍（一次建好、之后秒回）：llama.cpp 262K
```bash
bash C:/Project/local_model/scripts/switch.sh llama
```
窗口 262,144 / q3_0 / `--kv-vram-cells 93,696`（显存线）/ 其余 pinned RAM / sparse host-tail / MTP+lookup。
代价与收益：首读 30K ≈ 4 分钟（干净进程 236 s）、60K ≈ 28 分钟、100K ≈ 1 小时、209K ≈ 3–6 小时；
**建好之后每一次追问 0.9–1.1 s（cached ≈ 全部命中，decode 96 tok/s）**。

## 3. 三个必须知道的坑（都是踩出来的）

1. **显存线每次启动重算**：free 7,949 MiB → 线 93,696；free 7,798 → 线 82,688。起服前先关掉占卡程序。
2. **别的程序抢显存会让 llama 服务器「自杀」**：日志 `spill  VRAM spilled to system RAM (+530 MiB): the server is much slower now`，随后进程消失。
3. **prefill 速度依赖实例历史**：同一台机器、同一参数、同一份 30K 文档，干净进程 236.4 s，跑过半个 209K 的进程 476.3 s（2.0×）。
   ⇒ 以后测「首读多快」必须用刚启动的进程，否则读数无法互相比。

## 4. 已否掉的方案（省得再试）

| 方案 | 否掉的原因（实测/一手） |
|---|---|
| Strata（q36 迷你引擎）跑 Qwen3.6-35B-A3B | 8 G 能起（`READY`），但 trunk 4.40 GiB + staging 1.10 GiB ⇒ 上下文上限 **512–1,024 cell**，等于没用 |
| Strata 全量路线跑 125B（Qwen3.8-Flash-Next） | 要 35 GB 模型 + 约 44 GB 内存；本机 31.1 GB，只能靠磁盘 mmap（每个 chunk 重读专家，实测他人 519 GB 读盘/32K 提示） |
| Gyro-S（58.5 GB） | 官方低内存档，但 8 GB 档社区读数 20–37 tok/s 且质量分 KL 0.268 弱于 IQ2_XS 0.236 |
| NInfer 直发 209K 反复追问 | 首发 8/8，第二次 2/8，150K 0/8（HTTP 200、无报错行）⇒ **只可信一次** |
| GPU 解锁（gpu-unlock） | 只提 FP16/BF16 矩阵算力；实测我们 prefill 里只有 36.4% 走被钳的 A16 通路 ⇒ 上限 +16.3%，decode 与显存 0 |
