# 200K 上下文：本机可用的最终处方（RTX 4060 Ti 8GB · Bonsai 27B ternary PTQ1 · NInfer KVMem 20261019）

> 日期 2026-10-30。全部数字来自本机实测（同一张卡、同一支引擎 `C:/Project/local_model/engine/ninfer-serve-89.exe`、同一份模型 `models/bonsai2_27b_ternary_ptq1_native_mtp.ninfer`）。
> 未实测的格子一律标「未验」，不当结论用。

---

## 0 · 结论先给

1. **8 GB 显存能「喂」200K，但不能「反复问」200K。** 直连超池请求（prompt 209K > 池 40K）第一次给对（8/8 命中），**同一引擎进程里第二次开始静默答错**：HTTP 200、日志无 error、答案里出现文档中不存在的编造暗号（150K 那次 49 个假暗号）。
2. **可用的是三条路，按「问几次」选**：

| 场景 | 走哪条 | 输入上限 | 实测 | 可重复 |
|---|---|---|---|---|
| 日常对话 / Agent | **A 池内直连**（现役 40K 池） | 单请求 ≤ ~36K（留 4K 输出） | 97–98 tok/s（计数）、45.7（散文） | ✅ 无限次 |
| 长文档问答 / 一次性读 200K | **B 分片地图-化简**（`tools/longdoc.py`） | 200K 文档 → ≈9 片，每片 ≤27K | **209K 文档 8/8 全对、0 编造、316 s** | ✅ 可重复（连跑两次同结果，见 §2.2） |
| 想原样喂整段给模型看 | **C 重启后一次性直发** | ≤ ~209K | **8/8、378.6 s** | ⚠️ 每个引擎进程只可信一次 |

3. **别做的事**：在同一个引擎进程里连发两个超池请求。这是目前唯一会「静默错」的动作，而它没有任何报错提示。

## 2 · 三条路怎么用

### 2.1 A 路 · 日常（现在就在跑）
```bash
# 引擎（已在 8091 上跑着）
cd /c/Project/local_model && PROFILE=ctx40 GW=1 PORT=8091 MODELID=local FORCE=1 bash scripts/serve2.sh
# 客户端直连
curl -s http://127.0.0.1:8091/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"local","messages":[{"role":"user","content":"你好"}],"max_tokens":64}'
# 网关（给 DSH / 其他客户端；会自动把超长请求裁到池内）
curl -s http://127.0.0.1:8081/v1/models
```
- 池 40,000 token / 625 页 / rk2v4-e8，峰值 **7,469 / 8,188 MiB**（余 719）。
- DSH 侧已经指到 8081，`contextWindow: 36000`、`streamIdleTimeoutMs: 900000`（200K prefill 要 380 s，默认 300 s 会超时重发 ⇒ 双份 prefill 崩机）。

### 2.2 B 路 · 长文档（推荐）
```bash
# 默认打 http://127.0.0.1:8091/v1，每片 <=26K，出 答案.md
python tools/longdoc.py --doc 长文档.txt --out 答案.md \
  --question "把文档里所有「关键记录」的暗号按顺序列出来"

# 更小的池（如 24K）就把每片压到 22K
python tools/longdoc.py --doc 长文档.txt --out 答案.md --shard-tokens 22000 --question "..."

# 自检（造 200K fixture + 8 针，端到端验一次）
python tools/longdoc.py --selftest
```
- 做法：按行切碎 → 每片单独「只逐字取证、无关输出 NONE」→ 汇总取证再统一作答（「缺信息就写未找到」，不许脑补）。
- 209K 文档 → 自适应切 **9 片**，每片真实 prompt 5.5–27.3K（全在 40K 池内），总 **315.7 s**，**8/8 全对 0 编造**；同一份文档连跑两次 316.0 s / 315.5 s，**完全可重复**。
- 换算不是拍脑袋：首片按「纯中文下界 1.75 字节/token」保守切（≈13.5K token），拿到引擎回的真实 `usage.prompt_tokens` 后算出本文档的字节/token（本 fixture 3.63），再按 0.93 安全系数切剩下的片 —— 这样纯中文文档不会被撑爆池。
- 与 C 路的差别：全程不碰「超池」，所以**不污染引擎**，可以连问。
- 代价：跨片的「关系型」问题（需要同时看两处并推理）会被削弱——分片取证只保证「逐字有据」，不保证「跨片推理」。

**这个工具踩过两个坑（都已修，写在这里免得后人再踩）**：

1. **换算比例不能一刀切。** 原先固定 4.246 字节/token（来自另一份混合文档），遇到纯中文文档会低估一半 ⇒ 分片被撑到池外 ⇒ 静默答错。改成「首片保守 + 实测校正」。
2. **合成轮的提示词里不能出现「未找到」这种拒绝词。** 实测：同一份取证，用户轮末尾加一句「…只有取证没有相关内容时才写未找到」⇒ 模型直接吐 3 个字「未找到」；把尾巴删掉（拒绝词只留在 system 轮）⇒ 8/8 全对。27B ternary 这种小模型对词面极其敏感。
3. 兜底：合成环节万一还是空/「未找到」/报错，工具会**用取证原文逐字汇总**交付，不把空答案甩给用户（`__FINAL_ERROR__` 也一样）。

### 2.3 C 路 · 一次性原样直发
```bash
bash scripts/asklong.sh 长文档.txt "把文档里所有「关键记录」的暗号按顺序列出来" --oneshot
# 也可以直接看四路：auto（默认）/ --shard / --oneshot / --pool 40000 --shard-tokens 26000
```
- 会 `taskkill` 引擎 → 重启（≈60–90 s）→ 单发一个请求 → 结束。209K 实测 8/8 / 378.6 s（总 wall ≈ 8 分钟）。
- **每个进程只可信一次**；第二次起请直接重启，或改用 B 路。

## 3 · 为什么会这样：两条引擎 bug（这是本次最重要的发现）

### bug 1：打分表 `n_blocks` 是跨请求高水位，永不重置
- 209K 请求里 `n_blocks` 从 1 一路涨到 3,268（自洽）；此后同进程所有请求恒为 **3268**，`skip=2756 / candidates=3204` 一字不变。
- 100K 只有 1,562 块、150K 2,344 块，但 `KEPT` 里出现**超出本请求范围的块号**（max=3267）；最后一条 KEPT 里 87.3%/87.5% 的预算打在上一请求的**幽灵块**上。
- 结果：真正该留的页被挤掉，答案里出现编造暗号——而 HTTP 仍是 200。

### bug 2：ring 的 evidence 预算写死 128 页，且从不借用 free
```
[ring] budgets: protect=0 skeleton=0, evidence=128, recent=0, free=490 (pool 625)
       backend_pages=7 backend_capped=1 [protect+skeleton+evidence+recent+backend+free == pool: yes]
```
- 1,731 次采样**一字不变**：evidence 恒 128 页 = 8,192 token = 209K 提示的 **3.9%**；而打分器按 512 块（32,768 token）选；`free=490` 页（占池 78%）闲置，从不借给 evidence，`recent` 恒 0。
- 检索侧其实没坏：`restored_frac=1.000`（1,246 次 `preferred=152,079 = restored=152,079`）——不是「还原失败」，是「选错了页」。

### 两条都不足以单独解释
「先 209K 再复跑 → 8/8 变 2/8」：同预算、同长度却翻面 ⇒ bug 2 单独不成立；209K 复跑块号全合法仍 2/8 ⇒ bug 1 的「越界」也不足以解释。**两者叠加 + 跨请求状态残留**是目前最贴的假设（未验到底）。
前缀缓存已被 seed777 对照排除；池内请求永远干净（C1/C2）。

### 给作者的最小复现
1. 起一支引擎（pool 40,000 / rk2v4-e8 / MTP 开），确认 `/v1/models` 200。
2. 直发一个 209K-token 请求（8 针 needle 埋在 3/14/27/39/52/65/78/92% 深度）→ 8/8。
3. 同进程再发同一个请求 → 2/8，且 `grep -c "prompt exceeds the resident Device KV pool"` = 1。
4. 证据行：`kvmem_score: SELECT ... n_blocks=3268 ... skip=2756 candidates=3204 kept_range=[0,3267]`（n_blocks 冻结）；`[ring] budgets ... evidence=128 ... free=490`（1,700+ 次不变）。
5. 建议：`n_blocks` 每请求重置为 `ceil(prompt/64)`；`evidence` 上限 = `min(pool - backend - sink, ceil(prompt/64))`，并允许从 free 借页；两个预算进启动日志。

## 4 · 自检与排错

| 症状 | 查什么 | 处置 |
|---|---|---|
| 同一进程越问越离谱 | `grep -c "prompt exceeds the resident Device KV pool" logs/engine-40k.log` > 1 | 重启引擎（`taskkill /F /IM ninfer-serve-89.exe` 再起） |
| 客户端 5 分钟超时重发 | 200K prefill 要 380 s | 客户端超时 ≥ 10 min；DSH 已设 900 s |
| prefill 掉到 ~180 tok/s | 池 > 50K 触发显存⇄内存换页 | 池保持 40,000 |
| 起服即拒 | `requested Engine runtime reservation requires ... only ... available` | 池 52,000 是带 MTP 的实际上限，56,000 起不来 |
| 答案正确但慢 | 首次请求要载 5.52 GiB 权重 + device profile 自测 | 等 `/v1/models` 200 |

速度基线（本机，同卡）：
- 短问 97–98 tok/s（MTP draft4 / win8 / 接受率 ~80%）；散文 45.7。
- prefill：37K 提示 **963 tok/s**；209K 提示有效 ~552 tok/s。
- 池内 30K 前缀复用：第二次请求 **2.0 s**（cached）。

## 5 · 边界（别再往上试了）

| 池 | 结果 |
|---|---|
| 40,000 | ✅ 7,469 MiB，prefill 963 @37K，本档定稿 |
| 52,000 | ⚠️ 起得来（7,573 MiB）但 prefill 崩到 ~180 tok/s（换页），不可用 |
| 56,000+ | ❌ 拒启：runtime reservation 1,092,297,216 B > 可用 1,037,041,664 B |

`--max-context` 仍是 262,144（逻辑上限），真正的约束是池。**池 ≠ 上下文**：引擎的 `/v1/models` 报 262,144 是逻辑值，别拿它当真实窗口。

## 6 · 想要「真的 200K 随便问」怎么办

1. **换卡**（唯一根治）：池要 ≥ 209K token ⇒ 按 0.836 MiB/页，需要 ≈ 2.7 GiB 以上额外显存 + 保留输出空间；16 GB 卡（4060 Ti 16G / 5060 Ti 16G）能直接开 200K+ 池，社区实测（`二把刀呀` 4060 Ti 16G + 64G DDR4）256K 下 41–50 tok/s。
2. **换模型架构**（MoE + Strata）：权重激活少、专家可停内存，8G 也能 128–256K，但那是 125B MoE（37.6 GB 权重）另一套引擎，与本机 39.2 GB（31.1 RAM + 8 VRAM）只能勉强 Q2，且与现役不能并存。
3. **保持现状 + 分片**（本机最优解）：日常 40K 直连、长文档 `longdoc.py` 分片，都拿满 8 GB 能给的。
