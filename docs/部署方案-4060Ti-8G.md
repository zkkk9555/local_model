# RTX 4060 Ti 8GB 本地 27B 部署方案

> 状态：**方案稿，尚未动手**。本机数字来自 nvidia-smi 实测；NInfer 数字来自仓库 docs 与外部 8GB 回执；解锁数字来自 nv-uefi-unlocker 公开对照。凡未在本机复现的，标注【外推】。

---

## 0. 结论先行

1. **能跑，而且是『官方有一份 8GB 配方』的那种能跑** —— 模型是 Bonsai 2 27B ternary PTQ1（6G 那个包），引擎是 2026-10-19 三架构包里的 sm_89 版。
2. **可信上下文 = KV 池大小，不是 --max-context 那串数字**。不开投机约 66,432 token，开投机约 38,016 token。【外推·按官方 8G 配方】
3. **解码速度和解锁无关**（8GB 上瓶颈在主机侧），解锁只抬 prefill，大约把 20k 首字延迟从 ~25 s 压到 ~16–20 s。
4. 建议顺序：**先把服务跑通 → 测出你自己的基线 → 再决定要不要折腾 U 盘解锁**。

## 2. 模型选择：7 个文件怎么挑

| 文件 | 大小 | 真身 | 本机 8GB 能否跑 |
|---|---|---|---|
| bonsai2_27b_ternary_ptq1_native_mtp.ninfer | 6G | Bonsai 2 27B **PTQ1 三值** | ✅ **唯一可用**，常驻 5.52 GiB |
| Ternary-Bonsai-2-27B-ninfer-v3-mtponly.ninfer | 7.1G | Bonsai 2 27B **PQ2 精简** | ❌ 7.13 GiB 权重 + 约 1 GiB 运行时溢出 |
| Ternary-Bonsai-2-27B-ninfer-v3.ninfer | 8.9G | Bonsai 2 27B **PQ2 完整** | ❌ 8.16 GiB |
| gsq_rco_iq3_s_dflash2_prop.ninfer | 14G | **真·Qwen3.8-27B** IQ3_S | ❌ 13.4 GiB |
| swift-qwen38-rco-iq3s.ninfer | 14G | **真·Qwen3.8-27B** IQ3_S | ❌ 13.4 GiB |
| swift-qwen38-q4km.ninfer | 19.6G | **真·Qwen3.8-27B** Q4_K_M | ❌ 约 18.3 GiB |
| （第三个包 nemotron） | — | 另一个模型 | ❌ 无关 |

**哪个是原版千问 3.8-27B 量化**：最后三个（两个 14G + 一个 19.6G），全部 16GB 显存起步。
**你说那个是不是最合适**：是，仍然是 6G 那个 PTQ1。之前我说它『未发布』，这个判断作废 —— 它在模型包里就有。

- 三值（ternary）不是普通量化，是从 Qwen3.8-27B 重新推导的权重，必须用 NInfer 专属引擎跑。
- 27B 三值 KV 几何：64 层里 4 层出 1 层 full attention → **16 层带 KV，25,728 B/token**。

## 4. 配方 A：长上下文档（不开投机，建议先跑这套）

```bat
set NINFER_KV_WINDOW=65536
set NINFER_KV_RING=1
set NINFER_HOST_PAGEABLE=1
set NINFER_KV_REUSE_HOSTBACKED=1
set NINFER_KV_RETRIEVE=
set NINFER_TERNARY_PTQ1_FAST=1

ninfer-serve.exe ^
  --model bonsai2_27b_ternary_ptq1_native_mtp.ninfer ^
  --kv-capacity auto --kv-headroom-mib 1024 ^
  --kv-dtype rk4v4-e8 ^
  --max-context 131072 --max-concurrency 1 ^
  --prefill-chunk 256 --gdn-state-fp16 --no-cuda-graph ^
  --host-kv-mib 16384
```

**启动后必须核对 banner**：

```
capacity | KV 66,432 tokens, rk4v4-e8, auto | pages 1,038/1,038 | runtime 1.32 GiB
```

对不上就说明配置没吃到，别急着测。

- 权重 5.52 GiB + 运行时 1.32 GiB = 6.84 GiB，留 0.6–0.8 GiB 余量。
- NINFER_KV_RETRIEVE 必须是**空值**，不是 0。
- 只设 NINFER_KV_RING 不设 NINFER_KV_WINDOW → 引擎直接拒绝启动（已知坑 B30）。
- rk4v4-e8 的 PPL 代价 +0.30%（rk2v4-e8 是 +2.14%，别用）。

## 5. 配方 B：快档（开 MTP，短上下文换速度）

```bat
set NINFER_KV_WINDOW=10240
set NINFER_KV_RETRIEVE=8192
set NINFER_KV_REUSE_HOSTBACKED=1

ninfer-serve.exe ^
  --model bonsai2_27b_ternary_ptq1_native_mtp.ninfer ^
  --max-context 262144 --max-concurrency 1 ^
  --derive-session-keys --max-shared-prefixes 0 ^
  --prefill-chunk 1024 ^
  --kv-capacity 12800 --kv-dtype rk2v4-e8 --host-kv-mib 3328 ^
  --spec mtp --draft-tokens 1 --mtp-attention-window 8
```

- 池只有 12,800 token，引擎实测 7,365 MiB。
- 官方原话：**要池就不要开投机**。开 MTP 权重从 5.52 → 5.94 GiB，池从 66,432 掉到 38,016。
- 8GB 卡**绝对不要开 --spec dflash2**（dflash2 要多 1.3–2.07 GiB，MTP 只要 332–430 MiB）。

## 6. 验收（别只看『服务起来了』）

1. tools/自检-模型件.ps1 -Model <path> -VramGb 8 → 应打印 COMPONENTS / SPEC_CHOICES。若退出码 3（BARE 件）→ **绝对不要加 --spec**。
2. banner 里的 pages N/N 必须满。
3. 短 prompt 测通 → 20k 长 prompt 测首字延迟 → 流式长输出测会不会被回滚（输出需 ≥10 页空闲）。
4. 超池 prompt（比池大）必须走分段注入网关，直接单请求会得到 **HTTP 200 但答案不可信**（引擎只记一条 unverified）。这是本项目最危险的行为，务必开检索：NINFER_KV_RETRIEVE 非空。

## 7. 可选：GPU 算力解锁（nv-uefi-unlocker）

### 7.1 对我们的负载有多大用

NInfer 的 prefill 走 mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32（src/ops/common/mma.cuh:33-40）—— BF16 输入 / **FP32 累加**，正好是被限速的那条路径。

- 算一下：27.3B 参数、约 48.7 GFLOP/token，实测 prefill 801.6 tok/s → **39.0 TFLOPS**；卡的原厂峰值（4060 Ti 桌面实测）是 **46.78 TFLOPS** → 已经贴着 83% 天花板。带宽侧上限约 23,000 tok/s，所以完全是算力瓶颈。
- 解锁后峰值 75.28 TFLOPS（+60.9%）。
- **但**：作者的 4090 对照里，指令吞吐接近翻倍，实际 cuBLAS FP16 GEMM 只涨 12%–34%，另一个量化 MoE 负载**零提升**。所以别信满倍率。
- 乐观：prefill → 1,250 tok/s，20k TTFT 约 16 s
- 保守：prefill → 960 tok/s，20k TTFT 约 21 s
- **解码不变**：8GB 上解码是主机侧瓶颈（host 51.4 ms/round vs GPU 0.62 ms），且 5.52 GiB / 288 GB/s = 20.6 ms 的下限本身也是带宽。

### 7.2 本机可行性（10DE:2803，Ada AD106 桌面）

- ✅ 作者兼容性矩阵里 **2803 是实测通过**的（PR #5：回放 + 解锁 + 四写读回；8192 阶矩阵 FP16 46.78→75.28、BF16 47.24→76.71、FP32 12.17→12.04 TFLOPS）。
- ✅ Secure Boot 已关。
- ⚠️ **必须从 Windows 里点『重启』进入 U 盘**，不能冷关机启动。我们是混合模式（核显带屏），冷启动会让独显处在 D3cold，BAR0 全 0xffffffff，工具会以 dGPU powered off 拒跑。**不能等它休眠之后再进**。
- ⚠️ **每次冷启动都要重放一遍**（解锁是易失的，不刷 BIOS、不烧熔丝、断电即清）。
- ⚠️ 进系统后如果没提速，先怀疑覆盖丢了：电源域进 D3cold、某些复位、驱动重新初始化都会清掉易失状态。
- ⚠️ 即使是『无解锁载荷的回放模式』，也会写固件状态并做设备复位，**不是只读检查**。
- ⚠️ 作者明确：correctness 通过，但**没做长时间满载稳定性 / 温度 / 功耗测量**。

### 7.3 判断

**收益只在前段，代价是每次开机多一道 U 盘流程 + 一次固件验签绕过。**
→ 建议：先按第 4/5 节把服务跑起来、测出你自己**未解锁的基线**，再决定要不要解锁做 A/B。不要一开始就折腾。

## 9. 风险清单

1. 超池单请求会**静默给出错误答案**（HTTP 200 + 看似合理的胡说）。这是首要风险。
2. 8GB 档只有 RTX 4070 Laptop 的完整实测回执，4060 Ti 桌面属于【外推】。
3. 驱动 616.92 不在解锁项目的实测范围里。
4. 固件验签绕过 → EULA / DMCA 1201 层面的暴露面，自行判断。
5. --max-concurrency 在 ring 模式只能 1。
