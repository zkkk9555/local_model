# 本机部署实测报告：Ternary-Bonsai-2-27B 在 RTX 4060 Ti 8G 上跑起来

生成时间：2026-10-29 · 全部读数来自本机实测（RTX 4060 Ti 8GB / Win11 / Ryzen 7 7800X3D / 31.1 GB RAM）

## 一、结论先说

- 27B 三元模型**已经在 8 GB 卡上跑起来了**，服务地址 http://127.0.0.1:8091 ，OpenAI 兼容接口。
- 常驻显存 **7,074 MiB / 8,188 MiB**，权重 5.52 GiB，RAM 侧 KV 3.0 GiB。（此处原写「KV 池 99,712 token」是误读，见第十一节更正：该配置的可靠上限其实是 46,272 token。）
- 生成 **31 tok/s**（稳定），预填充 **1,106 → 842 tok/s**（随长度衰减）。
- 20k 题面首字 **22 秒**；同一份长文第二轮命中前缀缓存，67k 题面首字从 **84 秒掉到 0.54 秒**。
- 长文检索正确：36k、67k token 的针测试都能正确答出埋在中段的密钥。
- 投机（MTP）与 CUDA Graph 在 8G 档的第一版结论是「都没有收益」，**这条已被推翻**：MTP `draft-tokens 4` 把解码从 31.7 提到 98 tok/s（见第十节）。CUDA Graph 确实无收益。

## 三、模型件是怎么来的（本报告最关键的一步）

作者公开渠道只有 PQ2 完整件（8.87 GiB），8 GB 卡装不下；真正能进 8G 的 PTQ1 件只在他的夸克网盘，没有分享链接。
所以我们**自己把 PQ2 件降成 PTQ1 件**，并在本机复现出与官方完全同尺寸的产物：

1. 下载 `WaveCut/Ternary-Bonsai-2-27B-NInfer-v3` 的 `Ternary-Bonsai-2-27B-ninfer-v3.ninfer`：9,520,051,456 B，sha256 `cdc4810b0ff17c40d0f62cf214b6e0bcd08346e9eb05ca53371507037793c14a`。
2. `scripts/recontainer.py` 重新铺容器：丢掉 `dflash2 / vision / proposal` 三条绑定（403 对象 / 1.738 GiB），保留 text + mtp（790 对象），并把 322 张 `t2_g128_fp16` 张量按 `decode → encode` 无损转成 `ptq1_g128_fp16`（每 128 权重 34 B → 28 B，比例 0.8235）。
3. 产物 `models/bonsai-ptq1-mtp.ninfer`：**6,394,697,216 B**，payload 6,394,414,592 B，与作者夸克里 `bonsai2_27b_ternary_ptq1_native_mtp.ninfer` 的 6,394,697,216 B **完全一致**。
4. 引擎自报 `ftype=bf16+fp32+ptq1_g128_fp16+q8_g32_fp16`、`size=6,381,571,072`，与官方 PTQ1 件的元数据逐项相符 —— 说明这条重打包路线产出的就是同一个东西。

无损性验证：对 `weight/000000 [4096,5120]` 做 t2 → ptq1 → decode 往返，`codes identical: True`、`scales identical: True`，字节比 0.8235。

注意：仓库自带 `tools/`（2026-10-19 线）打不开这个 2026-09-30 容器 —— `schema.py:316` 要求 manifest 有 `identity` 且 `model_id`/`weights_id` 非空，源件没有这个键。所以重打包器是按 `framing.py` / `schema.py:176 plan_objects` / `schema.py:439 encode_directory` 自己铺的，manifest 键集照抄源件。

## 四、启动方式（可直接复用）

```bash
cd /c/Users/Administrator/Documents/deepseek-harness/default-workspace
bash scripts/serve.sh              # 默认就是下面这套已实测配置
```

等价展开：

```bash
export NINFER_KV_WINDOW=98304 NINFER_KV_RETRIEVE=8192 \
       NINFER_HOST_PAGEABLE=1 NINFER_KV_REUSE_HOSTBACKED=1 NINFER_TERNARY_PTQ1_FAST=1
engine/ninfer-serve-89.exe models/bonsai-ptq1-mtp.ninfer \
  --host 127.0.0.1 --port 8091 \
  --max-context 131072 --max-concurrency 1 --max-shared-prefixes 0 \
  --derive-session-keys --prefill-chunk 1024 \
  --kv-capacity auto --kv-headroom-mib 512 --kv-dtype rk2v4-e8 --host-kv-mib 3072 \
  --no-cuda-graph --gdn-state-fp16 \
  --default-reasoning-effort none --default-max-tokens 8192 \
  --log-stats-interval-ms 5000 --log-colours off
```

- 模型名对外是 `bonsai2-27b`；接口 `/v1/models`、`/v1/chat/completions`、`/v1/messages`、`/v1/responses`。请求头 `x-session-affinity: <任意会话名>` 用来串同一会话的前缀缓存。
- 停止：`taskkill //F //IM ninfer-serve-89.exe`。
- 冷启动 62 s（含 10–50 s 路由标定，标定结果落盘 `%LOCALAPPDATA%\ninfer\device-profiles.json`）；之后重启 3.6–3.9 s。
- 就绪判据：日志出现 `listening on http://127.0.0.1:8091`，且 `GET /v1/models` 返回 `status.value=loaded`。

## 六、调参记录：哪条路走通了、哪条没走通

| 尝试 | 结果 |
| --- | --- |
| `--spec mtp --draft-tokens 1`（投机） | **变慢**：26.7–28.5 tok/s，权重涨到 5.94 GiB，池被压到 25,984 token。不启用。 |
| 开 CUDA Graph（去掉 `--no-cuda-graph`） | 31.2 tok/s，与关闭时**完全一样**，不换。解码是带宽瓶颈，不是发射瓶颈。 |
| 窗口 16k / 32k / 49k / 65k / 98k | 解码与预填充速度**基本不变**（31.2 / 1,100），差别只在池大小。最终取 98,304 窗口。 |
| `--kv-capacity 768` 这类小数字 | 参数单位是 **token 不是页**，误用会得到一个 768 token 的池。用 `auto` 最省事。 |
| 默认 `--kv-headroom-mib 1024` + MTP | 直接起不来：`automatic KV headroom requires 1073741824 bytes, but only 1037041664 bytes are available after weights`。压到 512 MiB 才过。 |

## 七、边界与风险

1. **题面 token 不能超过池 token**（第一版此处写的 99,712 是误读，真实是 46,272；新 fast 档 32,000、long 档 64,000，见第十一/十二节）。超了就是作者文档说的「单请求答案不可信」，会打 `unverified`；再往上必须走他的分片注入网关。`/v1/models` 报的 context_window 是 131,072，但**实际可靠上限是池大小**。
2. 显存只剩 **507 MiB** 余量（桌面 QQNT / OBS / GameViewer 已占约 239 MiB）。跑长任务前建议关掉 OBS 采集和 QQ。若想更稳，把 `WINDOW` 降到 65536（池 66,944，余量约 1,019 MiB），速度不变。
3. 输出很长时要保证池里还有至少 10 页空闲，否则内容会被丢弃/回滚。
4. 只有 1 路并发（`--max-concurrency 1`），`--max-shared-prefixes 0` 是硬要求。
5. 推理会进思考循环，`--default-reasoning-effort none` 已经关掉；平台层仍建议对 EMPTY / TRUNCATED 做护栏。
6. 盘上现在有两份模型：源 PQ2 9.5 GB + 自造 PTQ1 6.4 GB。确认稳定后可以删掉源件省 9.5 GB。

## 九、还可以做什么（按性价比排序）

1. 关掉桌面 GPU 占用后重测：余量从 507 MiB 涨到 700+ MiB，可以把窗口推到 114,688（池 116,480 token）。
2. 想要更快的生成，只能换硬件或换更小的模型：31 tok/s 是 5.52 GiB 权重 ÷ 288 GB/s 带宽的结果（理论上限 48.5 tok/s，当前达到 64%）。
3. GPU 解锁（nv-uefi-unlocker）只提 FP16/BF16/TF32 矩阵算力，也就是**预填充**那一段：按本机预填充已吃到 83% MMA 上限推算，解锁后约 1,600–1,900 tok/s，20k 题面首字从 22 s 降到 13–15 s；解码不变。当前阶段不需要。
4. 若要跑满 262,144 原生上下文，需要 16 GB 以上的卡；8 GB 档的可靠上限就是池大小（fast 32k / long 64k）。
## 十、第二版（2026-10-30）：解码 31.7 → 98 tok/s，MTP draft-4 才是正解

第一版用 `--spec mtp --draft-tokens 1` 试过投机，结果更慢（26.7–28.5），于是错误地得出「8G 档投机无收益」。原因不是投机没用，而是 **draft 深度选错**：draft 1 每轮只多赌 1 个 token，验证开销盖过收益；draft 4 是这台卡上的最优点。

### 10.1 draft 深度扫描（同一件权重、同一 corpus：counting 1,133 进 / 400 出；prose 300 出）

| 配置 | counting 预填充 | counting 解码 | MTP 接受率 | prose 解码 | prose 接受率 |
| --- | --- | --- | --- | --- | --- |
| 无投机（window 16384, pool 17,792） | 1,000.6 | 31.6 | — | 31.7 | — |
| `draft-tokens 2` | 1,018.6 | 76.6 | 97.4% | 44.9 | 35.8% |
| **`draft-tokens 4`（现默认）** | **965.2** | **99.8 / 98.3** | **81.3–82.5%** | **48.5 / 50.0** | 22.8–29.4% |
| `draft-tokens 6` | 959.3 | 102.0 | 67.9% | 42.6 | 18.8% |
| `draft-tokens 12`（竞品 toolkit 的 fast 档） | 946.4 | 67.6 | 37.4% | 26.0 | 8.8% |

结论：**draft 4 综合最好**。可预测文本（数字序列、模板化输出、代码补全）解码 **31.6 → 98–100 tok/s（3.1 倍）**；散文类（写说明文）**31.7 → 48–50 tok/s（1.5 倍）**。draft 12 在散文上比不开投机还慢（26.0），所以竞品那套 `draft-tokens 12` 不能照抄。

### 10.2 顺带否掉的几个方向

| 尝试 | 结果 |
| --- | --- |
| `--kv-dtype k8v4`（竞品用这个） | 计数文本解码 108.0（略高），但散文 41.6（更低），且每页 1.65 MB 使池从 10,304 掉到 4,736 token。**不换**：我们的 `rk2v4-e8` 每页只 0.88 MB，同样显存能装两倍上下文，散文还更快。 |
| `--fast-prefill-kernel` | 预填充 1,022 对 965，噪声级差别，保留无害。 |
| 开 CUDA Graph | 仍无变化。 |
| 窗口 16k / 32k / 64k（显式池固定时） | 显存占用与速度完全相同（runtime 780.3 MiB、free 205 MiB），窗口不是瓶颈，**池才是**。 |

### 10.3 现在开机就是快档（`scripts/serve.sh` 默认 PROFILE=fast）

```
PROFILE=fast  NINFER_KV_WINDOW=16384 --spec mtp --draft-tokens 4 --kv-capacity 32000 --kv-dtype rk2v4-e8 --host-kv-mib 8192
PROFILE=long  NINFER_KV_WINDOW=16384 无投机 --kv-capacity 64000 --kv-dtype rk2v4-e8 --host-kv-mib 8192
```

banner 对照：fast `capacity | KV 32,000 tokens, rk2v4-e8, explicit | pages 500/4,096 | runtime 780.3 MiB | free 205.0 MiB`，权重 5.94 GiB；long `KV 64,000 tokens ... pages 1,000/4,096 | runtime 1.11 GiB | free 273.0 MiB`，权重 5.52 GiB。热启都在 4 秒级。

## 十一、更正：capacity 那个数才是可靠上限（第一版把总页数当成了池）

banner 里的 `capacity | KV X tokens ... pages a/b`：**X 才是可依赖的题面上限**，`a/b` 只是「已用页 / 池总页」，第一版把 b×64 当成了池（1,558×64 = 99,712），实际 X 是 46,272。引擎自己的告警把判据写死了：

```
[warning] prompt exceeds the resident Device KV pool: prompt 63080 tokens (986 pages) > pool 10304 tokens (161 pages). ...
the MIDDLE of such a prompt has been measured to go missing with no error line, HTTP 200 and a plausible wrong answer
```

本机针测试（中段埋随机口令，问口令）：

| 配置 | 题面 token | 池 token | 结果 | 告警 |
| --- | --- | --- | --- | --- |
| fast 档 | 26,360 | 32,000 | 命中 `IN28K-3344` | 无 |
| long 档 | 56,504 | 64,000 | 命中 `LG60K-5522` | 无 |
| fast 档 + 小池 | 63,080 | 10,304 | **命中（运气）** | 有 `unverified` |
| fast 档 + 小池 | 113,002 | 10,304 | **答错**：「文档中未提及任何重要记录」 | 有 `unverified` |

两点必须记住：① 超池时**可能猜对也可能答错，猜对不代表安全**；② 告警行 30 秒才重复一次，**没有告警不等于安全**（文档原话）。要跑超长题面只有两条路：把池开大（受显存限制），或走作者的分片注入网关。

## 十二、和 sm120a-8gb-toolkit（RTX 5060 8GB）的对照

| 项 | 它（RTX 5060，448 GB/s） | 本机（RTX 4060 Ti，288 GB/s） |
| --- | --- | --- |
| 主打启动器 | `fast`：`--spec mtp --draft-tokens 12 --fast-prefill-kernel` | `fast`：`--spec mtp --draft-tokens 4` |
| 池 | 显式 `--kv-capacity 8192`、`k8v4` | 显式 `--kv-capacity 32000`、`rk2v4-e8` |
| 公开读数 | 预填充 482–670、解码 54–99、接受率 89.1%（draft 4） | 预填充 965–1,000、解码 98.3–99.8、接受率 81.3% |
| 同 corpus 对照 | 1000 进 1000 出 | counting 1,133 进 400 出，**解码反而更快** |

为什么它看起来快、实际并不快：① 它公开的 54–99 是开了投机的数字，我们第一版 31.7 是没开投机的，**两个数不同口径**；② 它用 `k8v4`，每页 1.65 MB，同样显存只装得下一半上下文，换来的是计数文本略快、散文更慢；③ 它的 196.8 tok/s 是构建机 4080 SUPER 的读数，不是 5060；④ 它自己记录同配置重复测量 54.7 vs 80.0（差 46%），单次读数不可信。本机现在这两档读数是在同一 corpus、同一脚本下跑出来的。

真正可搬运的两条：**draft 深度要扫（4 最优，不是 12）**、**池必须显式给**（`auto` 会按窗口推导，一不小心就掉到 10k 档）。
