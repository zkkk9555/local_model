# 把本地 27B 接进 DSH（2026-10-30 实测口径）

> 结论先说：配置已写好并验证到「请求形状完全兼容」这一步，**只差用户在 DSH 菜单里点一次「重启应用与宿主」**，模型就会出现在选择器里。

## 一、现在长什么样

| 项 | 值 | 说明 |
|---|---|---|
| 引擎 | http://127.0.0.1:8091/v1 | ninfer-serve-89.exe，模型 id = `local` |
| 网关 | http://127.0.0.1:8081/v1 | `tools/chat_gateway.py`，超池时自动裁历史/分段摘要 |
| DSH 里选的模型 | provider **Local** / model **local** | 名字就是 `local`，够短 |
| API Key | 随便填 | 已内置占位凭据 `LOCAL_LLM_KEY`，DSH 不会真的校验 |
| 上下文 | 36,000 token（DSH 声明） | 真实池 **40,000**；DSH 留 4,000 给系统提示 + 输出，避免每轮都撞超池警告 |
| 峰值显存 | **7,469 MiB / 8,188 MiB** | 余 719 MiB |
| 速度 | 计数类 **97–98 tok/s**，中文散文 ~45.7 tok/s；37K 提示 prefill 963 tok/s | 40k 池 + MTP draft4 + win8 + slots0 |

## 二、DSH 侧改了哪两个文件

1. `C:/Users/Administrator/.dsh/profiles/desktop/cordis.patch.yml`（备份：同目录 `cordis.patch.yml.bak-before-local`）
   在 `llm-pi-ai.config.providers` 里新增：
```yaml
      local:
        displayName: Local
        api: openai-completions
        baseURL: http://127.0.0.1:8081/v1
        apiKeyEnv: LOCAL_LLM_KEY
        models:
          - id: local
            name: local
            contextWindow: 36000
            maxTokens: 4096
            input:
              - text
```
2. `C:/Users/Administrator/.dsh/.credentials.yaml` 的 `refs:` 下新增 `LOCAL_LLM_KEY: local-any-key`（占位，任意字符）。

改的是 patch 层，不动 `cordis.yml`；设置页「模型」写的是同一份文件，所以 GUI 里改也会落在同一处。

## 三、怎么生效（用户操作，一步）

1. DSH 菜单 → **「重启应用与宿主」（Restart App and Host）**。只刷新页面不够：配置在宿主进程启动时读入。
2. 重启后新开一个会话，把模型切换到 **Local / local**。
3. 随便聊一句验证。首次回答前会有 1–3 秒预热（引擎已在跑，不用等 1–2 分钟加载）。

## 四、已验证的兼容性（不用再怀疑）

- `GET /v1/models` 走网关 200，返回 `id: local`。引擎对 model id 严格校验：发别的名字直接 404，网关转 502。
- DSH 形状的一次真实请求（`stream=true` + `stream_options.include_usage` + `tools` + `tool_choice:auto` + `parallel_tool_calls` + presence/frequency penalty）：
  **200 text/event-stream，4 个 SSE chunk，usage 完整（prompt 289 / completion 29），正确吐出 `run_bash` 工具调用**。
- 未知字段（`foo_unknown`、`max_completion_tokens`）容错，不 400。
- 前缀复用有效：同一前缀第二轮 `cached_tokens=277`。
- 复验命令：`curl -s http://127.0.0.1:8081/v1/models`、`python tmp/dsh_shape_test.py`（工作区里）。

## 五、三档口径与切换（都要先 taskkill 引擎，同一张卡只能一个实例）

| 档位 | 池 | 速度 | 峰值 | 适合 |
|---|---|---|---|---|
| `PROFILE=fast FORCE=1` | 16,000 | 98 tok/s | 7,141 | 只做短问答；DSH 系统提示会吃掉大半空间 |
| **`PROFILE=legacy FORCE=1 POOL=40000 HOSTKV=6144`（当前）** | **40,000** | **97–98 tok/s** | **7,469** | **推荐**：速度不掉，37K 提示零 unverified 警告 |
| `PROFILE=long FORCE=1` | 51,200 | ~32 tok/s | 7,353 | 要长文档/长代码，能忍慢 |

```bash
# 停旧引擎（网关一起停）
taskkill //F //IM ninfer-serve-89.exe; for pid in $(netstat -ano | grep "127.0.0.1:8081 " | awk '{print $5}' | sort -u); do taskkill //F //PID $pid; done
# 起新档（legacy = 40k 池，host KV 6 GB）
cd /c/Project/local_model && PROFILE=legacy FORCE=1 GW=1 PORT=8091 MODELID=local POOL=40000 HOSTKV=6144 bash scripts/serve2.sh
```
换档后**必须同步改 DSH 里的 `contextWindow`**（`C:/Users/Administrator/.dsh/profiles/desktop/cordis.patch.yml` 里 `local` 那段），再「重启应用与宿主」一次：
池 16,000 → `contextWindow: 16000`；池 32,000 → `32000`；**池 40,000 → `36000`（当前）**；池 51,200 → `46000`。写大了会超池，引擎会打 `unverified` 警告、答案不可信。

`FORCE=1` 的原因：作者闸门公式对 32k 池估 `7,672 MiB`、40k 池估 `7,772 MiB`，都超过红线 7,488；但实测峰值 7,357 / 7,469（公式对固定开销高估）。池的天花板实测：52,000 能起但 prefill 崩到 ~180 tok/s，56,000 起就拒启（`runtime reservation requires 1,092,297,216 bytes, but only 1,037,041,664 bytes available`），所以 **40,000 是本机稳态上限**。闸门脚本 `scripts/plan.py` 保留不动，只在起服时人工放行。

## 六、出问题怎么查

| 症状 | 查什么 |
|---|---|
| 模型选择器里没有 Local | 是不是只刷新了页面没重启宿主；`cordis.patch.yml` 的 YAML 缩进（用 `python -c "import yaml..."` 校验） |
| 报 MISSING_CREDENTIAL | `.credentials.yaml` 里 `LOCAL_LLM_KEY` 是否在 `refs:` 下 |
| 报 401 / 连不上 | `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8081/v1/models` 应为 200；不是就重启引擎 |
| 回答被截断 / 上下文超限 | `contextWindow` 写大了，按上表改成与池一致 |
| 回答明显胡说且日志有 `unverified` | 题面超池了：换 32k/51.2k 档，或让网关去做裁剪 |

日志：引擎 `logs/engine-legacy.log`，网关 `logs/gateway-8081.log`。
