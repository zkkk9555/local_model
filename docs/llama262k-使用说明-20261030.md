> 这条路线跟现役 NInfer **二选一**：8 GB 显存放不下两个（NInfer 峰值 7,459 MiB、llama 7,931 MiB / 8,188）。
> 切换：`bash scripts/switch.sh ninfer` 或 `bash scripts/switch.sh llama`，查状态 `bash scripts/switch.sh status`。


**显存线 93,696 cell（≈93.7k 位置）**，比作者参考机 RTX 2060 SUPER 的 58k 高 60%，原因两条：桌面在 AMD 核显上
（`display_active=Disabled`，独显开局 free 7,949 MiB）+ q3_0 KV。超过 93,696 的位置全部在 pinned 系统内存里。

## 三、必知的三个操作事实

1. **要 API key**：`Authorization: Bearer <key>`，key 在 `llama8g/bundle/artifacts/api_key.txt`（48 字节，已写进
   DSH 凭据 `LLAMA_API_KEY`）。不带 key 一律 401。
2. **模型 id = `bonsai-2-27b`**（`GET /v1/models` 报的 id 与 aliases 一致）。
3. **关思考要显式说**：launcher 默认 `effort=medium`，请求里带 `"reasoning_effort": "none"` 才能压掉思考
   （实测 `reasoning_n` 从 38 → 2，等价 NInfer 的 `--default-reasoning-effort none`）。

## 四、速度的真相：prefill 是 O(n²)

短上下文很快（decode 中位 56.7 tok/s、首字 0.195 s），但**首读长文档极慢**，因为每多一个位置，前面的 prefix 都要
再读一遍（显存线之外还要过 PCIe）：

| 首读长度 | 累计耗时 | 有效 prefill |
|---|---|---|
| 14,336 tok | 105.1 s | 136 tok/s |
| 25,162 tok | 334.8 s | 74.8 tok/s |
| 209,000 tok | 约 20,400 s ≈ **5.7 h**（拟合 `t ≈ 9.34e-7·n²`，与作者自己 60k/1,600 s 的数据自洽） | ~10 tok/s |

⇒ **262K 窗口不等于 262K 可用**：窗口够，首读时间不够。日常 30k 以内、或「一次性建好上下文后反复追问」才是它的用法。

## 五、DSH 里怎么用

`providers.llama`（已写进 `~/.dsh/profiles/desktop/cordis.patch.yml`）：
`baseURL http://127.0.0.1:8089/v1`、`apiKeyEnv LLAMA_API_KEY`、`streamIdleTimeoutMs 3600000`、
模型 `bonsai-2-27b`（contextWindow 262144、maxTokens 8192）。
改配置后**点一次菜单「重启应用与宿主」**才出现。

## 六、排错

| 症状 | 原因 / 处置 |
|---|---|
| 401 unauthorized | 没带 key，见 §3.1 |
| `note this llama-server predates the tiered-KV runtime` | 用错 build；当前 build 有 `--kv-vram-cells`，不该出现 |
| 启动即 OOM / 显存线掉到 4 万 | 有别的程序占卡（游戏、录制、浏览器硬解）；launcher 会按当时的 free VRAM 重算线 |
| 首读 209K 想等 | 约 5.7 h，客户端 timeout 要放到 25,000 s 以上 |
| 想要更快 | 只能回 NInfer（fresh 30K = 45.8 s），或改走分片 `tools/longdoc.py` |
