# 8G 跑 200K 上下文：本机实测结论 + 优化清单（2026-10-30）

> 结论先行：**200K 上下文在这台 RTX 4060 Ti 8G 上已经跑通了，不是理论。** 实测 209,154-token 单请求、8 个针（3%–92% 深度）全部命中，过程中显存峰值 7,469 MiB 一动不动。
> 之前我说「40K 是上下文上限」是错的——40,000 是**常驻池**，不是上下文。作者自己的原话也是 256K。

## 一、本机实测（唯一可信的数字）

| 项 | 读数 |
| --- | --- |
| 提示词 | **209,154 token**（296,021 字符，中文 ≈1.42 字符/token） |
| 设备池 | 40,000 token / 625 页（`--kv-capacity 40000 --kv-dtype rk2v4-e8`） |
| 超池程度 | 3,269 页 vs 625 页 ⇒ **5.2 倍超订** |
| 显存峰值 | **7,469 / 8,188 MiB**（整轮不动，与 37K 提示时一致） |
| 端到端耗时 | **378.6 s**（≈ 552 tok/s 有效 prefill；引擎 5s 窗口读数 537→358 tok/s，host 占比 68–84%） |
| 命中率 | **8/8**：深度 3% / 14% / 27% / 39% / 52% / 65% / 78% / 92% |
| 引擎警告 | `prompt exceeds the resident Device KV pool: prompt 209154 tokens (3269 pages) > pool 40000 tokens (625 pages)`（**这是设计内行为，不是错误**） |
| 换页证据 | `kvmem_score: SELECT n_blocks=1610 budget_blocks=512 sink_blocks=64 kept=512 runs=175 skip=1098 kept_range=[0,1609]`、`mask hidden: span=742 resident=617 hidden=125 mid_hidden=0`、`[ring] retrieve preferred n=128 restored=128` |

复现：`python tmp/probe200k.py`（直连 8091），日志 `logs/probe200k.log`。

## 二、之前错在哪：池 ≠ 逻辑上下文

| 概念 | 我们这台 | 说明 |
| --- | --- | --- |
| 逻辑上下文 `--max-context` | 262,144 | 记忆里允许放多少 token，几乎不吃显存 |
| 常驻池 `--kv-capacity` | 40,000（625 页） | 显存里同时驻留多少，决定显存占用与速度 |
| 主机池 `--host-kv-mib` | 6,144 MiB | 溢出页放内存，按 query 打分后搬回 |

引擎的环（KVMem ring）本身就是「权重在显存、上下文溢到内存、按内容相关性回取」。我把常驻池当成了上限，所以得出「8G 只能 40K」的错误结论。

## 四、速度账：200K 到底多快

| 场景 | 有效 prefill | 首字等待 | decode |
| --- | --- | --- | --- |
| 本机 37K 提示（池内） | 963 tok/s | ≈39 s | 35 tok/s（实测） |
| 本机 209K 提示（5.2×超池） | **552 tok/s** | **≈380 s（6.3 分钟）** | 待分档矩阵给出 |
| 4060 Laptop 8G 长档（社区） | ≈610 tok/s @短提示 | 78.7 s @48K | **20 tok/s** |
| 2060S 8G llama.cpp 路线（社区） | 冷读 245K 要 1,489 s | 分钟级 | 52.4 / 29.6 / 11.4 @4K/128K/245K |

注：超池 prefill 掉速**不是算力问题**，是换页与 prefill 抢 PCIe/内存带宽（社区 FirePKU 口径：默认约 36K KV 在显存，过线就开始显存⇄内存交换）。

## 五、优化清单（按优先级，可直接执行）

### P0 已改
1. **DSH 客户端超时 5 分钟 → 15 分钟**。改的是 `C:/Users/Administrator/.dsh/profiles/desktop/cordis.patch.yml` 里 local 提供方的 `streamIdleTimeoutMs: 900000`（pi-ai 默认 300000）。原因：200K prefill 要 380–400 s，5 分钟超时会让 DSH 中途放弃并重发，两份 200K prefill 叠加直接把引擎打崩。生效需点菜单「重启应用与宿主」。

### P1 待 A/B（不重启引擎也能排期）
2. **`--fast-prefill-kernel`**：引擎自带（`help-full.txt:37-40`，专为 int8/rk* KV 的加速 prefill 路径，会把 `--prefill-chunk` 向下取整到整 tile）。200K 的瓶颈就是 prefill，这是最可能拿到倍数收益的开关。
3. **`--host-kv-mib 6144 → 3328`**：Aurora 用 3,328 就撑起 262,144 逻辑窗（4,096 逻辑页 = 3,296 宿主页）。我们白占 2.8 GiB 内存；在 Windows 上 pinned host 分配会映射进 GPU 地址空间与显存抢，缩下来还能降「死亡谷」风险（当前余量仅 ~719 MiB，社区阈值 400 MiB）。
4. **MTP 档位用散文基线 A/B**：社区（FirePKU）说 8G 不建议开 MTP、draft=2 最优；我们 draft4+win8 跑出 97–98 tok/s（计数题）但散文只有 45.7。要拿散文基线比 draft4-win8 / draft2 / 关 MTP 三档。
5. **`--kv-dtype rk2v4-e8 → rk8v4`**：rk2v4-e8 的 K 只有 2 bit，社区报「前 10 轮正常、第 11 轮复读」。质量侧值得单独 A/B（显存代价 ×2，需要缩池）。

### P2 观察
6. `--max-context 262144 → 204800`：社区（FirePKU）建议 200K 就够，理由 >180K 易幻觉 + 主流 Agent 在 80% 处压缩。**我暂不改**：我们自己的 209K 实测是干净的，等中段/相似干扰矩阵出来再定。
7. 关掉浏览器/录屏再跑长上下文，实拿几百 MiB 余量。

## 六、第二套：Strata（可以装，和现役不冲突）

- **作者**：斯洛文尼亚独立开发者 **Niko1221**，MIT，★35,970，`github.com/Niko1221/Strata`。**不是沈三殊**——沈三殊名下那个 Strata 是 fork（★0），他做的是中文本地化适配（cyber-on-strata 等）与 ninfer-fusion-kvmem；Strata 官方 docs 把 ninfer 列为第三方「思路来源」。
- **装法**：Windows 一键安装 `Strata-0.2.8-windows-x64-setup.exe`（GitHub Releases），或 PowerShell `irm .../install.ps1 | iex` 后 `strata launch`；首启按显卡下载引擎。
- **能不能跑**：我们 31.1 GB 内存 + 8 GB 显存 = 39.2 GB 合计。
  | 档位 | 需要 RAM+VRAM | 判断 |
  | --- | --- | --- |
  | Qwen3.8-Flash-Next Q2_0 | 37.6 GB | 勉强可试（留 1.6 GB 给系统，风险高） |
  | Qwen3.8-Flash-Next IQ2_XS | 39.2 GB | 打平，不可行 |
  | Coder IQ1_M | ≈32 GB | 最稳 |
  | Qwen3.6-35B-A3B | 32–52 GB | 低档可试 |
- **磁盘**：Q2_0 级下载量级 30 GB 上下，D: 剩 240 GB、E: 剩 112 GB，够。
- **与现役的关系**：不同端口、不同模型目录，可来回切换；但 8 GB 显存**不能同时驻留**两套（现役 7,469 MiB + Strata 任意档都爆）。
- **下载规则**：HF/ModelScope 走代理 `http://127.0.0.1:7897` 直接下；夸克网盘链接我只推给你，由你下。
