## 0. 一页结论（直接给 8G/4060 Ti 的 7 条）

1. **「池大小」和「逻辑上下文」是两个独立旋钮，这是 8G 拿到 200K+ 的第一性原理。** 三条独立证据：wiseaser（3060 8G）用「池子只能开两万多」撑满 **256K 逻辑上下文**；亦辰仙（RTX5060 8G+32G）在 kvmem+PTQ1 下「最多能腾出 **40K 池**」，代价是核显驱动显示器、上下文缩到 64K；异步页流水作者给 200K 上下文的池甜点是 **42K~56K**。→ 本机 40000 池正好落在甜点带里，方向没错，**加池不是拿 200K 的路**。
2. **51200 池 prefill 崩到 180 不是「池不够」，是踩到了 KV 换出阈值 + 换页与 prefill 抢带宽。** FirePKU 在 FAQ 里点明：默认约 **36K 的 KV 放显存**，过了这个点就开始「显存 ⇄ 内存」交换，本就极限的卡会直接掉速/爆显存。本机 40000 池 ≈ 阈值刚过，51200 就是大幅越线。**正确做法是把「逻辑上下文」做长（`-c`/`--max-context` 保持 262144 甚至更小到 200K），把池留在 40K。**
3. **8G 档 prefill 已经被 NInfer 的「专卡编译 + 三元专用张量核」解决掉了**：B站 UP 坠落糖梨（10-12）拆解沈三叔移植版引擎，三元模型 prefill 从 llama.cpp 的 **≈54 tok/s 提到 356~439 tok/s**（字幕原文），裸解码 +7%，MTP 投机吞吐翻倍、接受率 ~60%。→ **本机 963 tok/s @37K 已是同类最优档，不必换引擎**；超过池后的 180 是换页问题，不是算力问题。
4. **8G 开 MTP 是官方明确不推荐的（但和你要的 97-98 tok/s 冲突，需要实测分档）**：FirePKU 置顶「**8G 显存不建议开启 MTP**，12G 才开」；DeepLogiX 实测 draft 档位：**draft=3 接受率崩到 0.269（38~45 tok/s）、draft=2 接受率 0.56（均速 47）、draft=1 接受率 0.6（40~45）** → **draft 选 2 最优**。本机 draft4/win8 跑出 97-98 tok/s 说明这代引擎的调度不一样，但**必须拿「散文 45.7 tok/s」当基线 A/B 一次 draft2 / draft4 / 关 MTP**。
5. **8G 最硬的两个坑都在「显存之外」**：①**host 内存不足会表现为「显存不够」**——Windows 下 `cudaMallocHost` 的 pinned 分配会映射进 GPU 地址空间与显存争抢，报 `cudaMallocHost failed to pin ... cudaErrorAlreadyMapped`（岁月平静的完整报错）；坏心眼的大米2 把内存从 20G 加到 32G，同参数就不再爆。②**显存余量 <400 MB 会进「死亡谷」**：GPU 满占用、功耗极低、显存几乎不动、像卡死，过一会自己爬出来（异步页流水作者实测阈值 400 MB，有时 250 MB 就中）。→ 本机峰值 7,469/8,188 MiB，**只剩 ~719 MiB，正好在死亡谷边缘**；关掉浏览器/录屏（kris_yuu 的 7.7G 里就含这两样）能实拿几百 MiB。
6. **200K 之上真正的敌人是幻觉与环带重算，不是速度**：FirePKU 建议 **`-c` 设 200K 而不是 256K**（在 36K 激活 KV 下超过 180K 容易幻觉/读错文件），理由是主流 Agent 工具在 80% 处压缩上下文，200K 会在 160K 触发压缩；**384K 这类大设置会被拆成约 100K 一个「环带」，跨环要重新 prefill**（禾雨生实测）。→ 你要的「200K 可用」，`--max-context` 取 **204800** 比 262144 更稳。
7. **超时坑会直接把 200K 打成「双份 prefill 崩机」**：FirePKU 实测 5060Ti prefill 仅 ~500 tok/s，200K 上下文要 ~400 秒（6-7 分钟），而 **DSH 默认 5 分钟没收到 token 就重发** → 两份 200K prefill → 服务器崩。→ **先用 10 分钟+ 的客户端超时，再谈 200K。**

## 3. 逐条抽取（只留和 8G / 200K / 参数有关的）

### 3.1 8G 档直接相关

**7. BV1KtHD6kEi7（kris_yuu，10-08，3689 播）《8G 显存本地部署 Bonsai-2-27B》**
- 8G 卡实测：显存占 **~7.7 G**（含录屏 + 浏览器；纯模型 <7G），**速度稳定 50 tok/s**，上下文支持 **26 万（256K）**。
- 方案：modelscope `prism-ml/Ternary-Bonsai-2-27B-gguf` + **kvmem-llama.cpp 分支预编译包**；8G 选小文件（Q1/PTQ1），视觉解码器用 Q8；启动脚本 txt→bat 写模型路径。
- 评论区作者反复强调：**kvmem 至少要留 2G 显存**；有人问「8G 开 96K 还不够」，作者回「需要开 8192 上下文时显存能余 2G」。
- **对本机**：50 tok/s 是 llama.cpp-kvmem 分支的 8G 水平；本机 ninfer 的 97-98（MTP 爆发）/45.7（散文）已经高于它 → **不要在 8G 上退回 llama.cpp 分支**。

**8. BV1kgpd6pEn5（坠落糖梨，10-12，2695 播）《8g显存 qwen3.8 终极方案 ninfer+kvmem+bonsai 介绍》** ← 技术含量最高的一条
- NInfer vs llama.cpp（同卡同模型）字幕原文：**「单纯裸解码快 7%……但真正的杀手锏是预填充快了 6~8 倍……投机解码直接翻倍」**；后文具体数：**预填充从 llama.cpp 的 ≈54 tok/s 飙到 356~439 tok/s**（三元模型）。
- 三个原因：①**专卡专编**——30/40/50 系各自单独编译 CUDA kernel（40 系走 sm_89），「每条指令都是最优的」；②**三元量化专用张量核**——llama.cpp 用通用路径，NInfer 为 ternary 写了 **m16n8k16** 张量核 kernel，一次 tile 内多个 token 共用一次权重读取，「搬运量不变，算力成倍提升」，把 MTP 验证轮**从负收益翻成正收益**；③**内置 MTP 投机解码**——把 Qwen3.8-27B 的「next-token 层」拼成 MTP 草稿头，每轮猜 2~4 个，**接受率约 60%**。
- **关键事实：原版 NInfer 不支持三元量化**（格式表只有 Q4/Q5/Q6/Q8/FP8/MVFP4），直接加载 Bonsai 会报 `unknown tensor format: ptq1_g128_fp16` 然后退出（和评论区 haopyh 的 4060Ti 报错**完全一致**）。要跑三元必须用「沈三叔」的移植版：新增 `PTQ2_0_G128` / `PTQ1_0_G128` 两种三元类型 + 无损打包器（把 Bonsai 里 **402 个三元矩阵**逐字节搬进 NInfer 制品格式，不反量化）+ Hadamard 旋转机折进 kernel + 两条快路径（单 token 走 warp-per-row，批量 T≥2 走 m16n8k16 张量核）。
- **换页策略不是 LRU**：「不是按时间丢最旧的页，而是用当前 query 去评估每一页的相关度，把最相关的留在 GPU」（字幕 ASR 作「GUARM 内容打分 / rain 模式」，应为 rewrite 模式 + query 条件化打分）。官方原话效果：**「让 8G 卡上 8K 的 KV 池也能撑住 256K 的逻辑上下文」**。
- KV 分页物理量：**GPU 只留一个热窗口（6K~16K token）**，超出的打分后换到内存，需要时取回；「被换出的历史取回来时会慢一拍，但不丢」。
- 模型结构事实（解释了为什么 27B 的 KV 这么小）：Qwen3.8-27B 是**混合注意力，64 层里 16 层标准全注意力 + 48 层 GDN 门控递推网络**（用递推状态代替 KV）→ **KV 缓存只有 16 层的量**。
- 量化质量：Bonsai 三元 = -1/0/+1，log2(3)≈1.585 bit/权重；**PPL 6.445 vs 全精度 6.82±0.54**（在误差带内）；20 题社区基准 **19/20 = 95%**，错题与全精度相同。
- 视觉塔用 graft 嫁接（官方视觉塔 282 MB bf16 逐字节搬进三元制品），**overlay 模式：平时住内存，发图时临时借 GPU，编码 50~75 ms 后归还**；大图缩到 26 token。
- **对本机**：这条把「8G 能跑 27B 且 prefill 不慢」的机制讲透了；同时说明 **KV 池 8K 就能撑 256K 逻辑上下文**——本机 40000 池在「靠内容打分」的新架构里其实是偏保守/偏大的，**未来换带 query 打分的引擎版本，池可以进一步缩到 16K~24K 换更多显存余量**。

**13. BV1z2Jb6AEpH（宝藏二哥AIA，10-17，4925 播）8G~16G GUI 一键包**
- **8G 显存可跑 5.95G 的 27B**；16G 卡实测占 15.xG。
- ⚠️ **版本坑**：「ninfer 0.18.1 预览版是给 20 系和 V100 的，别下错」，要按 30/40/50 系选对应包。

**16. BV1G6nf6kEhP（国际米兰肠胃，10-24，4093 播）8G+32G 极限档**
- 极端档（32G 内存 + 8G/6G 显存跑 125B 级 MoE / Qwen3.8-Flash）字幕原话：「windows 开机让它占用 **2.1 G**；模型方面**去掉视觉、上下文减到 100K、KV 改为 Q4、投机解码改为 2**，这样就可以跑起来了，不读盘」。

- 3080 20G 走 U 盘无损解锁算力：ComfyUI 120 s → 106 s（+13%），**prefill 没加快（甚至略降）** → 网上说的「解锁提速 prefill」不成立。

### 3.2 16G+ 对照（用来标定「8G 该退到哪」）

## 5. 专题 B：拿到 200K+ 上下文的具体做法（可直接抄的配置清单）

### B1. 先把「三层预算」对齐（FirePKU 0.18/0.19 语义）

```
逻辑上下文 (-c / --max-context)  = 内存里允许记住多少 token（可以 200K~256K）
Budget (--kvmem-budget)          = 显存里能同时「看到」多少 token 的 KV（8G 上 16K~40K）
Reserve (--kvmem-gen-reserve)    = 留给生成的显存（0.18 默认 16K → 0.19 默认 4K）
```
- 硬规则：**逻辑上下文 ≫ Budget 是正常态，不是错误**（mhemh 实测 238K 上下文远超 Budget 36864，开头暗号仍被完整召回、finish=stop 非截断）。
- 硬规则：**单轮输出不要超过 Reserve**（超过会出问题）→ plan 模式 + 分步执行 + 大文件分块写。

### B2. 池（Budget）开多大 —— 四条独立证据收敛到 40K 附近

| 证据 | 结论 |
|------|------|
| 异步页流水作者（BV1U7Jo6dEih） | 200K 上下文配 **42K~56K** 池；「40K~70K 都可以试」，56K 比较安全 |
| 亦辰仙（8G RTX5060） | 8G + PTQ1 的池上限就是 **40K**（再大要核显驱动显示器 + 砍上下文到 64K） |
| 小睿sorry（16G） | 262K 逻辑上下文只要 **16K Budget + 16K Reserve** 就够（不必贪大） |
| 宝藏二哥AIA（16G） | **200K 上下文 → Budget 36864**；256K 留给 5080/5090 |

→ **本机 40000 是对的；51200 崩 prefill 说明已经越过「KV 换出」的坎，往上加池只会更糟。** 若要拿更多逻辑上下文，正确杠杆是 **降 MTP / 降 Reserve / 换 kv 类型 / 换带内容打分的引擎**，不是加池。

### B3. KV 类型（显存不够的第一顺位）

- 作者标准答法：**「显存不够」先换 kv 类型** → `rk8v4` 或 `nvfp4`（本机现在用的是 `rk2v4-e8`，K 只有 2 bit）。
- 反向警告（FirePKU FAQ）：**K 千万别压太低**，太低会循环思考/循环输出；V 压到 Q5/Q4 尚可。→ **本机 `rk2v4-e8` 属于激进档，若遇到「第 11 轮复读」「循环思考」，第一个要怀疑它**（评论区里世界滴神/jtu45446 描述的症状一模一样）。
- 对照：3080 20G 的 27B 256K 用 **int8,int8**（BV1Gvnp6gEjp）；_iiiAi 的结论是 **int8 KV 在 16G 上极易 OOM，换 k8v4 就很少出现**。

### B4. MTP 与 draft 档位

- FirePKU 置顶：**8G 不建议开 MTP，12G 才开**（MTP 主要加速写代码场景）；开了要「适当加 budget 和 gen reserve」。
- DeepLogiX 实测：**draft=2 最优**（接受率 0.56 / 47 tok/s），draft=3 接受率崩到 0.269，draft=1 也还行（0.6 / 40~45）。
- MTP 在 tensor 并行下很耗显存，layer 并行好一些（FirePKU 0.19 说明）。

### B5. 注入与长任务侧（不靠调参的三件事）

1. **客户端超时 ≥10 分钟**（DSH 默认 5 分钟 → 双份 200K prefill → 崩）。
2. **分片注入**：单轮输出 ≤ Reserve；大文件分块写；用 plan 模式。
3. **避开环带**：超长 `-c`（如 384K）会被拆成约 100K 的「环带」，跨环要重新 prefill（禾雨生）。→ 本机逻辑上下文定 **204800** 最稳（还能触发 80% 处的自动压缩）。

## 6. 专题 C：评论区大佬经验与坑（按「会咬人」排序）

### C1. 显存/内存类（最容易误判）

- **Windows pinned host 分配会抢显存**（岁月平静，0.18 完整报错）：
  ```KVMEM_REWRITE purpose=reconstruction capture skipped: cudaMallocHost failed to pin 147 MiB of host memory (device has 1117 MiB of 16302 MiB free; on Windows a pinned host allocation is mapped into the GPU address space and competes with it): cudaErrorAlreadyMapped```
  他推测根因是「已提交内存」超过 31~32G。→ **本机 32G 内存 + `--host-kv-mib 6144`，要把「已提交内存」盯住**（关掉浏览器/其他大进程），否则表现为「显存不够」。
- **加内存治「爆显存」**（坏心眼的大米2，4070TiS 16G）：默认参数接 Codex 频繁 `cudaMallocHost failed to pin`，降到 **Budget=25984 / Reserve=12032** 才不报；**内存 20G→32G 后同参数不再爆**。
- **显存余量 <400 MB 进死亡谷**（异步页流水作者）；**kvmem 至少留 2G**（kris_yuu）。→ 本机只剩 719 MiB，属于「能跑但脆弱」，**关录屏/浏览器能实拿 300~800 MiB**。
- int8 KV 在 16G 上极易 OOM（_iiiAi），换 k8v4 明显缓解。

### C2. 长上下文质量类

- **>180K 易幻觉**（FirePKU）：超过 180K 后「读错文件、搞错项目目录」→ 所以 `-c` 建议 200K。
- **输出超 2.5 万 token 会被截断**（wiseaser，池两万多的 8G 配置）。
- **单轮输出超 Reserve 出问题**（FirePKU）→ 0.19 干脆把 Reserve 默认降到 4K。
- **8G 的输出循环**：「前 10 轮正常，第 11 轮重复第 10 轮内容夹杂 1-2 句新内容」（里世界滴神）；「易思考循环/工具调用循环/乱码」（jtu45446）。→ 与「K 压太低」+「池/Reserve 越线」强相关，**建议先用更保守的 kv 类型复测一次**。

### C3. 版本/兼容类

- **原版 NInfer 不支持三元**，报 `unknown tensor format: ptq1_g128_fp16`（haopyh，4060Ti）→ 必须用移植版（沈三叔）或已有的 kvmem+Bonsai 分支。
- **0.18.1 预览版是 20 系/V100 专用**，30/40/50 系别下错（宝藏二哥AIA）。
- **35B-A3B 开 MTP 会失败**：`KVEM_STARTUP_ERROR failed to create context; check --ctx-size, KV types, --flash-attn and available memory` / `GDN replay requires single-sequence CUDA Qwen 27B with MTP 1-5 and all recurrent layers on one GPU`（Angel念地）。
- **tensor vs layer 并行**（mhemh，双卡 5070Ti+TT10）：layer 13:7 **prefill 819→532（-35%）、decode 24.65→22.32（-9%）**；tensor 模式到 256K 约 400 tok/s prefill、18 tok/s 生成，**全面慢于 layer**。

### C4. 栈选择类

- **ninfer+kvmem 的短板是 prefill**（Goodend：agent 场景 prefill 1k→300 tok/s、decode 快）；**Strata 的 prefill 强**（flamety：FN Q4xs ≥1600、Q3s 2200）。→ 若未来要跑超长 prompt 的批量任务，Strata 值得单独测。
- **turbo4 KV 压缩**（有个大帅锅，buun_llama）：精度接近 Q8、体积仅 Q8 一半，16G + gsq iq3s 能有 **100K KV 常驻显存**；副作用是吐字变慢。
- A 卡有 ROCm 预编译：`kvmem-llama.cpp/releases/tag/rc3-rocm-beta`；丶DarkRain（9060XT 16G, Win11）**254K prefill 171.1 / decode 21.51 tok/s**。
- 32G 内存的 27B 档「q8 256K」已有实例（神奇萌叔）；strata iq3s 256K 生成 **160 tok/s**、kvmem+ninfer nvfp4 256K 约 **130**（16G+ 才有意义）。

## 7. 专题 D：为什么这一代 NInfer 在 8G 上有戏（唯一讲清机制的片子）

| 层 | llama.cpp 路线 | NInfer（含移植版）路线 | 收益 |
|----|----------------|------------------------|------|
| CUDA kernel | 一套通用代码跑所有卡 | **30/40/50 系各自编译**（40 系 sm_89） | 裸解码 +7% |
| 三元矩阵乘 | 通用路径 | 专用 **m16n8k16** 张量核，一次 tile 多 token 共用权重读取 | prefill 从 ~54 → **356~439 tok/s**；MTP 验证轮由负转正 |
| 投机解码 | 无内置 | 拼 Qwen3.8-27B 的 next-token 层成 MTP 头，猜 2~4 token | 接受率 ~60%，吞吐翻倍 |
| KV 管理 | 显存内线性增长 | 分页 + **query 条件化打分**换页（非 LRU）+ 热窗口 6K~16K | **8K 池撑 256K 逻辑上下文** |
| 视觉 | 全量入显存 | graft 嫁接 + **overlay**（平时在内存，编码 50~75 ms 借用后归还） | 8G 也能识图 |

→ 与本机现象自洽：本机 963 tok/s @37K 的 prefill 远高于 llama.cpp 分支的 8G 水平（kris_yuu 的 50 tok/s 是 decode），说明**引擎侧的专卡编译+张量核已经在起作用**；而 51200 池崩到 180 是**换页/预算**问题，与 kernel 无关。

## 8. 对本机 4060 Ti 8G 的可执行清单

| 优先级 | 动作 | 预期 | 验证方法 |
|--------|------|------|----------|
| **P0** | 客户端/DSH 超时调到 **≥10 分钟** | 避免 200K prefill 触发重发 → 双份 prefill 崩机 | 跑一次 >150K 提示，看服务端是否只收到一次 prefill |
| **P0** | 逻辑上下文 `--max-context` 从 262144 **降到 204800** | 避开 >180K 幻觉带；自动压缩在 164K 触发 | 长文档任务复测「读错文件」概率 |
| **P0** | 池保持 **40000**，不再尝试 51200/56000 | 40K 在 42-56K 甜点带下沿；再加只会挤显存 | prefill 应稳定在 900+ |
| **P1** | 拿「散文 45.7 tok/s / 37K prefill 963」作基线，**A/B 一次 MTP**：draft4-win8 vs draft2 vs 关 | draft=2 接受率最高（0.56）；8G 官方不建议开 MTP | 同一提示词跑 3 次，记接受率与 tok/s |
| **P1** | 试 `--kv-dtype rk8v4`（或 nvfp4）替换 `rk2v4-e8` | K 从 2bit 提到 8bit，换质量稳定；显存略增 | 复测「第 11 轮复读」是否消失；tok/s 变化 |
| **P1** | 关掉浏览器/录屏/其他 GPU 进程，把峰值从 7469 MiB 压到 ≤7,600 MiB 以下，**留 ≥400 MB** | 脱离「死亡谷」阈值 | 任务管理器看 GPU 专用内存与 GPU 引擎功耗（满载但功耗低=死亡谷） |
| **P2** | 单轮输出硬限 ≤ Reserve（16K）：plan 模式 + 分块写 + 分片注入 | 避开「超 Reserve 出问题」 | 长代码生成任务复测 |
| **P2** | 备选模型：`modelscope.cn/models/KVMem/Bonsai2-27B-T5-MTP-Q4-NInfer`（8G 峰值 ≈7G）+ **0.19.0-rc1** | 官方 8G 专用档，Q4+MTP | 存盘后与现用 PTQ1 做同题 A/B |
| **P3** | 关注 `Ninfer-KVMem-Async`（异步页流水）：深超池 74K/256K 仍 114 tok/s，但收益只在长任务 | 若将来跑长 Agent 任务是刚需再上 | 以「浅池打平、深池 2 倍」为预期 |
| **P3** | 8G 若想再上一档容量：试 **35B-A3B MoE 路线**（BV1LhJD6XEmH 一键包 / FirePKU 预告「8G 上 35B-A3B 可能比极限压缩 Bonsai 更好」） | MoE 激活参数少，KV 小 | 注意 MTP 会启动失败（已知报错） |

**不建议做的事**（本次扫描的负结论）：
- ❌ 加池到 51200/56000 换 200K —— 三条独立证据都说 40K 是 8G 的上限带，越线只掉 prefill。
- ❌ 换回 llama.cpp-kvmem 分支 —— 8G 上 decode 只有 ~50 tok/s，本机 ninfer 已 97-98（MTP）/45.7（散文）。
- ❌ 信「解锁 GPU 算力能提 prefill」—— BV1G6nf6gEjp 实测 prefill 没加快、甚至略降。
- ❌ 用 384K/512K 逻辑上下文 —— 会被拆环带重 prefill（每 ~100K 一次），且 512K 档 KV 进内存后 tok/s 腰斩到 13。
