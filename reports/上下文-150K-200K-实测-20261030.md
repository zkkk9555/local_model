# 150K–200K 可信上下文：实测与做法（2026-10-30）

> 机器：RTX 4060 Ti 8 GB（7,392 MiB 预算）+ Ryzen 7 7800X3D + 31 GB RAM，Windows 11 26100。
> 引擎：NInfer KVMem `ninfer-serve-89.exe`（801,324,544 B，Release engine-v0.11.0-kvmem-20261008）。
> 模型：`Ternary-Bonsai-2-27B-PTQ1_0`（27B 三元，5.96 GiB）+ rk2v4-e8 KV（0.84 MiB/页，64 token/页）。

## 一句话结论

- **单遍**（一次前向读完全部提示词）的可信上限 = 设备 KV 池 token 数 = **88,618 token（实测 8/8 命中）**；150K/200K 单遍**在 8 GB 卡上算术不可能**。
- **150K / 200K 的正解是分片注入**：每片 ≤26,000 token（远小于池）⇒ 每片都可信，再合成。
  - **150K：134.9 s / 159.5 s / 173.2 s，三次全部 8/8**
  - **200K：211.4 s / 211.7 s / 211.4 s / 231.2 s，四次全部 8/8**（后三次耗时抖动 < 0.4 s）
- 已做成常驻代理（8086）并接进 DSH：provider `ninfer-long`，模型 `…-shard150k` / `…-shard200k`。

## 1 为什么单遍 150K 不可能（三条独立证据）

| 证据 | 读数 |
| --- | --- |
| 实测池天花板 | 池 88,000 起服后剩 33 MiB；池 96,000 直接拒启：`requested Engine runtime reservation requires 1559880704 bytes, but only 1487929344 bytes are available` |
| 算术 | 150K = 2,344 页 × 0.84 MiB = **1,921 MiB KV** + 权重 6,103 MiB + runtime ≈1,000 MiB ≈ **9.0 GiB** > 8,188 MiB |
| `--kv-dtype` 全表 | `bf16 / int8 / fp8 / rk8v4 / rk4v4 / rk4v4-e8 / rk2v4-e8 / nvfp4 / k8v4` —— rk2v4-e8（0.84 MiB/页）已是最省档，**没有更便宜的** |

顺带排除：`--stage-layers` 只在多卡 `--devices` 下有效；`--disk-kv-*` 只给「被逐出的会话」做落盘，不能用于单请求注意力；`--wddm-evictable-budget` 要 `NINFER_D3D12_RESIDENCY=ON` 的构建，本件不支持。

## 2 超池到底会发生什么（为什么必须分片）

引擎只在**每个请求第一次**越过池时打一行 warning，然后照常 HTTP 200 给一个「看着像真的」错答案：

```
[warning] ninfer-serve: prompt exceeds the resident Device KV pool: prompt 202586 tokens (3166 pages) > pool 64000 tokens (1000 pages).
Part of the prompt is therefore not resident, and the MIDDLE of such a prompt has been measured to go missing with no error line,
HTTP 200 and a plausible wrong answer ... Treat every answer to this request as unverified.
```

实测命中率随 prompt/池 比值掉崖（8 针 fixture，temperature 0）：

| prompt / 池 | 命中 |
| --- | --- |
| 0.98× | **8/8** |
| 1.31× | 7/8 |
| 2.37× | 1/8 |
| 3.17× | **0/8**（还声称「文档里 0 个校验码」） |

⇒ 判据只有一条：**每片 prompt ≤ 池**。这也是 `tools/longdoc.py` 里 `--pool-tokens` 硬闸的由来（超池即退出码 3）。

## 3 分片注入怎么做的

1. 按行切，每片 ≤26,000 token（首片用保守换算 1.75 字节/token，拿到真实 `usage.prompt_tokens` 后按实测比例校正余下各片）；
2. 每片独立请求：「只把与本问题相关的原文逐字摘出来，没有就输出 NONE」；
3. 把所有摘录拼起来做一次合成作答（system 里放拒绝词，用户轮保持极简——用户轮里出现「没有才写未找到」这种尾巴，模型会直接吐「未找到」）；
4. 合成失败/空/只回「未找到」→ 兜底按摘录逐字汇总，**绝不静默换成猜的答案**。

## 4 把 200K 从 1/8 救回 8/8 的三个 bug（都记下来，别再踩）

- **fixture 只插了 1 个针**：`tmp/exp/doc-200k.txt` 是早期的单针版；8 针版要重新生成 `doc-200k8.txt`（本次已生成，5,344 行 / 244,121 字符 / 8 针）。
- **模型退化**：数字密集段里它会「把所有四位数字抄一遍」（1024 token 全是数字），把取证塞满导致合并不出答案 ⇒ 加 `ANSWER_RE` 硬过滤（只留 `[\u4e00-\u9fa5]{1,6}-\d{3,5}` 形态、去重保序）。
- **过滤太狠**：模型有时只抄数字（回 `7112` 而不是 `赭石野兔-7112`），被过滤成 NONE ⇒ 加「短答保留」兜底（≤200 字且含数字就保留），并在 `EXTRACT_SYS` 里补一句「名称-数字必须整条原样抄」。

## 5 交付件与用法

| 东西 | 位置 | 说明 |
| --- | --- | --- |
| 分片注入代理 | `tools/longctx_proxy.py`（300 行） | OpenAI 兼容，`/v1/chat/completions`、`/v1/models`；估 token ≤ 池 85% 原样直通，超过则分片 |
| 启停脚本 | `scripts/longctx.sh start\|stop\|status` | 默认 8086 端口，日志 `logs/longctx-8086.log` |
| 命令行工具 | `tools/longdoc.py` | 新增 `--answer-regex` / `--pool-tokens` / 短答保留 |
| DSH provider | `~/.dsh/profiles/desktop/cordis.patch.yml` 的 `ninfer-long` | 两条模型：150K / 200K |

**日常怎么用：**

```bash
bash scripts/switch.sh ninfer      # 日常 40K（MTP draft4，散文 41.5 tok/s / 计数 107 tok/s）
bash scripts/switch.sh long72      # 长文单遍 72K（无 MTP，散文 35.7-37.0 tok/s）
bash scripts/longctx.sh start      # 150K/200K：在 long72 之上再起分片代理（8086）
```

DSH 里就是切模型：`Bonsai 27B Ternary PTQ1 · 无MTP · rk2v4-e8 · 池72K · 分片注入 150K` / `… 200K`。
回答开头自带一行「（超池分片注入：原文约 N token > 引擎池 72000，已切成 M 片…）」——**不会假装是单次推理**。

代价（本机实测）：

| 需求 | 做法 | 耗时 | 可信度 |
| --- | --- | --- | --- |
| ≤72K | 单遍（long72） | 70K ≈ 96 s 首读 | 8/8 |
| 88K | 单遍（池 88,000，需临时起服） | 129.8 s | 8/8 |
| 150K | 分片 7–8 片 | 135–173 s | 8/8 ×3 |
| 200K | 分片 9–11 片 | 211–231 s | 8/8 ×4 |

> 分片总耗时 ≈ 片数 × 单片 prefill（25K ≈ 25 s）+ 一次合成（≈10 s），所以 200K 比 150K 慢的只是「多两片」。

## 6 llama.cpp 262K 那条路（对照组）

llama.cpp 分叉（bonsai bundle，build 10807）能真开 262,144 窗口：KV 前 ~93,696 cell 在显存、其余在 pinned RAM，`kv tiered: cells 0..93696 in VRAM, 93696..262144 in system RAM`。

- 短上下文快：decode 65.1 tok/s（MTP on）/ 56.7 tok/s（MTP off），ttft 0.195 s。
- **prefill 是 O(n²)**：25,041 token 用 334.8 s（74.8 tok/s），逐段拟合 `t(n)=c·n²/2`（c≈9.34e-7 s/(token·位置)）⇒ 209K 推算 3.2–6.5 h。
- 本轮补测：**30,073 token、VRAM cell 钉 16,384（45% 上下文在主机内存）⇒ 8/8 命中，prefill 32.5 s（926 tok/s）** ⇒ host-tail 注意力在 30K 上是**可信**的，且小窗口下 prefill 并不慢。
- 150K 单遍实测（CTX=155,648，走 sparse host-tail）：**151,873 token / 268.3 s / 8/8**，decode 12.6 tok/s —— 详见 §6.1。

### 6.1 150K 单遍（llama）

**本机读数（2026-10-30 13:32–13:37）**：`CTX=155,648`、cells 由 launcher 自动算（`VRAM line 76800, 69120 once sparse engages`、`sparse host-tail reads: 12288,64,1024`）、MTP 关；探针 `tools/llama_probe.py --doc tmp/exp/doc-150k8.txt`（8 针、集合同 150K fixture）：

| 项 | 读数 |
| --- | --- |
| prompt_tokens | **151,873** |
| wall | **268.3 s** |
| prefill | 260.5 s ⇒ **582.9 tok/s**（前段 910 tok/s → 130K 处降到 633 → 收尾 583，随 host-tail 比例增长而衰减） |
| decode | 7.6 s / 97 token ⇒ **12.6 tok/s** |
| 命中 | **8/8**（8 个校验码全对，答案就是 1..8 逐条列出） |

含义：

- **llama.cpp 是唯一能在单次请求里真读进 150K 的路**，且答案正确（8/8），不需要分片。
- 代价：首读 **268 s**（比 NInfer 分片代理 150K 的 135–173 s 还慢），decode 掉到 **12.6 tok/s**（host-tail 注意力每 token 都要读内存）。
- 同一进程内第二次问同一篇文档走前缀缓存，几乎不再付 prefill（前测 30K：474.8 s 冷 → 1.1 s 热），但 decode 仍是 12.6 档 ⇒ **适合「读一次、慢慢追问」，不适合交互式问答**。
- 与分片代理的分工：要**快**用分片（每片 ≤26K，decode 正常）；要**单遍真读**（例如需要模型自己通读全文做全局归纳、不许分片摘录）用 llama。

## 7 结论与建议

1. **要 150K–200K 且要快** → 用分片代理（8086 / DSH `ninfer-long`）：150K 约 2.5 分钟、200K 约 3.5 分钟，命中率与单遍同等可信，且**每片都有池内保证**。
2. **要单遍真读** → 只有 llama.cpp 262K 这条路：本机 151,873 token **268 s / 8/8**，但 decode 只有 12.6 tok/s；200K 级 prefill 会更慢（O(n²)），短问仍是最快的（decode 65 tok/s）。
3. **要快问快答** → NInfer 40K 档（MTP），decode 41.5 tok/s（散文）/ 107 tok/s（计数）。
4. 任何「超过池」的做法都必须显式（分片 / 检索 / 直连报错），**不允许让引擎自己丢中间页**——那就是静默错。
