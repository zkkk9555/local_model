## 0 一句话结论

**8G 上这套引擎的极限是：prefill ≈1,100 tok/s@8k / 1,000 tok/s@37k（首字 TTFT 7.15 s / 36.7 s），decode ≈107 tok/s（计数）或 41–43 tok/s（散文），池上限 40,000 token（52k 起得来但 prefill 崩到 ~180 tok/s，56k 直接拒启）。触发条件：prefill 上限由 A8/INT8 通路独占（关掉就 396 tok/s，2.77×）；decode 上限由宿主 CPU 单核（实测 host 92–95%）+ MTP 接受率（计数 87%、散文 15–17%）共同卡死；池上限由 `runtime reservation = 固定底座 817.6 MiB + 图 allowance ≤ 989 MiB 可用` 这条硬账卡死。**

新现役 = `PROFILE=max`（下表 MAX16 档）：对现役 ctx40 的净收益 = **8k prefill +1.6%、37k prefill +3.3%（TTFT −1.20 s）、decode +3.1%、散文 +4.0%**，代价 = 峰值 +152 MiB（7,307→7,459）与启动多 220 ms 建图。

## 2 硬账：runtime reservation = 固定底座 + graph allowance（本报告所有拒启的根因）

从拒启原文反解，**精确到字节**（`kv_capacity.cpp:182-190` 打印的是 `curve.reservation_bytes(pages)`）：

| 臂 | allowance | 需要的 reservation | 减固定底座 857,289,216 B（817.6 MiB） |
|---|---|---|---|
| G-512 | 512 MiB | 1,394,160,128 B | 536,870,912 B = **正好 512 MiB** |
| G-256 | 256 MiB | 1,125,724,672 B | 268,435,456 B = **正好 256 MiB** |
| 作者 8g-fast 原样（未指定） | 自动 | 1,473,604,096 B | 616,314,880 B ≈ 588 MiB（draft1+win8 自动值） |
| X1（task-6 记录） | 自动 | 1,322,664,448 B | 465,375,232 B ≈ 444 MiB（draft4+ngram15 自动值） |

可用预算（weights 装完之后的实测空闲，逐次略抖）：**1,037,041,664 B = 989.0 MiB**（三次测得 984.6/989.0/990.6 ⇒ 抖动 ±3 MiB）。
⇒ **allowance 上限 ≈ 171 MiB**；自动值 444–588 MiB 全部超出，这就是「MTP + CUDA Graph 在 8G 上必然拒启」的真正机理，与池大小、draft 数、host-kv 无关（task-6 已用三家失败值 1.32/1.38/1.47 GiB 证明过）。

源码对应：`src/models/qwen3_5/program/planning/startup.cpp:1437-1444`（显式 allowance 整体替换自动值，并计入 `device_reservation_bytes = persistent + workspace + graph_allowance`）。

⇒ **MTP(draft4, ngram 15) 时 CUDA Graph 的真实驱动态用量 = 106.0 MiB**（引擎自己量的），给 64/32 属于记账超支（真跑不崩，但不可取）。

## 4 P1：prefill 内核 —— 三个开关两个空转、一个断崖

| 臂 | 关键参数 | 8k prefill | 24k prefill | 判定 |
|---|---|---|---|---|
| （底座） | ctx40 原样 | 1,091.2 | ~1,026（多臂收敛值） | — |
| FK | `--fast-prefill-kernel` | 1,098.0 | 1,028.6 | 噪声内（+0.6%） |
| CB | `--prefill-cublas` | 1,092.5 | 1,026.1 | **空转**（本制品无 cuBLAS 路由） |
| FKCB | 两个一起 | 1,093.0 | 1,025.1 | 空转 |
| CB-NP | + `--no-prefill-cublas-projections` | 1,092.3 | 1,025.4 | 空转 |
| **NOA8** | `--no-prefill-a8`（强制 A16） | **396.5**（TTFT 19,997 ms） | **386.0**（TTFT 61,752 ms） | **断崖 −63.7%** |
| FK-NOA8 | 再叠 fast kernel | 396.2 | 385.7 | 同上 |

**A8 会计（供 gpu-unlock 判据）**：A8/INT8 通路占 prefill 时间的 **63.6%**（1 − 396.5/1,091.2 = 0.6367）；关掉后剩余 A16 段在解锁后的最大提速按 1.624× 计，prefill 上限 = 1/(0.636 + 0.364/1.624) = **1.163×（+16.3%）**，即 8k ≈1,269 tok/s、37k ≈1,127 tok/s、TTFT 36.7→~33.5 s。**这是天花板，不是 +62%。**
⇒ 结论：`--fast-prefill-kernel` 与 `--prefill-cublas` 在本制品上不必开（它们默认也没开，收益在别的制品上）；`--no-prefill-a8` **永远不要用**。

## 6 env 杠杆：四条全部落在噪声内（含 lead 点的 B/D）

| 臂 | env / 参数 | 8k prefill | 24k prefill | 判定 |
|---|---|---|---|---|
| （底座） | — | 1,091.2 | ~1,026 | — |
| NR | `NINFER_KV_PREFILL_NO_RESTORE=1` | 1,097.1 | 1,029.4 | **池 ≤40k 时 0 收益** |
| EVSH | `NINFER_KV_EVIDENCE_SHARE=20` | 1,095.6 | 1,026.0 | 0 收益 |
| SB8 | `NINFER_TERNARY_KVMEM_SCORE_BUDGET=8192` | 1,087.9 | 1,025.0 | 生效但 0 收益 |
| W8K | `NINFER_KV_WINDOW=8192` | 1,091.2 | 1,023.5 | 0 收益 |

- **B（NO_RESTORE）为什么不灵**：日志确有 `[ninfer] ring retrieve: which=text preferred=128 restored=128`，即每 chunk 恢复 128 个 evidence 页（rk2v4-e8 ≈0.84 MiB/页）；24k 提示约 23 个 chunk ⇒ 总 H2D ≈2.4 GB ≈0.15 s，占 TTFT <1%。上游注释里「250K 预填里 280 s 是这段 H2D」（`src/models/qwen3_5/program/storage/context.cpp:2598-2605`）只在超长上下文成立——我们池 40k，>40k 的请求本来就 `unverified`。**⇒ 池 ≤40k 时这条可以跳过。**
- **D（SCORE_BUDGET）确实被读**：`kvmem_score: SELECT ... budget_blocks=512` → 设 8192 后变 `budget_blocks=128`（`kvmem_score.h:485`，`kvmem_window_plan.h:269,326`），但它只改**块选择预算**，不改 **evidence 页数**：`[ring] budgets: ... evidence=128` 三臂完全一致。**evidence 页数 = `NINFER_KV_RETRIEVE`(8192) ÷ 64 = 128 页**，这是给作者报 bug 的关键补充。
- 顺带否掉：`--fast-prefill-kernel` 不会改变 chunk 之外的任何东西；`NINFER_KV_WINDOW` 8k/16k 对 prefill 无差别（16k 是现役值，保留）。

### 为什么选它而不选 ctx40
1. **decode +3.1%**（104.1→107.3）：CUDA Graph 首次在 8G 上与本引擎的 MTP 共存（靠 `--cuda-graph-allowance-mib 16` + `--ngram-draft-tokens 0`，真实图用量 ≤16 MiB，零 WARN）。
2. **37k prefill +3.3%、TTFT −1.20 s**（37.93→36.72 s）：`--prefill-chunk 1536`（818→1536 之间最大的「整 attention wave」且账目还装得下）。
3. **散文 +4.0%**（39.9→41.5）：与 decode 同源，接受率不变（计数 87%，散文 15–17%）。
4. **峰值只 +152 MiB**，整卡仍余 729 MiB；且 `--ngram-draft-tokens 0` 自己又省回 118 MiB 图显存 + 24 MiB workspace。
5. 代价：启动多 220 ms 建图（不是 970 ms——那是有 ngram 的那组）；`free` 从 167 降到 39 MiB（记账余量变薄，实测 3/3 轮稳定起服）。

## 9 备选档 FINAL：要 `allowance 128` 的安全余量时（chunk 必须退回 1024）

**这是硬取舍，不是偏好**：chunk 1536 把底座抬到 959.8 MiB，allowance 给 128 就是 1,087.8 MiB > 989.0 可用 ⇒ **必然拒启**。所以 allowance=128 只能配 chunk 1024。

| 臂 | 参数 | 8k prefill | 计数 decode | runtime / free | 峰值 |

| FINAL | chunk 1024 + allowance 128 + ngram 0 | 1,099.4 | 107.9 | 921.4 / 179.0 | 7,291 |

取舍：FINAL 比 MAX16 少 **1.6%（8k）/ 3.3%（37k）prefill**、decode 持平，换来 free 179 MiB（记账余量厚 140 MiB）与「allowance 128 ≥ 实测 106 MiB」的通用余量（对**将来**把 ngram 打开的情形安全）。**只要 ngram 保持 0，MAX16 的 16 MiB 就是实测上限（零 WARN ×5 次启动），所以我推荐 MAX16。** 两者都已在测，切换只需 `PROFILE=ctx40 PROFILE=... ` 换一个 profile。

## 10 未验 / 风险

- 【未验】MTP 接受率对「不同的真实业务题面」的敏感性：本报告只有两种题面（计数 87%、散文 15–17%）。散文接受率低是 decode 只有 41 tok/s 的直接原因，但没做第三种题面。
- 【未验】`--cuda-graph-allowance-mib 16` 在**长输出/多轮并发**下会不会因图实例增长而超支：只跑了单请求 max_tokens ≤400（`--max-concurrency 1` 固定），measured 106 MiB 是 ngram=15 时的值，ngram=0 时实测 ≤16 MiB 但只有 5 次启动证据。
- 【未验】超池（prompt > 40,000 token）行为未在本轮重测；task-6 已知它打 `Treat every answer to this request as unverified`。MAX 档把 chunk 提到 1536 后 prefill 更快，但超池警告语义未变。
- 【未验】`--fast-prefill-kernel` 在 chunk 1536 下是否有额外收益（本轮只在 1024 下测过，结果噪声内）。
- 【已验·负控】`--prefill-cublas` 在本制品上无效；`--no-prefill-a8` 是 2.77× 慢的断崖；chunk ≥2048 在池 40k 下拒启；`--max-context` 降档不减少 reservation。
- 【口径】所有读数只对「RTX 4060 Ti 8GB + 上述制品 + 上述 env + 2026-10-30 的 exe」成立；换卡/换制品按作者规矩必须重测。
