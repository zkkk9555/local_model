3. **两类复读都抓得到**：逐字（「哈哈哈哈」×6，480 字符处）与整段（60 字符块在 480 字符窗口里覆盖率 1.0，484 字符处）。触发后客户端收到 finish_reason=length + 一段中文提示，网关主动断上游，引擎侧记 **HTTP 499 client disconnected**。

## 1 为什么做在网关，不做在引擎

| 位置 | 能不能做 | 证据 |
|---|---|---|
| 现役 NInfer 引擎 | 不能 | ./engine/ninfer-serve-89.exe --help 共 126 个开关，grep -ciE 'loop|repeat' 命中 **0**；也没有任何「重复即停」语义。另：task-17 的 28 臂证明现役是 q36 专用 build，serve 模式有更窄的参数白名单（--kv-resident 20480 / --kv k8v4 / --expert-cache 512 / --kv-grow / --memory-limit-mib 全被回 strata-q36: ignoring ... (not an option of this engine)） |
| DSH 客户端 | 不能 | 只收到字节流，拿不到累计文本与历史窗口，也无法在 SSE 事件边界上动手 |
| 8081 网关 | **能，且只需它** | 它同时掌握「完整 SSE 事件」与「累计生成文本」：这轮只加了 1 个类 + 1 个分支，fit_request / L0–L3 压缩链路一行没动 |

对照：Strata 把同类功能做在引擎里（reasoning_loop_recovery / repeat_stop_tokens，见 §9）。我们这条链路上引擎不提供，只能在网关补 —— 这也解释了为什么护栏必须「知道自己在哪一层」，提示文本里要明说「不是引擎报错」。

## 2 机制

### 2.1 干净事件边界（全部设计的前提）

- _event_boundary(buf)（chat_gateway.py:553）同时认 \n\n 与 \r\n\r\n，返回**首个完整事件的末尾下标**，半包返回 -1。
- _event_text(event)（568）只解 data: 行，取 choices[].delta.content 与 reasoning_content（思考内容也计入：跑飞时两者都会跑飞）。
- 转发顺序：**先把整条事件原样 write 给客户端，再喂给判定**（_relay_stream_guarded，788）。所以判定永远发生在事件之间，客户端看到的 SSE 永远是完整事件；触发时缓冲区里未闭合的那半个事件直接丢弃并关连接，不会以截断 JSON 的形式发出去。

### 2.2 判定节奏

- LoopGuard.feed(delta)（606）累积文本；每跨过 check_every（默认 480 字符）调一次 check()（635）。
- check() 先逐字、后整段：逐字便宜（只扫尾部），整段贵（扫窗口），顺序决定了常见情形（模型卡死在几个字上）走快路。

### 2.3 逐字复读 _check_verbatim（641）

- 从尾部依次试 period = 2..24：把尾部按 period 切成 repeat_times（默认 6）份，要求**完全相等**、总跨度 ≥ min_unit_chars（24）、unit 不是纯空白。
- 另有一条兜底：同一字符连跑 ≥ run_chars（默认 96）。
- 为什么要有单位上限 24：中文里「的的的的」这类语法重复很短，24 字符上限让它必须重复到 6 次才算「卡死」，避免把正常强调判成复读。

### 2.4 整段复读 _check_passage（664）+ _scan_units（618）

- 边喂边对每个**新出现的** 60 字符块做 stride-1 计数（self.units_seen，键是块文本）：stride-1 而不是 stride-60，使「段落长度不是 60 的整数倍」也能被切到重叠块（实测 66 字符段落 ×12 命中，selftest coverage 0.364、线上 1.0）。
- 判一次的条件：已生成 ≥ 4×unit（240）字符；窗口 = min(window, 已生成长度)，默认 window 2000；把窗口按 60 字符切块，统计「出现 ≥ repeat_count(3) 次」的块占窗口的比例，≥ coverage(0.25) 即判整段复读。
- 表体积有上界：超过 history + window + 4×unit 的两倍就按最近窗口重建，长跑不会无限涨内存（history 默认 30000 字符）。

### 2.5 触发动作 _emit_guard_stop（768）

1. 发一个提示 chunk：delta.content = 中文提示，**带 chatgw_loop_guard 字段**（客户端可据此区分「护栏停了」和「模型自己停了」）；
2. 发 delta={} + finish_reason="length" 的收尾 chunk（同样带该字段）；
3. 发 data: [DONE]，flush，然后 response.close() 断上游 → 引擎记 **HTTP 499 client disconnected**；self.close_connection = True；
4. stdout 打一行：loop guard tripped kind=<verbatim|passage> at_chars=<位置> generated_chars=<总长> -> finish_reason=length, upstream closed。

### 2.6 非流式 guard_nonstream_payload（705）

整包到达后才判：命中则把 finish_reason 改成 length、在 content 末尾追加同一段提示、加上 chatgw_loop_guard 字段。算力已经花完（非流式没有中途止损的机会），这一支只保证**调用方拿到明确信号**，不保证省电。

## 3 参数与阈值依据

口径说明：网关只看得到文本，看不到 token 计数，所以**全部按字符计**（中文 1 字 ≈ 1 token，英文约 4 字符 ≈ 1 token）。这是与 Strata 内建功能最本质的差别，也是误判率要重新标定的原因。

| 参数 | 默认 | 作用 |
|---|---|---|
| --loop-guard | 关 | 总开关；不加就等于没有这段代码 |
| --loop-check-every | 480 | 每生成多少个字符判一次（判定粒度） |
| --loop-window | 2000 | 整段判定的观察窗口（字符） |
| --loop-coverage | 0.25 | 窗口里「重复块」占比到多少判整段复读 |
| --loop-repeat-count | 3 | 一个块出现几次算「重复块」 |
| --loop-passage-len | 60 | 块长度（字符），≈ 一句半中文 |
| --loop-history | 30000 | 块计数表保留的历史（字符），超出按最近窗口重建 |
| --loop-run-chars | 96 | 同一字符连跑多少判死循环（逐字兜底） |
| --loop-run-unit-max | 24 | 逐字判定允许的最大重复单位长度 |
| --loop-repeat-times | 6 | 逐字判定要求重复次数 |
| --loop-min-unit-chars | 24 | 逐字判定的最小跨度（太短的重复不算） |

阈值依据：对照 Strata 文档里引擎内建实现的量级（docs v028-DETAILS.md:471-472 / DETAILS.md:471-472：reasoning_loop_recovery「每 512 output tokens 检查一次」、repeat_stop_tokens 默认 256）。我们把它换成字符口径后取同一量级：判定粒度 480（≈512 token 的中文口径）、窗口 2000、占比 0.25、出现 3 次、段落 60 字符、历史 30000。差别是**我们多了一条逐字判定**（引擎那边靠 repeat_stop_tokens 只看「同一 token 连跑」，抓不到「'哈哈哈哈' 这种 4 字符单元连跑」）。

调参建议：

- 想更早起跳：--loop-check-every 240（判定更勤，CPU 略增，实测网关 CPU 开销可忽略）；
- 长文有误判（例如刻意排比的散文）：--loop-passage-len 90~120，或 --loop-coverage 0.35；
- 结构化输出（表格/重复模板代码）偶尔误判：--loop-repeat-count 4 + --loop-coverage 0.35；
- 只要「死循环」不要「整段复制」：--loop-coverage 1.01（整段判定等价关闭，逐字判定仍有效）。

## 4 自测：--selftest

四条假 SSE 流（正常短文 / 逐字复读 / 整段复读 / 长文本无复读）+ 四条既有的 fit_request 用例，一条命令跑完，PASS/FAIL 决定退出码。原文（logs/loopguard-selftest.log，SELFTEST PASS，exit 0）：

```
[chatgw] selftest 1 L0 pass: level=L0 est=1002 -> True
[chatgw] selftest 2 L1 trim: level=L1 dropped=23 est_after=12206 msgs=42->19 -> True
[chatgw] L2s fallback=l2 (not applicable or a map call failed)
[chatgw] selftest 3 L2 compress: level=L2 kept=1 dropped=0 est_after=10820 -> True
[chatgw] selftest 4 L2s: level=L2s segments=5 calls=5 est_after=59 -> True
[chatgw] selftest loop 正常短文: want=None got=None chars=3000 -> True
[chatgw] selftest loop 逐字复读: want=verbatim got=verbatim chars=480 unit='1,2,3' x6 -> True
[chatgw] selftest loop 整段复读: want=passage got=passage chars=3168 coverage=0.364 -> True
[chatgw] selftest loop 长文本无复读: want=None got=None chars=6000 -> True
SELFTEST PASS
```

四个用例怎么造：

| 用例 | 造法 | 期望 |
|---|---|---|
| 正常短文 | _varied_text(3000)（伪随机但确定的中文长文） | None（不拦） |
| 逐字复读 | 「1,2,3」×6 结尾，共 480 字符 | verbatim |
| 整段复读 | _varied_text(2400) + 66 字符段落 ×12，共 3168 字符 | passage，coverage 0.364 |
| 长文本无复读 | _varied_text(6000) | None（不拦） |

为什么按 7 字节切片：_simulate_guard(events, read_size=7) 把假 SSE 流切成 7 字节的碎片再拼回事件，等价于真实网关里 response.read(4096) 把一条事件拦腰截断的情形 —— 事件边界逻辑（_event_boundary）必须在这种碎片下仍然只吐完整事件。**这是本功能最容易写错的地方，所以单独用碎片化通道测**。

顺带修掉一个既有的假绿：selftest 2（L1 trim）原本就返回 False —— 它断言 "tools" in fitted2，但实现是 fit_request 把 tools 从 body 里摘掉、暂存到 decision["trimmed_tools"]，到 payload 组装处（chat_gateway.py:904-905）再重挂。断言改成 bool(decision2.get("trimmed_tools"))，是**断言对齐实现**而不是放宽标准；L1 的实际行为（trim 掉 23 条消息、est 12206、msgs 42→19、tools 仍会被发出）完全没变。

## 8 已知局限（按重要性排）

1. **用户明确要求重复时会被截断**：「请把这句话重复 400 次」这类用法是护栏眼里的逐字复读。默认关闭就是为它让路；开了护栏就别再发这种提示。
2. **只抓字面复读，抓不到语义漂移**：模型换个说法反复表达同一件事、或逻辑空转（每句都不同但信息量为零），护栏看不见 —— 那需要 embedding/相似度，网关这层不做。
3. **判定有粒度**：最坏情况是超阈值后才在下一个 480 字符检查点被叫停，即多生成约 480 字符（实测 0.1–0.5 s 的生成量）。想更早发现就调小 --loop-check-every，代价是 CPU。
4. **短文本不判**：整段判定要求已生成 ≥240 字符，逐字判定要求重复跨度 ≥24 字符 ⇒ 很短的死循环（如 3 个字反复 2 次）不会被拦。
5. **非流式不能中途止损**：整包到达才判，算力已经花完，只保证调用方拿到明确信号（§2.6）。长跑 agent 请一律用流式。
6. **思考内容与正文合并计数**：长思考里正常的「回顾上文」如果有整段复述，可能被整段判定命中。出现过就调 --loop-passage-len / --loop-coverage（§3 调参建议）。
7. **只能 stop，不能 recover**：Strata 内建有 recover（重启一次继续答），我们只断流并给出提示，恢复由调用方决定。
8. **不处理 tool_call 流内部的重复**：护栏只看 delta.content / reasoning_content 文本；工具调用参数里的死循环（比如同一个字段写一万遍）不在此列。

## 9 与 Strata 内建能力的对照

| 维度 | Strata 引擎内建 | 本网关护栏 |
|---|---|---|
| 开关 | reasoning_loop_recovery（默认 off）、repeat_stop_tokens（默认 256） | --loop-guard（默认关）+ 11 个 --loop-* 阈值 |
| 判定粒度 | 每 512 output tokens 检查一次 | 每 480 **字符**检查一次 |
| 抓什么 | reasoning 里「整段重复」；repeat_stop_tokens 抓「同一 token 连跑」 | 逐字复读（短单元连跑）+ 整段复读（窗口覆盖率） |
| 动作 | stop（结束）/ recover（重启一次继续） | stop（finish_reason=length + 断上游 499） |
| 客户端可辨识 | 无专用字段（只能看 finish_reason） | chatgw_loop_guard 字段 + 中文提示 |
| 官方自述的坑 | 「可能把重复的有用代码当成 loop，测的时候要同时看答案质量」（#728） | 同类风险，用「默认关闭 + 提示文本」缓解 |
| 出处 | tmp/strata-docs/DETAILS.md:471-472（同 v028-DETAILS.md:471-472） | 本报告 §2–§3 |

结论：两边不是替代关系。Strata 那条在引擎里，换了引擎才有；我们这条在网关上，换引擎、换上游模型都仍然生效（只要走 8081 兼容口）。**如果将来 Strata 成为主力，建议两边都开**：引擎侧管 reasoning 循环，网关侧管正文与跨引擎的统一兜底。

## 10 附录：怎么认出「引擎是被外部 taskkill 掉的」

本轮实测中途遇到一次（09:28:24），判据如下，按可靠度排序：

1. **日志被切断，不是结束**：正常退出会有收尾行（统计/关闭），本例最后 1594 行全是周期性采样行 [ring] budgets: protect=0 skeleton=0, evidence=128, recent=0, free=493 (pool 625) backend_pages=4 ...，最后一条仍是采样中间态。
2. **无异常行**：grep -cE 'panic|ERROR|FATAL|shutdown' logs/restore-8091.log → **0**。真崩溃会有 panic 栈或 ERROR，不会干干净净。
3. **唯一「悬空」的是一条请求的开始行**：2026-10-30 09:28:24.859 INFO req#19 started | openai-chat stream | 1 message | max output 1,200 —— 之后既没有 done 也没有 cancelled，文件就结束了。请求开始后进程被整体带走，才会留下这种「有始无终」的配对。
4. **客户端侧形状**：HTTP 200 已建立、流在 84 个 chunk / 4.2 s 处被腰斩，报 [WinError 10054] 远程主机强迫关闭了一个现有的连接；随后的连接一律 10061 拒绝。
5. **旁证**：tasklist 里 ninfer-serve-89.exe 消失、8091/8081 同时 000、nvidia-smi 掉到 0 MiB（几秒后出现一次 4,165 MiB 尖峰，是另一个实验在起服）。

反例对照：如果是引擎自己崩，会看到 panic/栈 + 请求以 5xx 或 resets 结束；如果是 OOM，日志会有 cudaErrorMemoryAllocation 或 reservation 行。本例三者皆无 ⇒ **外部 taskkill /F**。本次是 lead 的测试窗口占用所致，已确认与护栏、与网关无关（护栏只在网关进程内做字符串判定，从不杀上游进程，最多关掉自己那条连接）。

同一次事故对本文档的影响：§5.4 的 run / para 两例没能在重启后的实例上跑完；其余结论全部基于已完成的实测。
