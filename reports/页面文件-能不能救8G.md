# 页面文件能不能救 8G —— Windows 页面文件 / 虚拟内存在这类引擎上到底兜底什么

> 侦察任务书：「用户主张：把虚拟内存（页面文件）调大就能跑更大的模型。要给严格答案。」
> **结论先行：页面文件一个字节的显存都补不了；它能补的只有"匿名提交内存装不下"这一种失败，代价是把"起不来"换成"起来了但每 token 读盘"。**

- 机器：RTX 4060 Ti 8 GB（nvidia-smi 报 **8188 MiB**，PCIe **max gen4 ×8**）、Ryzen 7 7800X3D、**33,409,253,376 B = 31.1 GiB** DDR5、Win11、页面文件 `C:/pagefile.sys` **已分配 23,552 MiB**、`AutomaticManagedPagefile=True`、两块盘都是 **NVMe SSD**。
- 被测引擎：Strata **0.1.54-windows-x86_64-cuda-cuda13**（`C:/Project/local_model/strata/components/engine/0.1.54-windows-x86_64-cuda-cuda13/strata.exe`）。
- 实测缺口（引自本仓 `reports/Strata-8G实测-Qwen36起不来.md`）：2K 上下文时 **1159 MiB needed / 917 MiB free，差 242 MiB**；`--expert-slots 1` 一臂 **差 418 MiB**。
- 本文所有网络证据均经代理 `http://127.0.0.1:7897` 取回（curl 走 `HTTP_PROXY/HTTPS_PROXY`），Microsoft Learn 与 NVIDIA 论坛均 200。

## 0. 一句话答案

| 你的问题 | 答案 | 为什么（一句话） |
|---|---|---|
| 调大页面文件，能补上「VRAM 差 240–420 MiB」吗？ | **不能。一 MiB 都补不上** | 页面文件是**磁盘上给"可换出的私有已提交页"用的后备存储**；显存（含 WDDM 共享显存）容量由 **RAM 与 VidMm 预算**决定，二者无通路 |
| 调大页面文件，能补上「RAM 差几 GB」吗？ | **分场景：只对"匿名提交内存（VirtualAlloc/arena）"有效，且只是把硬失败换成换页抖动；对 mmap 专家、对 cudaHostRegister 锁定的部分完全无效** | 提交上限 = RAM + 页面文件（可涨）；但锁定页"保证不写入页面文件"，文件映射页由文件本身支撑、根本不进页面文件 |

## 1. WDDM 的「共享 GPU 内存」是什么，`cudaMalloc` 能不能用

### 1.1 官方定义：它是 VidMm 的第三种 segment，不是"多出来的显存"

Microsoft 的 WDDM 文档把 GPU 可用的物理内存抽象成 **segments**，明确分三类（[GPU segments](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/gpu-segments)）：

> "There are three types of segments: **Memory Segments** / **Aperture Segments** / **System Memory Segments**"
> "A **memory segment** represents memory dedicated to a GPU. It can be VRAM on a discrete GPU…"
> "The **system memory segment** is an implicit segment representing system memory references… To place an allocation in the system memory segment, the KMD needs to use the aperture segment ID."

任务管理器/dxdiag 里的 "Shared GPU memory" 就是 **system memory segment**：物理实体是 **主机 RAM**，通过 aperture（全局页表）让 GPU 引擎看到"连续"的一段。

WDDM 2.0 起 GPU 用虚拟地址，页表项能指向哪边，文档写得很直白（[GPU virtual memory in WDDM 2.0](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/gpu-virtual-memory-in-wddm-2-0)）：

> "GpuMmu implies that the GPU uses GPU page tables to access data. **The page tables could point to system memory or local device memory.**"

管理这一切的是 VidMm（[Video Memory Management and GPU Scheduling](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/video-memory-management-and-gpu-scheduling)）：

> "The video memory manager (**VidMm**) is a system-supplied component within the DirectX Graphics Kernel (Dxgkrnl) that is responsible for managing a GPU's memory."

回收机制（[Video memory offer and reclaim](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/video-memory-offer-and-reclaim)）：

> "WDDM 1.2 and later user-mode display drivers must use the memory **offer and reclaim** feature … to reduce memory overhead needed for temporary surfaces in local and system memory."

### 1.2 关键：`cudaMalloc` 在 WDDM 上**确实**会走到共享内存 —— 但这是"能分配"，不是"能用"

本次侦察最重要的一条一手证据。NVIDIA 论坛（NVIDIA 员工 Robert_Crovella，2025-10-15，帖 #2）在 [cudaMalloc with sysmem fallback](https://forums.developer.nvidia.com/t/cudamalloc-with-sysmem-fallback/347791) 里逐条回答：

> "**cudaMalloc, on a windows platform, with WDDM driver model, does not actually directly allocate memory on the GPU.** It makes a request of the WDDM driver (a Microsoft API) to request the allocation."
> "The WDDM system actually manages GPU memory (**plus sysmem as a fallback**) via something like a demand-paged virtual memory system. … This memory management is **not directly under the control of the NVIDIA driver**…"
> "**oversubscription is possible.** I've not personally witnessed oversubscription for a single client (e.g. CUDA) but I have witnessed oversubscription when there are multiple clients making memory requests"
> "**paging (i.e. movement/relocation) of data is possible, between device memory and sysmem**"
> "However, when a CUDA kernel is running, for example, my understanding is **any necessary device memory allocations will be moved to and actually resident in device memory**, for the CUDA client to use."
> "There would be no reason to return e.g. an out-of-memory error, and in fact the NVIDIA driver **has no knowledge of whether the data will be moved and be resident in sysmem**…"
> "If you don't like this behavior, for certain kinds of NVIDIA GPUs, you can select an alternate driver model, eg. **TCC**, which will take the WDDM subsystem out of the picture."

同帖楼主的原始抱怨正好是现象描述：

> "it looks like cudaMalloc can allocate to the shared GPU memory. **The only way to prevent this is to change the sysmem fallback in the windows driver.** … we need to now tell customers to turn off this setting."

**把两段合起来就得到严格答案：**

1. `cudaMalloc` **能**申请到超出专用显存的量 —— 请求交给 VidMm，VidMm 允许 allocation 落到 system memory segment（共享显存）。
2. 但**每次 kernel 执行前，被换出去的页必须搬回 device memory**（Crovella 原文）。"能分配"≠"能白嫖"：热数据仍必须真的待在 8 GB 里，否则每个 token 都要跨 PCIe 往返。
3. 所以"共享显存"是**给多客户端抢时间用的过载缓冲**，不是给单一大模型扩容的显存池。

### 1.3 共享显存有多大：官方没有明文，实测是 **RAM 的一半**

NVIDIA 论坛（njuffa，[How do I increase the shared GPU memory allocation multiplicator?](https://forums.developer.nvidia.com/t/how-do-i-increase-the-shared-gpu-memory-allocation-multiplicator/165033)）：

> 楼主："**Shared GPU memory is computed by CPU memory ÷ 2** … it's always half of the capacity of your RAM"，16 GB RAM → 8.0 GB Shared。
> njuffa（NVIDIA）："I have a vague recollection that **this 50% limit is baked into Windows**, at least with the **WDDM** driver model where the operating system is in charge of GPU memory allocation. Note that when we speak about 'shared memory' in the context of CUDA programming, we usually mean something entirely different…"

**本机实测**（`dxdiag /t`，2026-10-30）：

| 适配器 | Dedicated Memory | Shared Memory | Display Memory |
|---|---|---|---|
| NVIDIA GeForce RTX 4060 Ti | **7949 MB** | **15930 MB** | 23879 MB |
| AMD Radeon(TM) Graphics（7800X3D 核显） | 485 MB | **15930 MB** | 16416 MB |

- RAM 报 `32768MB RAM`；**15930 MB ≈ 15.6 GiB ≈ 31.1 GiB 的一半**，与 njuffa 的 50% 说法吻合。
- **决定性的一点：这个 15930 MB 与页面文件（本机 23 GiB）毫无关系。** 把页面文件从 23 GiB 改到 100 GiB，dxdiag 的 Shared Memory 一个数都不会动 —— 它由 RAM 总量算出。

> 官方文档里没找到"共享显存 = RAM/2"的明文（Microsoft 的 GPU segments / GPU virtual memory 两篇都没给比例），**这条只有 NVIDIA 论坛一手陈述 + 本机 dxdiag 实测数值，Microsoft 侧【未核源】**。但"它由 RAM 而非磁盘决定"这一点由 segment 定义直接成立。

## 2. 页面文件到底支持哪些分配：三种内存，三种命运

### 2.1 普通 host `malloc`/`VirtualAlloc(MEM_COMMIT)` —— **页面文件是它的后备**

Microsoft（[VirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc)）：

> `MEM_COMMIT` — "**Allocates memory charges (from the overall size of memory and the paging files on disk)** for the specified reserved memory pages. … **Actual physical pages are not allocated unless/until the virtual addresses are actually accessed.**"
> `MEM_RESERVE` — "Reserves a range … **without allocating any actual physical storage in memory or in the paging file on disk**."

Microsoft（[Introduction to page files](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/introduction-to-the-page-file)）：

> "Page files can be used to 'back' … system crash dumps and **extend how much system-committed memory (also known as 'virtual memory') a system can support.**"
> "**The system commit memory limit is the sum of physical memory and all page files combined.**"
> "If the system commit charge reaches the system commit limit, the system and processes might not get committed memory. This condition can cause **freezing, crashing, and other malfunctions**."
> "System-managed page files automatically grow up to **three times the physical memory or 4 GB** (whichever is larger, but no more than one-eighth of the volume size)…"

**⇒ 结论 1：调大页面文件，唯一确定能买到的是"更高的 commit limit"。** 即让 `VirtualAlloc(MEM_COMMIT)` 不返回 `ERROR_COMMITMENT_LIMIT`。它买到的是**承诺（promise）**，不是**物理页** —— 文档原话 "Actual physical pages are not allocated unless/until the virtual addresses are actually accessed"。

**本机实测**（`Win32_PageFileUsage`/`Win32_OperatingSystem`）：

| 项 | 值 | 换算 |
|---|---|---|
| `TotalPhysicalMemory` | 33,409,253,376 B | 31.1 GiB |
| `C:/pagefile.sys`/`AllocatedBaseSize` | 23,552 MiB | 23.0 GiB |
| `TotalVirtualMemorySize`（= commit limit） | 56,743,472 KB | **54.1 GiB** |
| `CurrentUsage` / `PeakUsage` | 3,171 MiB / **10,001 MiB** | 峰值已换出 10 GB |

54.1 ≈ 31.1 + 23.0，与文档公式逐位吻合。**峰值 10 GB 说明这台机器已经在用页面文件兜底** —— 这正是"页面文件在干活"和"页面文件救不了显存"可以同时成立的现场证据。

### 2.2 `mmap` 文件映射 —— **页面文件完全不参与**

Microsoft（[CreateFileMappingW](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-createfilemappingw)）：

> "If *hFile* is **INVALID_HANDLE_VALUE**, the calling process … of a specified size that is **backed by the system paging file instead of by a file in the file system**."

反向即：hFile 是真实文件句柄时，section 由**该文件**支撑。

**⇒ 结论 2：模型文件用 `MapViewOfFile` 映射时，换入换出走"文件本身"，脏页可干净丢弃（clean page，无需回写），不消耗提交额度、不占页面文件。** 所以对 mmap 路径，**改页面文件大小的收益恰好是 0**。

这条对 Strata 直接成立：`--mmap-experts` 就是 `MapViewOfFile`（见 §3），其命中率取决于 **OS 文件缓存**，而文件缓存吃的是**空闲物理内存**，不是页面文件。

### 2.3 `VirtualLock`/ 页面锁定 —— **不可能来自页面文件（硬约束）**

Microsoft（[VirtualLock](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtuallock)）：

> "Locks the specified region of the process's virtual address space **into physical memory**, ensuring that subsequent access to the region will not incur a page fault."
> "**All pages in the specified region must be committed.** Memory protected with PAGE_NOACCESS cannot be locked."
> "Each version of Windows has **a limit on the maximum number of pages a process can lock**. This limit is intentionally small… Applications that need to lock larger numbers of pages must first call the **SetProcessWorkingSetSize** function to increase their minimum and maximum working set sizes. **The maximum number of pages that a process can lock is equal to the number of pages in its minimum working set minus a small overhead.**"
> "Pages that a process has locked **remain in physical memory** until the process unlocks them or terminates. **These pages are guaranteed not to be written to the pagefile while they are locked.**"

CUDA 侧同一件事（[cudaHostRegister](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html)）：

> "**Page-locks the memory range** specified by ptr and size and maps it for the device(s)…"
> "**Page-locking excessive amounts of memory may degrade system performance, since it reduces the amount of memory available to the system for paging.** As a result, this function is best used sparingly to register staging areas for data exchange between host and device."

CUDA 最佳实践（[Pinned Memory](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)）：

> "**Pinned memory should not be overused.** Excessive use can reduce overall system performance because **pinned memory is a scarce resource**…"

**⇒ 结论 3（最硬一条）：锁定页"保证不写入页面文件"，因此页面文件在定义上无法为锁定内存提供任何容量。** 想锁住 N GiB 专家 arena，就需要 N GiB 物理 RAM 减去系统最低工作集；页面文件从 23 GiB 调到 230 GiB，可锁上限一点不涨。

还有一个耦合陷阱：`VirtualLock` **要求页已提交**（"must be committed"），而提交额度 = RAM + 页面文件。所以"调大页面文件 → 提交成功 → 然后 `VirtualLock` 因物理内存不够而失败"是完全可能的失败序列 —— 钱花了，事没成。

## 3. Strata 的 `--resident-experts` 与 `STRATA_ARENA_PIN_GIB` 在页面文件上的实际行为

证据来源：`strata.exe`（0.1.54）二进制内嵌的 help / 日志文本（`strings` 提取，原样引用）。**本机一手**，无 URL；与 §1–§2 官方文档交叉验证。

### 3.1 help 原文（逐字）

> `  --resident-experts   the low-RAM PC's resident mode (setup): --mmap-experts --resident-cpu-experts`
> `                       with the copy page-locked when possible, 4 GiB headroom, plain mmap if it`
> `                       does not fit.  Same answers as --mmap-experts for the same placement.`

拆开就是三档降级：
1. `--mmap-experts` + `--resident-cpu-experts`（把 GPU 装不下的专家常驻普通 RAM）；
2. **能锁就锁**（`page-locked when possible`）；
3. **装不下就退回纯 mmap**（`plain mmap if it does not fit`），并留 **4 GiB headroom**。

配套的 `--mmap-experts` 原文很关键：

> `  --mmap-experts       R2.1: opt OUT of the resident expert arena, back to MapViewOfFile.`
> `                       The A/B arm: the mmap's rate depends on the OS page cache holding`
> `                       34 GB, and measured 71.97 vs 34.78 ms/token cold vs warm.`

**⇒ 这是页面文件的"归零证据"：mmap 档的性能由 `the OS page cache holding 34 GB` 决定，实测冷 71.97 ms/token、热 34.78 ms/token（2.07×）。文件缓存用的是物理内存，页面文件不在这个链路里。**

### 3.2 锁定预算的公式（引擎自己算的）

二进制定长字符串相邻出现，构成一条预算链：

> `STRATA_ARENA_PIN_GIB`
> `the GPU's shared-memory budget %.1f GiB - %.1f GiB in use - 4 GiB`
> `%s: RAM/2 - 8 GiB of %.1f GiB`
> `STRATA_ARENA_LOCK`
> `large pages are resident without a lock; `
> `arena lock disabled (STRATA_ARENA_LOCK=0); `
> `NOT registered with the GPU driver (integrated GPU, UMA mode; STRATA_ARENA_PIN_GIB=0 registers it); `
> `by the engine (multi-GPU under WDDM, or remote experts)`
> `by STRATA_ARENA_PIN_GIB`
> `cudaHostRegister PORTABLE ok; ` … `cudaHostRegister limited to ` … `; STRATA_ARENA_PIN_GIB=auto; N sets a cap; #243); `
> `cudaHostRegister of the whole arena FAILED (` … `) - the arena is NOT pinned, so copies will be slow; `
> `cudaHostRegister FAILED (` … `, the driver refused the next one` … `, the cap was reached`

多 GPU 的补充：

> `strata generate: multi-GPU under WDDM: at most 8 GiB of the expert arena is pinned (STRATA_ARENA_PIN_GIB changes it)`
> `strata generate: STRATA_ARENA_PIN_GIB=%d: %s`

**读法（推断，依据上述字符串的顺序与语法）：**

    pin cap = min( shared-memory budget − in use − 4 GiB ,  RAM/2 − 8 GiB )

`STRATA_ARENA_PIN_GIB` 只是**上限开关**（`N sets a cap`），`auto` 是默认。

**⇒ 关键：两个口径里都没有页面文件。**
- 第一项用 **WDDM 共享显存预算**（§1.3 那类数）减去占用再减 4 GiB —— 由 RAM 决定；
- 第二项是 **RAM/2 − 8 GiB** —— 直接是物理内存的一半（与 njuffa 说的 50% 同源）。

调大页面文件，两项都不动 ⇒ **pin cap 不动**。按本机 31.1 GiB 算：31.1/2 − 8 ≈ **7.6 GiB**，再被 15930 MB − 占用 − 4 GiB 压一次。

### 3.3 失败模式：引擎会明确说"没锁上"

> `[pinned-memory-exhausted] the OS gave no more page-locked memory`
> `the exchange buffers could not be page-locked`
> `FileExpertSource: exchange buffer rotation enabled: %lld buffers in %zu block sizes (largest %llu bytes, %.2f GiB page-locked); no host commit memcpy`

**⇒ 锁不上时的报错是 "the OS gave no more page-locked memory"，不是 "commit limit exceeded"。** 对前者，页面文件是无效药。

### 3.4 匿名 arena 装不下时：引擎自己承认"会换页"

> `the expert arena needs %.2f GiB of RAM but %.2f GiB is available (%.2f GiB short%s): **the load may swap or be stopped by the OS**%s. Close other programs, or run with less RAM: --mmap-experts with --resident-budget-gib N`
> `strata generate: %.2f GiB of RAM is available now (after %.1f s): loading the expert arena`
> ` - with this little room the whole machine can stall in memory reclaim until it is restarted (#4051); on Linux a systemd MemoryHigh= below the RAM keeps one program from taking all of it`
> `ArenaExpertSource: the expert arena needs %.2f GiB of RAM but this process's memory limit (cgroup memory.max / memory.limit_in_bytes) is %.2f GiB: it would be killed while loading.`

**⇒ 这正是页面文件唯一"有效"的那一格：** arena 是 `VirtualAlloc` 提交的匿名内存（§2.1），commit 额度 = RAM + 页面文件，所以**调大页面文件确实能让这条 "%.2f GiB short" 从"拒绝加载"变成"加载成功"**。但引擎把后果写在同一警告里：`the load may swap or be stopped by the OS`、以及`the whole machine can stall in memory reclaim until it is restarted (#4051)`。

## 4. 结论：两个缺口，分别判

### 4.1 「VRAM 差 240–420 MiB」—— 页面文件**不能**补

三层独立理由，任一层都足以否决：

**第一层：通路不存在。** 页面文件是 `MEM_COMMIT` 的后备（§2.1），共享显存是 system memory segment（§1.1）。两者没有共享容量池。本机实测：页面文件 23 GiB 时 Shared Memory = 15930 MB；这两个数由**不同资源**（磁盘 / RAM）决定。

**第二层：即使 sysmem fallback 让 `cudaMalloc` 不报错，性能也不成立。**
- 机制：Crovella 原文 —— "when a CUDA kernel is running … any necessary device memory allocations will be **moved to and actually resident in device memory**"。
- 量级：这 240–420 MiB 是**每轮前向**的专家缓冲 + 槽（`reports/Strata-8G实测-Qwen36起不来.md`：需求 1159 MiB 是"混合专家的缓冲 + 槽"，arch 决定的固定开销）。
- 算术（**估算，非实测**）：0.24–0.42 GiB 按 40 tok/s 往返 ⇒ **9.4–16.8 GB/s** 持续跨 PCIe 流量；本机是 **PCIe Gen4 ×8**（nvidia-smi `pcie.link.width.max=8`），Gen4 ×8 理论 15.75 GB/s、实用约 12–13 GB/s。**仅这一项就吃满（甚至超过）整条链路**，还没算权重本身的读。
- 对照：`--mmap-experts` 档实测 **71.97 ms/token（冷）**（§3.1），即约 14 tok/s，同一量级。

**第三层：在这个引擎上它连"试"的机会都没有。** 报错是 `1159 MiB needed, 917 MiB free` —— 这是**加载前按 `cudaMemGetInfo` 做的准入检查**，不是 `cudaMalloc` 返回的 OOM。失败发生在引擎自己的预算判断里，改页面文件对判定输入（free VRAM）零影响。

**⇒ 唯一"能补"的路径不是页面文件，而是把驱动设成允许 sysmem fallback（NVIDIA 控制面板 `CUDA - Sysmem Fallback Policy`）或换 TCC / 换 Linux**（Crovella 原文给了这两条），代价就是第二层的性能崩塌。**这不是"跑更大的模型"，是"把 OOM 换成 thrash"。**

### 4.2 「RAM 差几 GB」—— 分场景，只有一格有效

| 场景 | 页面文件调大后 | 判据 |
|---|---|---|
| **A. arena 是 `VirtualAlloc` 匿名提交内存，只要求"能加载 / 不被 OS 杀掉"** | ✅ **有效**：commit limit 涨，`%.2f GiB short` 消失，能进加载 | §2.1 commit limit = RAM + 页面文件；§3.4 引擎原文 "the load may swap" |
| **B. 同上，但要求 tok/s** | ❌ **无意义**：缺页从 NVMe 读，SSD 顺序 ~3–7 GB/s 量级，远低于 DDR5；且换入同步阻塞 | §3.4 "may swap"；本机两块盘均 NVMe |
| **C. 需要 `cudaHostRegister` 锁定的那部分** | ❌ **完全无效**：锁页 "guaranteed not to be written to the pagefile"，上限 = 最小工作集 | §2.3 VirtualLock 原文；§3.2 pin cap 公式；§3.3 `pinned-memory-exhausted` |
| **D. `--mmap-experts` 的专家（MapViewOfFile）** | ❌ **完全无关**：由文件本身支撑，脏页可丢弃，不占提交额度 | §2.2 CreateFileMappingW 原文；§3.1 "the OS page cache holding 34 GB" |
| **E. 想让文件缓存命中率变高** | ❌ **无关**：文件缓存吃空闲物理内存，页面文件不参与 | 推论（§2.2 + §3.1） |

**一句话：A 是唯一有效格，而 A 恰恰是"能用但会很慢"的那一格 —— 用户想要的"跑更大模型"，落在 B/C/D。**

---

## 5. 判定阈值（可直接拿去回答用户）

1. **页面文件 ∈ {磁盘}，显存 ∈ {RAM + VidMm 预算}。** 想让页面文件影响显存，需要一条不存在的通路。→ 任何"调虚拟内存跑更大模型"的说法，在**显存**这一侧恒假。
2. **页面文件能买的只有 commit limit。** 判据是失败信息长什么样：
   - `ERROR_COMMITMENT_LIMIT` / `%.2f GiB short` / "out of memory: commit limit" → 页面文件**可能**有用（场景 A）；
   - `cudaErrorMemoryAllocation` / `CUDA out of memory` / `1159 MiB needed, 917 MiB free` → 页面文件**无用**，这是 device 侧预算；
   - `pinned-memory-exhausted` / `cudaHostRegister FAILED` / "the OS gave no more page-locked memory" → 页面文件**无用**，且**反向有害**（锁定越多，可给分页的物理内存越少，CUDA 文档原话）。
3. **锁定上限是物理内存的函数，且被工作集二次限制**（`min working set − overhead`，需先 `SetProcessWorkingSetSize`）。本机 pin cap 的引擎口径是 `RAM/2 − 8 GiB = 15.6 − 8 ≈ 7.6 GiB`；再被 `shared budget − in use − 4 GiB` 压一次。
4. **危险组合**：`VirtualLock` 要求先 committed ⇒ 调大页面文件能让"提交"过关、再在"锁定"处失败。**看到"提交成功但锁不上"就不要再加页面文件了，加 RAM。**
5. **对本机的具体建议（只读结论，未改任何配置）**：VRAM 差 242–418 MiB 属第 2 类判据，**改页面文件是纯浪费**；正解是降模型 / 降上下文 / 换 `--mmap-experts + --resident-budget-gib N`（引擎自己在 §3.4 的警告里就这么建议）。
