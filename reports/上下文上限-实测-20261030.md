# NInfer 单次可信上下文上限：实测与结论（2026-10-30）

机器：RTX 4060 Ti 8 GiB（可用 8,188 MiB）· Ryzen 7 7800X3D · 31.1 GB DDR5-6000 · Windows 11 26100
引擎：`engine/ninfer-serve-89.exe`（801,324,544 B）· 模型：Ternary-Bonsai-2-27B PTQ1_0（5.96 GiB）

## 一、一句话结论

**单次请求的可信上下文 = 显存池（`--kv-capacity`）的大小，不多一个 token。**

- 本机池的天花板：**88,000 token 能起服（只剩 33 MiB），92,000 起不来**。生产推荐 **72,000**（243 MiB 余量）。
- 这是从过去 40,000 的 **1.8×**，也是这台卡在「可信」前提下的物理上限。
- **150K / 200K 单遍算术不可能**（见第四节），但**分片注入**可以做到 150K 8/8 = 192.6 s、200K 8/8 = 316 s（见第五节）。

## 二、显存池天花板扫描（无 MTP、rk2v4-e8、chunk 1024、max-context 262144、host-kv 8192 MiB）

| `--kv-capacity` | 结果 | 起服后剩 |
|---|---|---|
| 64,000 | OK | 349 MiB |
| 72,000 | OK | 243 MiB |
| 80,000 | OK | 137 MiB |
| 88,000 | OK | 33 MiB |
| 92,000 | **FAIL** | `requested Engine runtime reservation requires 1505027072 bytes, but only 1487929344 bytes are available for runtime capacity` |
| 96,000 | **FAIL** | 同上（1,559,880,704 B / 1,487,929,344 B） |

结论：引擎的 runtime 预留是**固定 1.39–1.50 GiB**（改 `--prefill-chunk 512/256` 不变），可用量被桌面占用（OBS/QQNT/GameViewer 各占一点）锁在 1,487,929,344 B。
**想让池更大 → 只能靠关掉占用显存的程序**（每让出 105 MiB ≈ 多 8,000 token 池）。

## 三、可信边界实测（`tools/exp_long_probe.py`，8 针 fixture，temperature 0，全部写 `tmp/exp/runs.jsonl`）

| 探针 | prompt token | prompt÷池 | 命中针 | 编造 | 耗时 |
|---|---|---|---|---|---|
| q9（池 72K） | 70,473 | 0.98× | **8/8** | 0 | 96.0 s |
| q6（池 72K，单针文本） | 70,528 | 0.98× | 1/1 正确 | 0 | 90.5 s |
| q12（池 88K） | 84,705 | 0.96× | **8/8** | 0 | 111.6 s |
| q13（池 88K，贴边） | 88,618 | 1.007× | **8/8** | 0 | 128.5 s |
| q1/q10/q11（池 64K→72K） | 94,439 | 1.48× → 1.31× | 8/8 → **7/8** → **7/8**（两次缺的针不同） | 0 | 129.8 / 136.1 / 4.9 s |
| q2/q4（池 64K） | 151,805 | 2.37× | **1/8** | 0 | 277.5 / 249.6 s |
| q3/q5（池 64K） | 202,586 | 3.17× | **0/8**（还声称「文档里 0 个校验码」） | 0 | 414.3 / 405.7 s |

判据：**prompt ≤ 池 = 8/8 可信**（88,618 贴边过 1,375 页也 8/8）；**一明显过池立刻掉**——只超 31%（1.31×）就稳定丢 1 针，超 2.4× 只剩 1/8，超 3.2× 全丢且答案听起来完全合理。

**本机实测到的最高可信单遍：88,618 token（池 88,000，起服后只剩 33 MiB）**；日常档推荐池 72,000（243 MiB 余量）跑 70K 提示 8/8。

## 四、为什么 150K 单遍不可能（算术）

- 150K token = 2,344 页 × 0.84 MiB（rk2v4-e8 每页价）= **1,921 MiB KV**；
- 权重 5.96 GiB = 6,103 MiB；runtime ≈ 1,390 MiB ⇒ 合计 ≈ **9,414 MiB > 8,188 MiB**。
- 池从 64K 加到 150K 需要 +1,126 MiB，而 64K 池起服后卡上只剩 349 MiB。
- 200K = 3,125 页 × 0.84 = 2,562 MiB KV，更远。

（每页 64 token，价目见 `README-pack.md`：bf16 4.0 / k8v4 1.67 / rk4v4-e8 1.16 / **rk2v4-e8 0.84** MiB —— rk2v4-e8 已是最便宜档。）

## 五、150K / 200K 的正解：分片注入（`tools/longdoc.py`）

把长文切成 ≤26,000 token 的片，逐片问同一个问题，再把各片取证拼起来。每片都 ≤ 池，所以每片都可信。

| 文档 | 分片 | 每片 prompt | 总耗时 | 命中 |
|---|---|---|---|---|
| 150K（151,805 token / 4011 行） | 7 片 | 18.6K–25.0K | **192.6 s（3.2 分）** | **8/8** |
| 200K（202,586 token） | 8 片 | ~25K | **316 s（5.3 分）** | **8/8** |

代价：3–5 分钟一次；好处：**结果是可信的**，而单遍 200K 那次给出的是「文档里 0 个校验码」这种自信的假答案。

## 六、和 llama.cpp 262K 路线对照（同一台机器）

| 维度 | NInfer 单遍 72K | NInfer 分片 200K | llama.cpp 262K（tiered KV） |
|---|---|---|---|
| 可信上限 | 72K（实测 8/8） | 任意（分片数 × 26K） | 262K（作者件，实测 209K 可跑） |
| 首字 | 70K → **96 s** | 200K → 316 s | 25K → **335 s**；209K → 3–6 小时 |
| decode | 65–107 tok/s | 同左 | 56–97 tok/s |
| 显存 | 7,945 MiB（池 72K） | 同左 | 7,798 MiB |
| 适用 | 日常/中长文 | 超长文档问答 | 真·200K 单遍但首字以小时计 |

## 七、推荐怎么用

1. **日常（默认）**：`bash scripts/serve2.sh` —— 池 40,000 + MTP draft4，97–107 tok/s，40K 内 8/8 可信。
2. **长文（推荐档）**：`PROFILE=long72 bash scripts/serve2.sh` —— 池 72,000、无 MTP、id `bonsai27b-ptq1-nomtp-rk2v4-72k`，96 s 读 70K。
3. **超长（150K+）**：保持 long72，用 `python tools/longdoc.py --doc X --question "…" --engine http://127.0.0.1:8091/v1 --model <id> --shard-tokens 26000`。
4. **别做**：把 `--kv-capacity` 开到 100K+ 去「试试看」——起不来；或把 150K 塞进 64K 池单遍问——会得到自信的假答案。

## 八、怎么知道自己在超池（唯一侦测手段）

引擎会打这行（每 30 s 最多一次）：

```
[warning] ninfer-serve: prompt exceeds the resident Device KV pool: prompt 202586 tokens (3166 pages) > pool 64000 tokens (1000 pages).
Part of the prompt is therefore not resident, and the MIDDLE of such a prompt has been measured to go missing with no error line,
HTTP 200 and a plausible wrong answer; the root cause is not localized. Treat every answer to this request as unverified against its context,
and raise --kv-capacity to at least the prompt's token count (measured: prompt >= pool is the condition that reproduces it) before reading a result.
```

**没有这行不等于安全**（30 s 节流）；唯一可靠的判断是「prompt token 数 ≤ 池」。
