# 超池长上下文可用性实测：200K 到底能不能用

| 项 | 值 |
|---|---|
| 测试日期 | 2026-10-30 |
| 测者 | overpool-verifier（独立验证，非引擎作者） |
| 引擎 | ninfer-serve-89.exe build engine-v0.11.0-kvmem-20261003-98-g43c39c6 |
| 模型 | Bonsai 27B ternary PTQ1（5.94 GiB 权重） |
| 硬件 | RTX 4060 Ti 8G（8,188 MiB，sm_89）/ Ryzen 7 7800X3D / 32 GB DDR5-6000 / Win11 |
| 现役跑法 | --kv-capacity 40000 --kv-dtype rk2v4-e8 --host-kv-mib 6144 --max-context 262144 + MTP draft4/win8 + --no-cuda-graph --device-state-slots 0 |
| 端点 | **直连 127.0.0.1:8091**（不经 8081 网关；网关会裁剪/摘要，会污染结论） |
| 全程约束 | 未 taskkill 任何引擎、未改引擎参数、未起第二实例；请求之间 sleep 5 s；cached_tokens 实测恒为 0 |

## 0. 结论

**一句话：200K 能跑通，但「能跑通」只在引擎刚启动后的第一个大请求上成立；同一进程里从第二个大请求开始就静默错，而且 200K 并不比 100K 更安全。**

实测（全部 HTTP 200、无报错、答案通顺，直连 8091）：

| 次序 | 请求 | 结果 |
|---|---|---|
| 引擎启动后第 1 个大请求 | 209K（lead 的 probe200k，8 针） | **8/8** |
| 之后 | 100K（8 针） | **2/8** |
| 之后 | 150K（8 针） | **0/8**，答案里 49 个文档中根本不存在的编造暗号 |
| 之后 | 209K 复跑（同一份结构、同一长度） | **2/8** |
| 之后 | 209K 中段专测（6 针全在 41–59%） | **0/6**，模型答「无」 |
| 之后 | 100K 相似干扰（30 条同句式假条目） | **1/8**，且引用了 2 个假编号 |
| 之后 | 100K **完全无关**的第二份文档（开头 16 字符后即分叉） | **1/8**，答案退化成无限重复同一个错暗号 |
| 同一污染进程内 | 13K / 30K（池内） | **8/8 / 8/8**（见 §5.1） |

三句话处方：

1. **每个长上下文任务之前重启引擎，并且一个进程只服务一个大请求**（本机唯一可行做法）。
2. **日常 ≤40K 的对话不受影响**（§5.1 实测），可以长期跑，不用重启。
3. **超池答案一律要抽查关键事实**：失败是静默的——HTTP 200、没有 error 行、还能编出 49 个看起来合理的暗号。

引擎自己说 unverified，但它仍然回 HTTP 200 和一份通顺答案：**没有拒答、没有降级标记、finish_reason 也没有异常**。

## 3. 机制：四层证据

### 3.1 环形 KV 的预算表是静态的：evidence 只有 128 页

```text
[ring] budgets: protect=0 skeleton=0, evidence=128, recent=0, free=490 (pool 625) backend_pages=7 backend_capped=1
```

- 全日志 **1,731 次采样，这一行一字不变**（唯一波动是 free 490↔497），与 prompt 是 13K 还是 209K 完全无关。
- 页大小 64 token（209,154 / 3,269 = 64.0）。⇒ 内容打分能拿到的「证据」预算 = 128 × 64 = **8,192 token**，只占 209K 提示的 **3.9%**。
- free=490 页（31,360 token，占池 78%）**一直闲置，从不借给 evidence**。这是 200K 装不下的直接原因：
  不是卡装不下 3,269 页，而是分配器把它锁在 free 里不给长上下文用。
- backend_pages=7 backend_capped=1：host-kv 给了 6144 MiB，实际只用了 7 页（448 token）就到顶。

检索本身没有失败，失败在选择：

```text
[ring] retrieve preferred req=N n=128          # 采样里 preferred 恒为 128
[ninfer] ring retrieve: which=text preferred=128 restored=128 first=4 last=1162
# 1246 次检索合计：preferred=152079 / restored=152079 -> restored_frac = 1.000
```

即：**要求多少页就还原多少页，一次都没少**。所以丢的不是「还原失败」，而是**排名把要还原的页选错了**。

### 3.2 打分预算(512 块) 与 环形证据预算(128 页) 不匹配

```text
kvmem_score: SELECT ... n_blocks=3268 budget_blocks=512 sink_blocks=64 kept=512 ... scored_kept=448 candidates=3204 ...
```

内容打分器每条 KEPT 选出 **512** 块（32,768 token），可信证据区只有 **128** 页（8,192 token）。
⇒ 选中的 512 个里最多 128 个能真正驻留，其余的选择本身毫无意义。

### 3.3 打分表跨请求复用（高水位永不重置）

```text
# 209K 首次（8/8）：n_blocks 跟随本请求
kvmem_score: SELECT ... n_blocks=1    ... span_abs=[3,209147)
kvmem_score: SELECT ... n_blocks=3268 ... span_abs=[3,209147)   # 3,269 块，自洽
KEPT#0 / KEPT#118 / KEPT#235: real=512 stale=0   # 235 条 KEPT 全部 0% 陈旧

# 100K（2/8）：n_blocks 冻结在 3,268，而本请求只有 1,562 块
kvmem_score: SELECT ... n_blocks=3268 budget_blocks=512 sink_blocks=64 kept=512 skip=2756 candidates=3204 kept_range=[0,3267] span_abs=[3,99904)
KEPT#0   real(<1562)=512 stale=0
KEPT#113 real(<1562)=65  stale=447     # 结尾 87.3% 预算打在上一请求的幽灵块上

# 150K（0/8）：同样冻结，本请求 2,344 块
kvmem_score: SELECT ... n_blocks=3268 ... skip=2756 ... candidates=3204 ... span_abs=[3,149958)
KEPT#169 real(<2344)=64 stale=448     # 87.5% 陈旧
```

- skip=2756 / candidates=3204 在所有后续请求里**一字不变**（只由 n_blocks=3268 与 sink_blocks=64 决定）。
- KEPT 里出现 max=3267 的块号，而 100K 请求自己只有 1,562 块。⇒ 打分表按块号索引、**跨请求不复位**；块号每请求从 0 重排，
  于是「上一请求第 i 块的分数」被当成「本请求第 i 块的重要性」用来淘汰。
- 209K 复跑时 n_blocks=3268 恰好等于自身 3,269 块，块号**数值上全部合法**（235 条 KEPT 全 0% 陈旧），结果仍只有 2/8 ——
  说明坏的不是「块号越界」，而是**分数属于上一请求的内容**。

### 3.4 mask hidden：中段被系统性藏掉

```text
209K 首次（8/8）： span=3270 resident=617 hidden=2653 (81.1%)  mid_hidden=1132 / 1145 块 = 98.9%
209K 复跑（2/8）： span=3267 resident=617 hidden=2650 (81.1%)  mid_hidden=1143 / 1143 块 = 100%
150K（0/8）：     span=2350 resident=616 hidden=1734 (73.8%)  mid_hidden=810  / 823 块 = 98.4%
100K（2/8）：     span=1562 resident=616 hidden=946  (60.6%)  mid_hidden=514  / 547 块 = 94.0%
```

中段（mid_lo–mid_hi）恒定隐藏 94–100%，与引擎警告里 the MIDDLE ... has been measured to go missing 完全对上。
注意 209K 首次那一次**也**隐藏了 81.1%、中段 98.9%，却拿到 8/8 —— 说明「隐藏」本身不致命，
决定性的是**排名有没有把那几页选回来**（解码阶段每个 token 还会重新检索一次）。

## 5. 三条对照实验

### 5.1 池内回归：污染进程里 ≤40K 还好不好？

两个池内请求都跑在**已被 150K/209K 污染的同一个进程**里：

| 请求 | prompt_tokens | HIT | wall (s) | decode (tok/s) | exceeds 警告 | mask hidden 行 |
|---|---|---|---|---|---|---|
| 13K | 12,952 | **8/8** | 20.5 | 53.2 | 无 | 无 |
| 30K | 29,818 | **8/8** | 47.1 | 56.4 | 无 | 无 |

⇒ **污染只影响超池路径**。池内请求不触发 mask/淘汰，打分表的脏数据用不上，40K 以内照常可用。
这是本次测试最重要的一条好消息：**这台机器只要不碰超池，日常对话不受影响。**

说明它确实在从文档里取件，只是取错——不是「靠独特 token 走运」的问题。

## 7. 速度账

| 上下文 | prompt_tokens | 有效 prefill (tok/s) | decode (tok/s) | 单次 wall (s) | 相对 32K 的 decode |
|---|---|---|---|---|---|
| 32K（历史实测） | ~32,000 | 963 | 97–98（散文 45.7） | — | 1× |
| 13K（池内） | 12,952 | 678 | 53.2 | 20.5 | 0.55× |
| 30K（池内） | 29,818 | 651 | 56.4 | 47.1 | 0.58× |
| 100K | 99,911 | 586 | 37.2 | 171.2 | 0.38× |
| 150K | 149,965 | 534 | 36.7 | 291.7 | 0.38× |
| 209K（首次） | 209,154 | ~567 | ~7（5.2–9.2） | 378.6 | 0.07× |
| 209K（复跑） | 209,038 | 485 | 28.8 | 431.9 | 0.29× |

- 有效 prefill 缓慢下滑（678 → 485–586 tok/s），但瞬时值在 209K 尾部会掉到 358 tok/s、最低见过 67 tok/s。
- 真正疼的是 decode：209K 首次只有 5.2–9.2 tok/s（73 token 花了约 10 s），比 32K 的 97 tok/s 掉一个数量级。
- 体感：一次 200K 请求 **约 6–7 分钟出第一个字**，之后每秒 7–29 字。

## 8. 可复用判据与处方

**判据 A（池内，可信）**：prompt_tokens ≤ 40,000 → 可信，decode 37–53 tok/s。13K/30K 实测均通过。

**判据 B（超池，一次性可信）**：只有当**当前引擎进程启动后还没处理过任何超池请求**时，第一个超池请求才可信（209K 实测 8/8）。
之后同一进程内的超池请求一律不可信，而且**长度更短不会更安全**（100K 2/8、150K 0/8、209K 复跑 2/8）。

**判据 C（一行自检，可脚本化）**：

```bash
grep "kvmem_score: SELECT" /c/Project/local_model/logs/engine-40k.log | tail -1
# n_blocks 若明显大于「本请求 prompt_tokens / 64」，说明打分表已被上一请求污染 -> 本次答案不可信
grep -c "prompt exceeds the resident Device KV pool" /c/Project/local_model/logs/engine-40k.log
# 这个计数 > 1 基本可以判定当前进程已经不适合再发超池请求
```

**操作处方**：

1. 需要长上下文 → **先重启引擎，再发那一个请求**；一个进程只服务一个大请求。
2. 「把 --kv-capacity 提到 ≥ prompt」在本机做不到：51200 能起但 prefill 崩到 180 tok/s，56000 直接拒启；
   而且即使提上去，evidence 仍是 128 页（§3.1），装进去了也未必用得上。
3. 日常使用拆成 ≤40K 的段：池内 decode 37–53 tok/s，且不会静默错。
4. 任何超池答案必须抽查关键事实；别把「HTTP 200 + 答案通顺」当可信证据。

## 9. 机理：两种假设，各自需要什么证据才能分辨

现有证据已经把故障钉在「超池路径的页选择/淘汰」上，但具体是哪个环节，还剩两种互斥解释。
分开写是因为**处方完全不同**：H1 靠重启/复位打分表就能救；H2 只能改引擎预算或把池提上去。

| | 假设 | 一句话 |
|---|---|---|
| **H1** | 打分表跨请求复用 | 块号每请求从 0 重排，打分表按块号索引且进程内**不复位** ⇒ 上一请求第 i 块的分数被当成本请求第 i 块的重要性 |
| **H2** | 证据预算静态 128 页 | 环形 KV 的 evidence 预算恒为 128 页（8,192 token），远小于打分器选出的 512 块（32,768 token），且 free 490 页闲置不借 |

### H1 的支持证据

- n_blocks 冻结在 3,268，而 span_abs 随请求变化（100K 只有 1,562 块、150K 2,344 块，仍报 3,268）。
- KEPT 列表里出现 max=3,267 的**越界块号**（本请求根本没有这些块）。
- 100K 最后一条 KEPT：real=65 / stale=447（87.3%）；150K 最后一条：real=64 / stale=448（87.5%）——检索预算几乎全打在上一请求的幽灵块上。
- skip=2,756 / candidates=3,204 在所有后续请求里一字不变（只由 n_blocks 与 sink_blocks 决定）。

**H1 的缺口**：209K 复跑时块号全部合法（235 条 KEPT 全 0% 陈旧）却仍 2/8。⇒ 「分数属于旧内容」这一层本身无法从日志直接观测，属推断。

### H2 的支持证据

- [ring] budgets 这一行 1,731 次采样一字不变，与 prompt 是 13K 还是 209K 无关。
- free=490 页（31,360 token，占池 78%）长期闲置，从不借给 evidence。
- restored_frac = 1.000（1246 次检索 preferred=152,079 / restored=152,079）：还原没失败，是**选错了要还原的页**。
- mask hidden 恒定隐藏中段 94–100%，正好对上引擎警告里 the MIDDLE ... has been measured to go missing。

**H2 的缺口**：该预算在「第一次 8/8」和「第二次 2/8」里完全相同，**单独无法解释同长度同结构的结果翻面**。

### 分辨这两种假设需要什么证据

| 实验（都要在干净进程里做） | H1 预测 | H2 预测 | 说明 |
|---|---|---|---|
| 重启后**先发 100K**（8 针） | **8/8** | 仍 0–2/8 | **最省事的判别器**，一次请求 3 分钟即可定性 |
| 重启后先发 209K，然后立刻复跑 209K | 8/8 → 2/8 | 8/8 → 8/8 | 已实测：8/8 → 2/8 ⇒ **H2 单独不成立** |
| 换无关前缀的 100K 文档 | 仍错 | 仍错 | 已实测 1/8，两条都预测错 ⇒ 不能分辨（但排除了「前缀缓存」） |
| 把 evidence 预算从 128 页放大（需改引擎） | 若仍错 ⇒ H1 主导 | 应显著改善 | 需要改代码/改池，本机做不到 |

**当前判断**：两条不是二选一，而是叠加——**H1 决定「选错页」，H2 决定「选错了也装不回去」**。
已测到的 8/8 → 2/8 翻面证明 H2 不足以单独解释；而 209K 复跑块号全合法仍错证明 H1 的「块号越界」也不足以单独解释。
要一次性钉死，只需 lead 那个重启对照：**重启后先发 100K**——8/8 则 H1 主导（重启即救），仍错则 H2 主导（必须改预算/加池）。

## 10. 没做的与建议

- **240K 档未测**：在已被污染的进程里再跑 240K，无法区分「长度边界」与「第 N 次请求污染」，测了也不可外推；
  且 240K 单次要约 10 分钟。需要边界值时应在重启后的干净进程里一次跑 240K。
- **决定性实验（建议 lead 做，3 分钟）**：重启 8091 引擎后**先发 100K**：
  - 8/8 ⇒ 证实「长度无关、只看进程状态」，100K/150K 的塌陷全部由打分表污染 + 128 页证据预算解释；
  - 仍 2/8 ⇒ 说明 100K 另有独立问题（例如 host-kv 6144 MiB 装不下），需要单独查。
- **值得报给引擎作者的两处**：
  (a) evidence=128 / free=490 的静态分配 —— 池里 490 页闲着也不给长上下文用，这是 200K 装不下的直接原因；
  (b) n_blocks 高水位跨请求不复位 —— 后续请求的 KEPT 里出现上一请求的块号（§3.3），这是「静默错」最可疑的来源。
