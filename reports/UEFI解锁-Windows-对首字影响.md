# UEFI 解锁（Windows）对首字时延有没有用

> 结论：**能刷，但对我们的首字几乎没有用 —— NO-GO。** 同一张卡、同一份 8k 提示实测：默认 prefill 有 **63.6% 的时间跑在不加锁的 int8 路径**上，只有 36.4% 落在被钳的 A16（FP32 累加）路径，所以解锁的理论上限是 **×1.163（+16.3%）**；落到 TTFT 上：8k 省 **1.0 s**、24k 省 **3.3 s**、37k 省 **5.4 s**（保守 +8.8% 再减半）。decode **+0**、显存 **+0**。代价是每次冷启动过一遍固件写事务 + 易失 + 重启打断服务 + Code 12 风险。

## 1. 这个项目是什么（与 Zagitta/gpu-unlock 不是同一个）

- 仓库 **physicsdolphin/nv-uefi-unlocker**：**119 stars / 10 forks / 128 commits**，最近提交 **2026-10-29T19:46:05Z**（`commits/main.atom`），Rust 写、开发环境本身就是 Windows。自述（本地副本 `tmp/ext/nvuefi.md:9-13`）："20~40 系 全平台操作系统通用 UEFI **预驱动** NVIDIA GPU 解锁器"。
- **不是驱动补丁、不是内核模块、不刷 VBIOS**：它在 UEFI DXE 阶段、NVIDIA 驱动加载**之前**跑完整个固件事务 —— SEC2 擦洗 → FWSEC/WPR2 → 签名 Booter 起 GSP-RM → V67 四写 payload → **读回校验** → FLR → 链回 Windows Boot Manager（`nvuefi.md:9-13`）。
- **Windows 侧的代价**：① **必须关 Secure Boot**（`nvuefi.md:74-117` 步骤 1；本机已 SecureBoot=False ⇒ 前提已满足）；② **每次冷启动都要过一遍 U 盘**（5 s 倒数确认后自动跑，任何键中止；**解锁是易失的，断电即消失，不落盘**）③ 不换驱动、不用 DDU、不用改注册表；④ **回滚 = 强制重启进原 Windows 项**，最坏 DDU（`nvuefi.md:508-522` 三种失败场景：黑屏 / STOP / 驱动不认卡）。
- 作者自己的风险口径：解锁是"把被禁用的晶体管恢复工作，不是超频"（`nvuefi.md:269`），不改功耗墙；但**未测持续负载热**，社区口径热区 80→100 °C（【未核】，B 站转述）。

## 3. 它解锁什么，以及"矩阵乘速率"怎么变成"首字"

- 解锁对象：**FP16/BF16/TF32 的 tensor-core matmul，前提是 FP32 累加**。GeForce 被钳到半速，解锁后 SS0=0x88888888（满速 BF16）、SS1=0x8（IMLA4）（Zagitta 机制，`repos/gpu-unlock/README.md:157-161`）。**INT8/INT4 路径不受影响**（这条路本来就是满速）。
- 所以问题变成：**我们的 prefill 里有多大比例的 FLOPs 走 FP32 累加的 A16 GEMM？** 这不是猜，我们有实测（`--no-prefill-a8` 强制全 A16 的 A/B，ninfer-limit 跑，日志我已核）：

| 提示 | 默认 prefill | 全 A16 prefill | 比值 | 默认 TTFT | 全 A16 TTFT |
|---|---|---|---|---|---|
| 7,926/7,928 tok | 1.10k tok/s | 396.7 tok/s | **2.777×** | 7.2 s | 20.0 s |
| 23,833/23,835 tok | 1.03k tok/s | 386.2 tok/s | **2.664×** | 23.2 s | 61.8 s |

⇒ **A16 段只占 prefill 时间的 36.1–37.6%**，其余 63.6% 在 int8（A8）路径，解锁对那一半**一滴不给**。
⇒ 交叉验证：全 A16 臂 396.7 tok/s × 48.7 GFLOP/token ≈ **19.3 TFLOPS**，只有被钳峰值 46.78 的 **41%** —— A16 通路本身也没跑满，这也是为什么"解锁 +62%"乘上去只剩 +16%。

## 4. 定量上限（乐观 / 保守）

公式（可复用）：`S = 1/(s_A8 + (1−s_A8)/1.624)`，`s_A8 = 0.636`，`1.624 = 76.71/47.24`（2803 实测 解锁/原厂 BF16 FP32-累加）。

| 场景 | 解锁前 | 乐观 ×1.163 | 省 | 保守 ×1.088 | 省 |
|---|---|---|---|---|---|
| **8k 冷读**（7.9k tok） | TTFT 7.2 s | 6.19 s | **−1.0 s** | 6.62 s | −0.6 s |
| **24k** | TTFT 23.2 s | 19.95 s | **−3.3 s** | 21.3 s | −1.9 s |
| **37k**（日常上限） | TTFT 38.8 s | 33.4 s | **−5.4 s** | 35.7 s | −3.1 s |
| 37k prefill | 969 tok/s | ~1,127 | +16.3% | ~1,054 | +8.8% |
| 200k（552 tok/s） | TTFT ~362 s | ~311 s | −51 s | ~333 s | −29 s |
| **llama.cpp 25.2k 档** | TTFT **334.8 s** | 287.9 s | (−46.9 s) | 307.7 s | (−27.1 s) |
| **decode 任意档** | 107 tok/s | 107 | **0** | 107 | **0** |
| **显存/上下文** | 7,459 MiB / 40k 池 | 不变 | **0** | 不变 | 0 |

**llama.cpp 那一行必须打叉**：它 13.37 ms/token 只有 NInfer 同档的 4.5%，说明瓶颈完全不在 matmul（真在 matmul 的话 46.78 TFLOPS ÷ 48.7 GFLOP/token ≈ 960 tok/s 起步）。因此给它套 36.4% 的份额是错的，实测预期 **≈0–5 s**。同理，**roofline 判定**：
- decode 下限 = 6.3947 GB ÷ 288 GB/s = **22.2 ms/token = 45.1 tok/s**；实测 107 tok/s（计数档）说明靠 ngram/MTP 一次权重趟吐 ≈2.4 token，另一道墙是 host 每轮 51.4 ms。**解锁两道墙都不碰 ⇒ decode +0**。
- prefill 上限 = 由 §3 实测的 A16 时间占比直接封顶 **+16.3%**，与"作者说 +25–55%"不冲突：那个区间是**稠密 FP16/BF16 模型 + 满 FP32 累加**的场景；作者对量化推理自己的说法就是 **llama.cpp/Ollama 量化 GGUF 0–15%**（`repos/gpu-unlock/README.md:66-77`），且明确写 **"LLM decode（memory bound）No change"**、**"INT8/FP8/INT4 models No change"**。

## 5. 代价与风险（真实故障单，不是假设）

| 项 | 事实 |
|---|---|
| 每次冷启动 | 必须插 U 盘过一遍事务，5 s 倒数（`i_know_what_i_am_doing.txt` 才自动跑）；**易失**，休眠不覆盖 |
| 服务中断 | 重启会打断 8091/8081 两个常驻服务与 NInfer 常驻进程 |
| 驱动更新 | 每次换驱动后要重跑（FLR 会把选择器打回原厂） |
| 最坏故障 | Code 12 / 黑屏 / BSOD（#61 / #35 / #55）；#54 说明**驱动绑定时的 FLR 会重新锁上**，TB3/eGPU 场景白干 |
| 工具自身 | #34：`ssdiag` 的内核态驱动把 Windows 干坠机过；#39/#40：服务残留、无 HVCI 预检；#59：下载截断导致 SHA 校验失败 |
| 本机特有 | 显示器在**核显**（`nvidia-smi` display_active=Disabled、iGPU 2560×1440@144），黑屏风险低；但 **GameViewer 是 IDD 虚拟显示**，属"混合模式"，`nvuefi.md:118-132` 明确要求**经"混合关机→重启"**进入，纯 iGPU 关机态会 D3cold 零写中止 |
| 收益侧代价 | 热区可能 80→100 °C、功耗上升（【社区口径，未核】） |

## 6. 结论：**NO-GO**

1. **收益太小**：日常 8–37k 的首字只省 **1.0 / 3.3 / 5.4 s**（占 TTFT 的 8–14%），而每次冷启动都要为它付一次固件写事务 + 5 s 倒数 + 服务重启。
2. **我们的两个真痛点它一点都碰不到**：显存 8 GB（池 32k/64k）与 decode（107 tok/s 计数 / 41.5 散文，双墙 288 GB/s + host 51.4 ms/round）。
3. **风险不对称**：Code 12 / 黑屏的失败面在同类 AMD 平台上是**真实发生过的**（#61、#35），本机组合（AM5 + 616.92 + 26100 + IDD）无先例；收益上限 5 s，故障代价是整机不可用。
4. **要更快首字，先吃软件红利**：网关前缀缓存（67k 命中 84.2 s → 0.54 s，`README.md §0`）与 `--prefill-chunk` 调参的收益确定性远高于硅片解锁；200K 场景的正解是分片（`tools/longdoc.py`，316 s/本，8/8），省 29–51 s 也追不上。
5. **什么情况下才值得回头看一眼**：换引擎/换模型使 A16 段占比 ≥60%（例如跑稠密 bf16 模型、或去掉 PTQ1 的 int8 路由），此时上限会升到 ~1.4×，可复用 §4 公式重算；以及本机多一块盘、愿意把 U 盘常驻并接受每次冷启动多 5 s 时。
