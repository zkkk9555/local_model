# 虚拟内存实测帖汇总 —— 页面文件调大，对本地大模型到底有没有用

> 侦察日期：2026-10-30（Asia/Shanghai）。全部网络证据经代理 http://127.0.0.1:7897 取回。
> 只收**带 URL 且带数字**的一手材料；没有数字的听说法一律标 **【未核源】**。
> 本机未启动/停止任何引擎与服务，未改动 C:/Project/local_model 下任何配置脚本。

---

## 0. 结论先行

1. **调大页面文件唯一确定买到的是「commit limit 变高」**，不是内存、不是显存。commit limit = 物理内存 + 所有页面文件，1:1 线性叠加 —— 本机实测 31.1 GiB + 23.0 GiB = 54.1 GiB（见 §5）；跨机对照 Strata #1607：79.9 GiB RAM + 16 GB 页面文件 = 95.93 GiB，换成 32 GB 页面文件后 = 111.93 GiB，差值正好 16.00 GiB。
2. **对「权重走 mmap」的引擎（llama.cpp 默认、Strata 的 --mmap-experts）收益恰好是 0**：映射页由**模型文件本身**支撑，不进页面文件、不占 commit。唯一有效的是**物理 RAM 里的文件缓存**，页面文件不在这个链路上。
3. **对「专家/权重被当匿名内存 commit」的引擎，页面文件能救的是「崩」而不是「慢」**：Strata #1607 是唯一一份完整 A/B —— 16 GB 页面文件时 commit 撞限、5 次静默崩溃（0xC0000409）；32 GB 页面文件 + 故意占位的 8 GiB commit（不触碰、不占 RAM）后 30 分钟不崩。作者原话：**"the limit, not the load, is what fails"**。
4. **但一旦真的开始换页，代价是灾难级的**：hermes-agent #142082 描述 `--load-mode dio` 把 mmap 换成 committed 内存后，"Windows starts paging to the pagefile and the whole machine becomes unresponsive for minutes"。
5. **对 CUDA/显存申请完全无效**：显存不够时页面文件 1 MiB 都补不上；Windows 上的合法替代是 NVIDIA 控制面板的 **System Memory Fallback**（llama.cpp `docs/build.md:318` 明写），不是 pagefile。
6. **中文侧没有找到任何一份带可复现数字的一手实测**（检索记录见 §4）。中文内容基本是「调大虚拟内存就能跑大模型」的二手教程/AI 生成文，按规则全部标 **【未核源】**；反过来，英文侧的一手实测**系统性地否证**了这个说法。

## 1. 判定表：谁受益、谁无效

| 失败形态 | 页面文件有用吗 | 依据（一手） |
|---|---|---|
| `VirtualAlloc(MEM_COMMIT)` 返回 `ERROR_COMMITMENT_LIMIT`（匿名提交内存不够） | **有用**：抬高 commit limit，把「起不来」变成「起得来」 | Strata #1607；MS《Introduction to page files》 |
| 引擎静默退出 0xC0000409，崩时物理 RAM 还有 7 GiB 空闲 | **有用**（同上，纯 commit 型失败） | Strata #1607 |
| 权重 mmap（llama.cpp 默认 `-lm auto`、Strata `--mmap-experts`） | **完全无效**（0 收益） | llama.cpp `common/arg.cpp`；`CreateFileMappingW` 文档 |
| 专家 arena 被 `cudaHostRegister`/`VirtualLock` 锁定 | **完全无效**（锁定页"保证不写入页面文件"） | `VirtualLock` / `cudaHostRegister` 文档；本仓《页面文件-能不能救8G.md》§2.3 |
| CUDA 显存申请（`cudaMalloc` 不足） | **完全无效** | llama.cpp `docs/build.md:318`；本仓 §1 |
| 大页 `VirtualAlloc` 返回 1450（`ERROR_NO_SYSTEM_RESOURCES`） | **无效**（不是 commit 问题，是物理页碎片/连续性问题） | Strata #2295（复现者实测 commit 还剩 63 GiB 仍 1450） |
| GPU 侧 launch failure（hipErrorLaunchFailure 等） | **无效**（commit limit 188 GB 也照崩） | Strata #1630 |

## 2. 英文侧一手实测（带数字）

### 2.1 Strata #1607 —— 唯一一份「页面文件大小」对照实验 ★最重要

https://github.com/Niko1221/Strata/issues/1607

- 机器：RTX 5060 Ti 16 GB（driver 616.92）/ Ryzen 7 5700X3D / **80 GB RAM（79.9 GiB 可见）** / Win11 Pro 10.0.26200 / Strata 0.1.40.3
- 模型：unsloth **UD-IQ4_XS**，专家 **55.4 GiB**；`strata.exe` private ≈ **78 GiB**（负载中 79.2 GiB）
- 参数：`--max-context 393216 --rope-scaling yarn --rope-scale 1.5 --kv int8 --kv-resident 32768 --expert-cache auto --spec 4 --pcie-frac 0.20 --spec-min-p 0.70`

| 组 | 页面文件（commit limit） | 负载 | 额外 commit | commit 峰值 | 崩溃次数 |
|---|---|---|---:|---:|---:|
| A | 16 GB（95.93 GiB） | agentic，WSL+Docker | — | 95.92 | **5** |
| B | 16 GB（95.93 GiB） | 同样请求录制回放，关 WSL | — | 92.0 | 0 |
| b8 | **32 GB（111.93 GiB）** | agentic + 8 GiB 占位 | 8 GiB | 102.48 | **0** |
| C | 32 GB（111.93 GiB） | 回放，占位压到只剩 0.8 GiB | 到 0.8 GiB | 111.86 | **1** |

- 「占位」= 一个只 `VirtualAlloc(MEM_COMMIT)` 从不触碰的进程：commit +2.00 GiB，**可用 RAM 不变**。因此 b8 组证明了**撑住它的是 commit 额度，不是物理内存**。
- 崩溃现场：commit 111.88 / 111.93 GiB，**物理 RAM 仍剩 7.0 GiB**，退出码 3221226505（0xC0000409）。作者结论原文：**"the limit, not the load, is what fails"**。
- 关键反证（说明页面文件并不是"多出来的内存"）：引擎日志写着 `expert arena read unbuffered (0 of 32 probe reads from the file cache; 9.1 GiB available, 87.2 GiB of files)` —— 专家是从**文件**按需读的，页面文件里没有专家的一个字节。
- 维护者 v0.1.42 的修法也印证了性质：admission 从「只看可用 RAM」改成 **min(可用 RAM, 可用 commit)**，并在 serve 启动时打印 commit 余量 + 页面文件建议。v0.1.43 复测：仍在 commit 111.88/111.93 处崩、private 79.1 GiB —— 说明**加页面文件只是把悬崖挪远，不是把悬崖填平**。

### 2.2 Strata #141 —— committed 数字虚高，页面文件是「预留未用」

https://github.com/Niko1221/Strata/issues/141

- RTX 5060 Ti 16 GB + Ryzen 5 5600 + **48 GB DDR4**，Qwen3.8-Flash-Next IQ2_XS
- 任务管理器：专用 VRAM 15/16 GB、共享 VRAM 23/24 GB、RAM 44/48 GB、**已提交 64/72 GB**；strata.exe = 36 GB RAM + 15 GB VRAM + 23 GB 共享 = 74 GB
- 页面文件约 25 GB，但 resmon 里只看得到 n-gram 的读
- 维护者回复：「Windows also charges the card's VRAM against RAM + page file, which inflates "committed" without any paging (**the page file is reserved, not used**)」；「**the limit is your RAM, not VRAM + RAM**」

⇒ 读任务管理器的"已提交"会严重误导：WDDM 把显存也算进 commit，看起来"页面文件在救命"，其实一个字节都没落盘。

### 2.3 Strata #4605 —— commit 真的被吃干

https://github.com/Niko1221/Strata/issues/4605

- Win11 / **128 GB RAM** / 页面文件 initial 4096 MiB、maximum 8192 MiB、system-managed=false
- `SystemCommitCharge` 145,636,839,424 / `SystemCommitLimit` 145,729,966,080 / `strata-dsv41.exe` 118,554,161,152 → 只剩 **93,126,656 B ≈ 89 MiB** commit，Windows 事件 2004，分配失败
- 作者自己标注：**"no measured pagefile-size A/B"**（只观察、没做对照）——按规则这条只能算**机制证据**，不能算"调大页面文件有效"的实测。
- 评论区的解法是 `--ple-io direct`（避免 PLE 表进 RAM 引发系统换页），不是加页面文件 —— 又一次说明真正的杠杆是**别让引擎把该走文件的东西塞进匿名内存**。

### 2.4 Strata #2295 —— 大页 1450 与 commit 无关；4K 页不掉速

https://github.com/Niko1221/Strata/issues/2295

- 首发：RTX 5080 16 GB + Core Ultra 7 265K + **96 GB DDR5**，IQ3_S，`--max-context 262144`；专家 arena 50,295,996,416 B
- 同一台机器同一配置，大页有时成功有时 `VirtualAlloc error 1450`；失败那些次日志是 `14.9 GiB left of a 107.1 GiB commit limit`。作者直接问：**"Would a pagefile tweak make large pages reliable here?"**
- 复现者（2×5060 Ti 16 GB / i5-12400F / 96 GB DDR4 / Strata 0.1.44.1 / arena 42,916,118,528 B，已授予 `SeLockMemoryPrivilege`）：清空 standby（`RAMMap -Et`）后 Free&Zero 76.1 GB **仍然 1450**；serve 日志 `23.4 GiB left of 139.8 GiB`，即大页申请失败时还有约 63 GiB 空闲 —— **"A commit or working-set quota shortage would normally return 1455 or 1453, not 1450"**，指向物理页碎片而非额度。
- 顺带一个有用的数字：**4 KB 页 vs 大页，解码 56.4 vs 55.9 tok/s（几乎无差），只有启动慢（27–31 s vs 33–42 s）**。

⇒ 这条同时否掉两件事：加页面文件救不了 1450；把大页换成 4 KB 页也不掉速。

### 2.5 Strata #1630 —— 页面文件 188 GB 也救不了 GPU 崩溃（反例）

https://github.com/Niko1221/Strata/issues/1630

- Win10 LTSC 21H2 / RX 7900 XTX 24 GB / 80 GB RAM / 页面文件 **固定 100,000 MB + 4096–35840 MB** → commit limit **≈188 GB**
- 现象：`--prefill 8192` 时整机 commit 一秒内跳 +69 GB、"Virtual Memory Minimum Too Low"、0xC0000409
- 9 天后作者自己更正：**+69 GB 是崩溃之后 WER 给死进程拍快照**（事件日志显示崩溃比跳变早约 45 s），不是病因；真因是 `hipErrorLaunchFailure`（prefill 6144/7500 全平，7936/8192 全崩）
- **教训**：commit 用满 ≠ 页面文件不够。这条是中文圈最常被误读的现象（"看，虚拟内存爆了"），实际是 GPU 侧故障 + 事后快照。

### 2.6 ollama #7798 / #10494 —— 页面文件被"撑爆"，但那是浪费不是收益

- https://github.com/ollama/ollama/issues/7798 ：GTX 1070 8 GB 跑 Phi-3-mini Q4（约 2 GB），`ollama ps` 显示 **20 GB**、63%/37% CPU/GPU，C 盘被 **10–20 GB 页面文件**填满
- https://github.com/ollama/ollama/issues/10494 ：Win11 + ROCm gfx1151，7.0 GB 模型 100% 在 GPU 上，仍把整模型 commit 到系统内存，"**causes massive pagefiles to be created unnecessarily**"

⇒ 两例都是"页面文件被无谓占用"，性能没有因此变好。给 8 GB 卡的启示：**先看是谁在 commit，而不是先加页面文件**。

### 2.7 hermes-agent #142082 —— dio 把 mmap 变成 committed，整机卡死分钟级

https://github.com/NousResearch/hermes-agent/issues/142082

- `--load-mode dio`（supervisor.py 里强制）"uses **committed** memory instead of file-backed mmap pages, so the OS can't just drop pages under pressure and has to swap them out"
- 后果原文："**Windows starts paging to the pagefile and the whole machine becomes unresponsive for minutes**"
- 该 issue 里 MoE 专家钉在 CPU、每个约 20 GB，三个常驻即超 64 GB RAM

⇒ **同一个模型、同一台机器、同样"跑得起来"：mmap 档是"慢"，dio 档是"整机不可用"。** 这是区分"跑得起来但很慢"与"跑不起来"的分水岭：换页一旦发生，就不是 tok/s 的问题，是交互性问题。

### 2.8 llama.cpp #864 —— 41 GB 模型只占 5 GB RAM，0.65 tok/s

https://github.com/ggml-org/llama.cpp/issues/864

- 双 Xeon Silver 4216 + 383 GB RAM + 4×RTX 3090；模型需 **41478.18 MB**，运行时整机只用了 **5 GB** 内存，生成速度 **0.65 tok/s**（Windows 10 21H2，text-generation-webui）
- 维护者解释：mmap 的引入让"内存不够也能跑更大模型"，但会拖慢"内存本来够"的用户；`--mlock` 可关掉
- ⇒ **mmap 的容量来自模型文件，不来自页面文件**。这也是"跑得起来但很慢"的经典量级：**0.65 tok/s**（对比 §2.4 里正常情况 56 tok/s，差两个数量级）。

## 3. 引擎源码/文档怎么说（判定依据，全部一手）

### 3.1 llama.cpp：默认 mmap，权重根本不进页面文件

`common/arg.cpp`（master）`-lm/--load-mode` 帮助文本（约 2704–2713 行）逐字：
> `- auto: mmap, unless a device does not support it`
> `- none: no special loading mode`
> `- mmap: memory-map model (if mmap disabled, slower load but may reduce pageouts if not using mlock)`
> `- mlock: force system to keep model in RAM rather than swapping or compressing`
> `- dio: use DirectIO if available`

`-lzm/--lazy-mode`（约 2719–2731 行）：
> `- on: read the rows of such tensors from disk on demand instead of keeping them resident (requires mmap)`
> `- auto: on, but only for tensors larger than 4 GiB`

⇒ 默认路径是 mmap + 需要时按行读盘。**mmap 页 = 文件支撑页，页面文件不参与**（`CreateFileMappingW`：只有 `hFile = INVALID_HANDLE_VALUE` 时 section 才由系统页面文件支撑，反之由文件支撑）。

### 3.2 llama.cpp：显存溢出在 Windows 上走 NVIDIA 控制面板，不走 pagefile

`docs/build.md:318` 逐字：
> `The environment variable GGML_CUDA_ENABLE_UNIFIED_MEMORY=1 can be used to enable unified memory in Linux. This allows swapping to system RAM instead of crashing when the GPU VRAM is exhausted. In Windows this setting is available in the NVIDIA control panel as System Memory Fallback.`

⇒ 显存不够的正规出口是 **RAM（System Memory Fallback）**，而 RAM 不够时靠的是**减少驻留**（降层/降量化/offload），不是页面文件。

### 3.3 KTransformers：三层里的「Disk」是 prefix cache，不是权重

https://github.com/kvcache-ai/ktransformers/blob/main/README.md#L50
> `**June 30, 2025**: Support 3-layer (GPU-CPU-Disk) prefix cache reuse.`

https://github.com/kvcache-ai/ktransformers/blob/main/README.md#L59
> `**Feb 10, 2025**: Support Deepseek-R1 and V3 on single (24GB VRAM)/multi gpu and 382G DRAM, up to 3~28x speedup.`

⇒ 它的容量口径是 **382 GB DRAM**，落盘那层只服务 prefix cache（可重算的中间态），**权重不落盘**。所以对 KTransformers，"调大页面文件跑更大模型"没有着力点：权重要么在 VRAM，要么在 DRAM。

### 3.4 Microsoft 文档（机制底座）

- 《Introduction to page files》：commit limit = 物理内存 + 所有页面文件之和；达到上限会「freezing, crashing, and other malfunctions」
- `VirtualAlloc`：`MEM_COMMIT` 才从"内存与磁盘分页文件的总量"里记额度，且「Actual physical pages are not allocated unless/until the virtual addresses are actually accessed」
- `VirtualLock`：锁定页「are guaranteed **not** to be written to the pagefile while they are locked」
- Russinovich《Pushing the Limits of Windows: Virtual Memory》：系统可用虚拟地址空间「is NOT limited to RAM + pagefile size … The "extra" is in all the mapped files」
  https://learn.microsoft.com/en-us/archive/blogs/markrussinovich/pushing-the-limits-of-windows-virtual-memory

## 5. 对接本仓既有结论（避免重复造轮子）

本仓 `reports/页面文件-能不能救8G.md` 已经把机制（WDDM segments、cudaMalloc、VirtualLock、CreateFileMappingW）拆到源码/文档级。本文不重复，只补三点**本文新增**的、可交叉验证的数字：

1. **commit limit 的 1:1 线性关系**（本机实测 + 跨机 #1607 双证）：
   - 本机：`TotalPhysicalMemory` 33,409,253,376 B（31.1 GiB）+ `C:/pagefile.sys` 23,552 MiB → `TotalVirtualMemorySize` 56,743,472 KB = **54.1 GiB**（31.1 + 23.0，逐位吻合）；`PeakUsage` **10,001 MiB** ⇒ 这台机器**已经**在用页面文件兜底，而它并没有因此多跑起任何模型。
   - Strata #1607：79.9 + 16 = 95.93；79.9 + 32 = 111.93。
2. **mmap 档的真实速度代价**（来自本机 `strata.exe` 0.1.54 内嵌 help 文本，逐字）：
   > `--mmap-experts  R2.1: opt OUT of the resident expert arena, back to MapViewOfFile. The A/B arm: the mmap's rate depends on the OS page cache holding 34 GB, and measured 71.97 vs 34.78 ms/token cold vs warm.`
   ⇒ 冷/热 **71.97 vs 34.78 ms/token（2.07×）**，且决定因素是**OS 文件缓存**（物理内存），页面文件不在链路里。
3. 本仓 `haven` issue #24（https://github.com/erpzz/haven/issues/24）那次本机实测也记着：**"Minimum available RAM was 15.0 GiB; pagefile use remained about 104 MiB without a configuration change."** —— 跑得好好的时候页面文件几乎没被用到（104 MiB）。

## 6. 给本机的处方（只给建议，不动配置）

1. **别再加页面文件去"换容量"**。8 GB 卡（本机 4060 Ti，8188 MiB）缺的是 VRAM 与 RAM 驻留，页面文件在这两条路上收益为 0（§1 表）。
2. **页面文件该不该调，只取决于一件事：会不会撞 commit limit**。判据不是"内存用了多少"，而是 `SystemCommitCharge / SystemCommitLimit` 的余量。Strata 0.1.42+ 已经会在 serve 启动时打印这个余量（#1607 的修复），本机 0.1.54 可直接看日志。
3. **如果撞的是 commit limit**：先按 `ollama #7798/#10494` 的教训排查"谁在无谓 commit"（WDDM 把显存也计入 commit）；再考虑把页面文件设为**固定大小**（避免动态扩张时的停顿与 C 盘抖动）。这一步只买"不崩"，不买速度。
4. **如果已经在换页**（现象：整机卡住分钟级、磁盘 100%）：立刻减少驻留，而不是加页面文件 —— 见 §2.7，那是"整机不可用"级别，不是 tok/s 变慢。
5. **显存不够的正规出口**：降量化/减层/加 `--mmap-experts` 类的按需读盘，或用 NVIDIA 控制面板的 System Memory Fallback（`docs/build.md:318`），不是 pagefile。
6. **验证方法（只读，不启停引擎）**：
   - `Get-CimInstance Win32_OperatingSystem | Select TotalVirtualMemorySize,FreeVirtualMemory,TotalVisibleMemorySize`
   - `Get-CimInstance Win32_PageFileUsage | Select AllocatedBaseSize,CurrentUsage,PeakUsage`
   - 换页是否真发生：`(Get-Counter '\Memory\Pages Output/sec').CounterSamples.CookedValue`，以及 `\Paging File(_Total)\% Usage`
   - 只有在 **A/B 两次都留了日志与读数** 时才算实测；本仓此前那次"页面文件前后对比"就是因为没留证而被判不成立（haven #24）。

## 8. 一句话回答原问题

**「把 Windows 虚拟内存调大，能不能跑更大的模型？」——不能。** 它能做的只有一件事：把「commit 额度不够导致的启动崩溃」延后（#1607 的 5 崩 → 0 崩是可复现的）；而权重 mmap、专家锁页、CUDA 显存这三条真正的容量瓶颈，页面文件一条都碰不到（#141/#2295/#864 + `VirtualLock`/`CreateFileMappingW`/`build.md:318`）。真要靠磁盘换容量，代价是 0.65 tok/s 那一档的速度（#864），或者整机卡死分钟级（#142082）——那不是"跑得慢"，是"没法用"。
